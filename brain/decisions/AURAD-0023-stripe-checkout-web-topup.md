# AURAD-0023 — На вебе деньги приходят через Stripe Checkout; кошелёк пополняет BFF по данным Stripe, а не браузер

Date: 2026-11-11
Status: accepted (решения владельца 2026-11-11 в `AURAI-0013` «Решения владельца» п. 1–4; задачи —
«да, подготовь задачи, чтобы полностью подключить страйп к вебу»). В live — только после того, как
Stripe активирует аккаунт Silvermind OÜ, и после ворот из «Последствий».
Связано: `AURAI-0013` (выбор PSP, Implementation Notes), `AURAF-0009` (реальные платежи),
`AURAF-0020` (веб, бэклог 011, 037–042), `AURAD-0002` (кошелёк в USD), `AURAD-0009` (сессия
оплачивается с кошелька), `AURAD-0010` / `AURAD-0017` (пополнение через сторы — тот же вид),
`AURAD-0020` (веб на `web.aura-app.cc`)

## Decision

На вебе деньги приходят через **Stripe Checkout** — страницу оплаты Stripe с переходом на неё и
возвратом. Аккаунт Stripe принадлежит Silvermind OÜ. Пополнение на вебе — новый вид пополнения
предоплаченного USD-кошелька (`AURAD-0002`), а не новый путь брони. Сессия по-прежнему
оплачивается с кошелька (`AURAD-0009`), ledger остаётся append-only. В приложениях остаются
сторы (`AURAD-0010`, `AURAD-0017`).

Решено пять вещей:

1. **Сумму зачисления задаёт BFF, в USD.** Checkout Session создаёт BFF: `price_data` в USD, сумма —
   по правилу BFF, сумма из браузера правилом не является. Покупатель платит в своей валюте через
   Adaptive Pricing, а на кошелёк ложится USD-сумма сессии, в какой бы валюте ни списали деньги. Это
   то же правило, что «SKU задаёт зачисление» в `AURAD-0010`.
2. **Зачисляет только BFF и только по данным Stripe.** Основание — одно из двух:
   - вебхук с проверенной подписью: `checkout.session.completed` с `payment_status = paid` или
     `checkout.session.async_payment_succeeded`;
   - сессия, которую BFF сам запросил у Stripe, когда клиент вернулся на сайт.

   Сам факт, что клиент вернулся по `success_url`, ничего не доказывает.
3. **Ключ идемпотентности — ID Checkout Session**: одна сессия — одна запись в ledger,
   уникальное ограничение в БД. `paymentId` веба (UUID попытки) соответствует сессии один к
   одному (`client_reference_id`). Поэтому повторный «старт» с тем же `paymentId` отдаёт ту же
   открытую сессию, а не создаёт вторую.
4. **Возврат и диспут — компенсирующие отрицательные записи; баланс может уйти в минус**, как в
   `AURAD-0010` п. 5:
   - отменённая сессия возвращается на баланс (`AURAD-0009`, без изменений);
   - неистраченный баланс по запросу возвращается на карту (Terms §07). Возврат делает BFF через
     Stripe Refunds, а не человек в Dashboard;
   - возврат, начатый в Dashboard, всё равно попадает в ledger через `charge.refunded` /
     `refund.updated`; не прошедший возврат (`failed` / `canceled`) возвращает сумму на баланс;
   - диспут списывает сумму с кошелька, когда Stripe снимает деньги
     (`charge.dispute.funds_withdrawn`), и возвращает её при `charge.dispute.funds_reinstated`. По
     запросу информации (inquiry) деньги не снимают, поэтому и кошелёк не трогаем.
5. **Оплата на странице Stripe, методы оплаты подключаются в Dashboard, валюта — через Adaptive
   Pricing.**
   - Методы: карты, Apple Pay, Google Pay, Link, iDEAL, Bancontact, BLIK. Остальные — только после
     отдельной проверки; SEPA Debit — нет.
   - 3DS запрашивается для всех карт (`payment_method_options.card.request_three_d_secure: any`).
     Иначе платёж до ~€30 может пройти без 3DS по исключению для мелких сумм, и мошеннический
     диспут ляжет на нас.
   - Лимитов на пополнения в сутки на пользователя нет (решение владельца 2026-11-11). Сумма одного
     пополнения — целые доллары от $5 до $120.
   - Stripe Tax ждёт исследования НДС (`AURAI-0013` шаг 4).
   - Managed Payments Stripe не даёт: услуги с участием человека.

## How it works

- **BFF** (`AURAT-0207`; пути — по её спеке 2026-11-11, сверить с итоговой версией):
  - старт пополнения — `POST /v1/wallet/top-ups/card` → Checkout Session: `mode=payment`,
    `price_data` в USD, `client_reference_id`, `metadata`, `success_url` и `cancel_url` только на
    origin из `WEB_ALLOWED_ORIGINS`, `locale`, `consent_collection.terms_of_service`, короткий
    `expires_at`, 3DS для всех карт;
  - вебхук `POST /webhooks/stripe`: сырое тело запроса и проверка подписи → быстрый ответ 2xx →
    обработка (зачисление, отказ, истечение, возврат, диспут);
  - статус для опроса — `GET /v1/wallet/top-ups/card/:paymentId`; отмена —
    `POST /v1/wallet/top-ups/card/:paymentId/cancel`;
  - возврат на карту — из бэкофиса;
  - всё за отдельным флагом `CARD_TOP_UP_ENABLED`. `NODE_ENV=production` стоит на всех стендах,
    поэтому без флага прод-BFF с включённым биллингом не запустился бы без live-ключей.
- **Веб** (`AURAT-0208`): настоящий `TopUpProvider` вместо фейка, `startCard` → BFF → переход на
  `url`. Маршрут `/checkout` и опрос — из `AURAT-0108`. Отдельная кнопка Apple Pay / Google Pay
  уходит: её показывает сам Checkout.
- **Ключи:** restricted-ключ и секрет вебхука — только в окружении BFF, у веба ключей нет. Для
  разработки — sandbox `Silvermind OU sandbox` (bff-dev и web-dev), live-ключи — только в проде.
- **Аккаунт и публичные данные** — как в `AURAI-0013` «Следующие шаги» п. 1:
  - публичное название Aura, строка в выписке `AURA-APP.CC`;
  - почта поддержки `support@aura-app.cc`;
  - зачисление в USD (multi-currency settlement).

## Why

- **Комиссия и ниша** (`AURAI-0013` §1–2): минимальная комиссия среди тех, кто принимает нишу.
- **Checkout на странице Stripe:**
  - PCI-нагрузка минимальная, SCA и 3DS встроены;
  - Apple Pay и Google Pay работают без файлов на нашем домене;
  - Adaptive Pricing работает только с Checkout Sessions;
  - у iDEAL и Bancontact нет диспутов.
- **Безопасность:** если браузер может сам себе зачислить, кошелёк бесплатен. Поэтому, как и в
  `AURAD-0010`, вся защита — в том, что зачисляет сервер.
- **USD-зачисление — как в мобайле.** Кошелёк в USD от начала до конца, а покупатель видит свою
  валюту, как в сторе. Зачисление, выведенное из списанной суммы, при движении курса рано или поздно
  зачислит больше, чем списано.

## Последствия

- Реализация — `AURAF-0009`: BFF `AURAT-0207`, веб `AURAT-0208` (после BFF и новой версии
  `@aura/contracts`), условия и данные продавца `AURAT-0209`.
- BFF `TECH-DEBT #7` уже закрыт (`AURAT-0027`): append-only `ledger_entries` защищён триггером в
  БД. Stripe — ещё одна сторона, которая может отменить зачисление, поэтому её возвраты и диспуты
  ложатся только компенсирующими записями. `TECH-DEBT #29` (у пользователя нет истории кошелька, и
  возврата он не видит) с картой становится заметнее — решить в `AURAT-0207` или отдельной задачей.
- **Ворота live:**
  - Stripe активировал аккаунт;
  - Terms, Privacy и данные продавца опубликованы (`AURAT-0209`);
  - вопрос НДС закрыт (`AURAI-0013` шаг 4);
  - прод-веб работает на `web.aura-app.cc` (`AURAD-0020`; 2026-11-11 DNS-записи ещё нет);
  - live-ключи и live-вебхук в окружении прод-BFF;
  - Adaptive Pricing и методы оплаты включены в live, в том числе Apple Pay, Google Pay и Link;
  - согласие с Terms в Elements (добавлено 2026-11-13). Варианты: Stripe открыл аккаунту Terms Element
    (это превью, владелец запросил доступ) или своё согласие (веб + BFF). Затем — проверка на sandbox
    со ссылкой на Terms.
- Закрывает бэклог `AURAF-0020` 037–041. Строки 011 (пополнение из шапки) и 042 (продление) —
  в `AURAT-0208`, если владелец включит их в спеку.

## Поправка 2026-11-11 — оплата на странице сайта

Hosted Checkout проверили вживую из слотов, оплата прошла. Владелец: «можно сделать без перехода на
отдельную страницу оплаты? … или мб как-то на той же странице делать». На рекомендацию координатора:
«да, делай по рекомендации тогда».

- **Целевой вид — Embedded Checkout** (`ui_mode: 'embedded_page'`): та же Checkout Session внутри шторки
  веба.
  - Выбор «Checkout, а не своя форма на Elements» в силе.
  - PCI, SCA и 3DS, Adaptive Pricing, iDEAL и Bancontact — те же. Меняется только место показа.
- **Порядок:**
  1. Смёржить hosted: `AURAT-0207` и `AURAT-0208`, оба проверены вживую 2026-11-11.
  2. Затем `AURAT-0211` — BFF и контракты `v0.33.0`.
  3. Затем `AURAT-0212` — веб.
- **Следствия:**
  - у веба появляется публичный ключ Stripe — он не секретный;
  - CSP веба должен пропускать Stripe.js;
  - Apple Pay во встроенной форме требует зарегистрированного в Stripe домена. Пункт «Why» выше
    («без файлов на нашем домене») верен только для hosted.
- **Галочка Terms в Checkout** (`AURAT-0207-011`):
  - в sandbox выключена: `STRIPE_TERMS_CONSENT=none`, это разрешено только с тестовым ключом. В
    sandbox нельзя задать ссылку на Terms — его данные бизнеса доступны только через анкету live;
  - в live галочка обязательна.

## Поправка 2026-11-12 — Elements вместо готовой формы

Встроенную форму (`AURAT-0211` / `AURAT-0212`, `embedded_page`) проверили на web-dev. Владелец: «высота
ифрейма вечно меняется, стили тут выбиваются из наших… Можно отдельно вывести оплату картой и оплату
apple pay, google pay…». Решение владельца: «держим открытой и делаем elements в ней»
(`AURAT-0212-013`).

- **Целевой вид — Stripe Elements с Checkout Sessions** (`ui_mode: 'elements'`). Checkout Session та же:
  зачисление по слову Stripe, вебхук, Adaptive Pricing, 3DS, отмена — без изменений.
- **В шторке Book:**
  - кнопки Apple Pay / Google Pay / Link (`ExpressCheckoutElement`);
  - выбор валюты (`CurrencySelectorElement`, обязателен при Adaptive Pricing);
  - кнопка перехода к шагу оплаты: `PaymentElement` с нашей кнопкой и нашими текстами.
- **Вид** — Appearance API на наших токенах. Payment Intents не используем: Adaptive Pricing есть только
  у Checkout Sessions.
- **Задачи:** BFF и контракты `v0.34.0` — `AURAT-0213`; веб — `AURAT-0212`, спека v2 `015`. Встроенная
  форма работает, пока новый путь не готов. Снятие `hosted` / `embedded` — отдельной задачей.
- **Согласие с Terms в live** нужно для всей сессии, включая кошельки. В sandbox его не проверить: там
  нет ссылки на Terms. Перед live — проверка на sandbox со ссылкой на Terms.
