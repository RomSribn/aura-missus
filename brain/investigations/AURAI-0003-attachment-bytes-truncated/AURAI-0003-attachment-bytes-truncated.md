# AURAI-0003 — Вложения обрезались на 8192 байтах

Дата: 2026-08-21
Статус: **закрыто, причина измерена и устранена** (`aura-app` @ `0d13e54`)
Задачи: `AURAT-0035` (приём), `AURAT-0036` (отправка)

> Ранняя редакция этого файла обвиняла половину BFF — объявленный
> `Content-Length`. **Это было неверно.** Та сторона проверила себя
> исчерпывающе: девять вложений из девяти отдаются целиком по HTTP/1.1 и h2,
> со сжатием и без, с `Range` и `HEAD`, от 60 КБ до 22,9 МБ, на скоростях до
> 40 КБ/с и чтении длиной 561 секунда — длина всегда сходится. Файл переписан
> по факту, а не по догадке.

## Симптом

Картинки от советника рисовались серым прямоугольником, иногда с полосой
изображения сверху; голосовое показывало `0:01`. В Chatwoot те же файлы целы.

## Как нашлось

Три версии подряд оказались неверными: объявленная длина ответа, затем gzip,
затем подписка на прогресс. Каждая была правдоподобной, ни одна не пережила
проверки. Поиск закончился, когда на устройство поставили сборку с трейсом,
который печатал **сколько байт легло на диск и какие первые четыре**:

```
fail status=threw bytes=8192 magic=ffd8ffe0 expected=260800 message=Download interrupted.
fail status=threw bytes=8192 magic=ffd8ffe0 expected=77448  message=Download interrupted.
```

**8192 при любом ожидаемом размере.** Один сегмент Okio. Заголовок JPEG
корректный — значит начало файла настоящее, а продолжения нет.

Ни сеть, ни сервер так себя не ведут: они рвутся на разной длине.
Одинаковое число — это буфер, а не канал.

## Причина

`react-native-blob-util` 0.24.10, путь загрузки в файл, под React Native 0.85.
`ReactNativeBlobUtilFileResp.ProgressReportingSource.read()`:

```java
long read = originalBody.byteStream().read(bytes, 0, (int) byteCount);
if (read > 0) ofStream.write(bytes, 0, (int) read);
return read;                      // в переданный Okio буфер не записано ничего
```

Возвращает число прочитанных байт, но сам буфер оставляет пустым. Потребитель
Okio видит пустоту и прекращает чтение после первого захода: 8 КБ в файл,
`isDownloadComplete()` сравнивает свой счётчик с длиной, не сходится — и
бросает `Download interrupted.`

Отключение `.progress()` ничего не изменило: сломан путь, а не его настройка.

## Устранение

Скачивание переехало на **`@dr.pogodin/react-native-fs`** — нативная загрузка
сразу в файл, свои заголовки, побайтный прогресс, без JS-моста.
`react-native-blob-util` остался на multipart-отправке и открытии файла
системным просмотрщиком.

Подтверждено на устройстве: `ok status=200 bytes=60672 magic=fffb94c4` — файл
целиком, дальше `cache-hit`.

Две файловые библиотеки в одном проекте — это **находка, а не недосмотр**;
записано в `TECH-DEBT.md` пунктом 5, чтобы никто не «упростил» обратно.

## Что попутно исправлено в приложении

Дефекты не причина, но они делали её неисправимой на глаз:

- **Обрыв не удалял недокачанный файл.** Отказ с кодом удалял, а брошенное
  исключение — нет. Огрызок оставался под настоящим именем, следующий запрос
  находил его через `exists` и отдавал без загрузки. Отсюда «серое навсегда» и
  повтор, который ничего не перекачивал (`f1b5a37`).
- **У `<Image>` не было `onError`.** Недекодируемый файл рисовался тем, что
  осилил декодер, — серым прямоугольником, выданным за картинку (`fd5ee58`).
- **Повтор при недекодируемом файле не был ограничен.** Теперь одна попытка,
  затем «This file won't open» без кнопки (`64dfe49`).

## Уроки

1. **Одинаковое число — это буфер.** 8192 при любом размере файла указывало на
   код, а не на канал; три версии до этого искали причину в канале.
2. **Мерить раньше, чем рассуждать.** Диагностическая сборка стоила двух минут
   в цикле `apk → adb install → logcat` и закончила поиск, который три
   правдоподобных гипотезы только удлиняли.
3. **Логи умеют врать — и код возврата тоже.** Первая сборка отрапортовала
   успех, потому что наружу вышел код `tail`, а не gradle. Проверять артефакт,
   а не последнюю строку.
4. **Четыре байта вместо тела.** Магия файла отвечает на вопрос «что это
   вообще» без единого байта чужой картинки в логе.
