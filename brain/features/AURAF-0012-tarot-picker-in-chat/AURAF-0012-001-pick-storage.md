# AURAF-0012-001 — Где живёт выбор карты

Дата: 2026-09-01 · проектное решение, не реализовано

Дизайн требует, чтобы расклад **не переоткрывался**: одна карта на веер,
результат остаётся в истории. Значит выбор — строка в базе, а не состояние
экрана; иначе переустановка вернёт нетронутый веер, а вторая точка входа
(история на другом устройстве) покажет расклад открытым.

## Отдельная таблица, а не колонки в `Message`

Рассматривались обе.

**Колонки в `Message`** сначала выглядели опаснее, чем оказались: я ожидал, что
повторный ингест из Chatwoot затрёт отметку о выборе. Проверено —
`prisma-messages.repository.ts` делает **create-then-read**, а не `UPDATE`:
повторный вебхук проигрывает гонку на `(conversationId, chatwootMessageId)` и
до существующей строки не доходит. Затирания бы не было.

Причина всё же завести таблицу другая, и она про жизненный цикл. `Message` —
таблица **ингеста**: её строки пишет адаптер Chatwoot и после вставки никто не
трогает. Отметка о выборе пишется **пользователем**, один раз, много позже, и
это единственное мутируемое поле во всей таблице. Плюс три колонки, пустые у
99.9% строк.

```prisma
model TarotSpread {
  // Расклад — это одно сообщение, поэтому id сообщения и есть ключ.
  // Первичный ключ здесь бесплатно даёт «один расклад на сообщение».
  messageId      String    @id
  message        Message   @relation(fields: [messageId], references: [id], onDelete: Cascade)

  // Денормализовано намеренно: проверка прав при выборе становится одним
  // JOIN'ом к conversations вместо двух.
  conversationId String
  conversation   Conversation @relation(fields: [conversationId], references: [id])

  // Что задал оператор: 'cups-02'. FK, поэтому ::CUPS_99:: не доедет до базы.
  cardId         String
  card           TarotCard @relation(fields: [cardId], references: [id])

  // Ничего этого нет, пока человек не выбрал.
  pickedAt       DateTime?
  pickedPosition Int?

  createdAt      DateTime  @default(now())

  @@index([conversationId])
}
```

**Зачем `pickedPosition`, если карта от него не зависит.** Три причины, и
только третья про будущее. Это **единственная запись о том, что человек
действительно что-то выбрал** — при варианте A больше нигде этого следа нет.
Это то, чем отвечают на вопрос «а выбор вообще что-то значил»: данные скажут,
что было нажато. И это то, что делает переход на вариант B (несколько
присланных карт, выбор настоящий) **изменением проверки на сервере и нулём
миграций**.

## Запись выбора — один оператор, без транзакции

Права, идемпотентность и гонка закрываются одним `UPDATE`:

```sql
UPDATE tarot_spreads s
   SET picked_at = now(), picked_position = $position
  FROM conversations c
 WHERE s.message_id = $messageId
   AND s.conversation_id = c.id
   AND c.user_id = $userId          -- чужой расклад не выбрать
   AND s.picked_at IS NULL          -- второй тап ничего не меняет
RETURNING s.card_id, s.picked_at, s.picked_position;
```

- **Ноль строк** означает одно из трёх: расклада нет, он не этого пользователя,
  или карта уже выбрана. Первые два — `404` (не `403`: отвечать «не ваш» значит
  подтверждать, что такой расклад существует). Третий — **не ошибка**: двойной
  тап и повтор запроса на плохой связи это норма, поэтому в ответ идёт уже
  записанный выбор и `200`.
- Чтобы различить их, после нуля строк делается один `SELECT` по `messageId` с
  тем же JOIN. Это второй запрос **только на неуспешном пути**.
- Транзакция не нужна: `AND picked_at IS NULL` внутри самого `UPDATE` — это и
  есть гонка, выигранная в один заход.

## Карта не уезжает на устройство до выбора

**`GET /v1/chat/history` не отдаёт `cardId` невыбранного расклада.** Это стоит
назвать прямо: карта задана заранее, и если она приедет вместе с раскладом, то
исход лежит в памяти клиента до того, как человек коснулся экрана. Кто-то,
кто смотрит трафик, увидит ответ раньше вопроса.

Поэтому в истории у невыбранного расклада едет только факт его существования:

```
spread: { picked: null }                                  // веер открыт
spread: { picked: { position, at }, card: TarotCard }      // закрытая карточка
```

Карта приходит **ответом на выбор** — `POST …/pick` возвращает её.

**Это ложится на анимацию, а не спорит с ней.** У дизайна между отделением
карты и переворотом ровно **560 мс** — окно, в которое запрос успевает. Тап →
карта отделяется и запрос уходит; ответ пришёл → переворот. Ответ не пришёл →
карта возвращается в веер и показывается «попробуйте ещё», а не застрявшая
рубашка. Без этого разделения оффлайн-переворот показал бы карту, о выборе
которой сервер никогда не узнает.

## Эндпойнт

```
POST /v1/tarot/spread/:messageId/pick
  { position: 0..6 }
  200 { card: TarotCard, pickedAt, position }   // и на повторный вызов тоже
  404                                            // нет, не ваш, или не расклад
```

`position` валидируется по числу карт в веере; не по колоде — веер это семь
рубашек, а не семь карт.

## Что происходит на приёме из Chatwoot

Сообщение советника с токеном превращается в **сообщение плюс строку
`TarotSpread`, в одной транзакции** — расклад без своей строки был бы веером,
который невозможно выбрать.

- Токен **вырезается из `content`** там же. Приложение копию не парсит никогда
  (`map-message.ts` уже несёт долг «чтения копии» для маркеров сессии — второго
  такого места не заводим).
- **Неизвестная карта** (`::CUPS_99::`) не создаёт расклад: `cardId` — внешний
  ключ, и до базы такое не доедет. Оператору уходит **приватная заметка** в
  Chatwoot с текстом ошибки; сообщение клиенту не публикуется вовсе, иначе в
  переписке повиснет веер, который никогда не откроется.

## Как о выборе узнаёт оператор

**Приватной заметкой в Chatwoot.** Не сообщением от лица пользователя: оно
вернулось бы к нам вебхуком и нарисовалось пузырём, которого человек не писал.
Приватные заметки для этого и годятся — адаптер их отбрасывает на приёме
(`chatwoot-webhook.controller.ts`: «activity/private/template never leave the
adapter»), так что заметка видна оператору и не видна приложению.

## Разделитель «YOU CHOSE THE HERMIT» — не хранится

Он **выводится клиентом** из состояния расклада и рисуется сразу под ним. Так
он не может разъехаться с карточкой результата и не занимает строки в таблице
сообщений. Это отличается от маркеров платной сессии, которые хранятся, — и
отличается по делу: те пишет сервер и их видит оператор в своей ленте, а этот
существует только на экране.
