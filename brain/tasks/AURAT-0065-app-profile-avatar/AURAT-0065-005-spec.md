# AURAT-0065-005 — План реализации

Дата: 2026-09-08
Статус: **ждёт одобрения владельца**

Отдельного файла фичи нет: `AURAF-0015` написана, эта задача закрывает `UI`
строки `009`. Серверная половина влита (`aura-bff` `develop` = `85806af`,
контракты `v0.17.0`), решение о хранении — `AURAD-0013`.

## Что строится

```
entities/user/
  ui/                          ← папки сегодня нет
    ProfileAvatar.tsx          # фотография или орб — одно решение, три места
    PhotoRow.tsx               # ProfileAvatar + тиловая «Change photo»
  api/avatar-api.ts            # PUT и DELETE /v1/me/avatar
  model/types.ts               # Profile += avatarId
  model/profile-store.ts       # ответ на PUT/DELETE — полный профиль

features/profile-photo/
  model/use-profile-photo.ts   # источник, выбор, загрузка, отказ
  lib/refusal-copy.ts          # AvatarRefusalCode → фраза человеку
  ui/PhotoSourceSheet.tsx      # камера / библиотека / убрать
```

`ProfileAvatar` отдельно от `PhotoRow` потому, что мест показа три, а мест с
кнопкой — два. Один компонент решает «фотография или орб», и это решение не
размазано по экранам.

## Решения, которые выношу

### D1 · Чем показывать байты

Аватар за токеном, публичного адреса нет. Два пути разобраны в
`004-context` §1.

**Предлагаю `<Image source={{ uri, headers }}>`.** React Native кладёт
заголовки в запрос на обеих платформах и кэширует по URI — а URI несёт
неизменяемый `avatarId`, поэтому замена меняет адрес и старая картинка
перестаёт находиться сама собой. Это то самое свойство, ради которого id
положен в путь маршрута.

Файловый кэш по образцу `attachment-cache.ts` дал бы прогресс, дедупликацию и
повтор с обновлённым токеном — но это полторы сотни строк на задачи, которых у
одной картинки 56–72 pt нет: ни прогресса показа, ни шаринга, ни проигрывания.

**Цена, которую надо назвать:** загрузчик картинки не умеет повторить с
обновлённым токеном, как это делает кэш вложений на 401. Лечится в фиче: токен
берётся на монтировании через `getIdToken()` (Firebase сам обновляет его
вблизи истечения), а на ошибке — один повтор с `getIdToken(true)` и сменой
`key`. Если и это не поможет — рисуется орб, а не битая картинка.

### D2 · Как убрать фотографию

Дизайн рисует только «Change photo». На сервере `DELETE /v1/me/avatar` есть.
Без интерфейса убрать её будет **нечем вообще**.

**Предлагаю не вторую кнопку, а лист по нажатию на «Change photo»**: «Сделать
фото» / «Выбрать из галереи» / «Убрать фотографию» — последний пункт только
когда фотография есть. Форма уже написана в `use-attachment-draft.ts`, включая
неочевидное: пикер открывается **после** того, как шит закрылся, иначе на iOS
он не появляется.

Это добавление к нарисованному. Отвергнуть можно — тогда убрать фотографию
будет нельзя, и это стоит решить сознательно, а не по умолчанию.

### D3 · Показывать ли фотографию в шапке настроек

`PROFILE_FORMS.md` рисует `PhotoRow` на экранах 28 и 29; в `ProfileCard`
(шапка настроек) нарисован орб. Написано это тогда, когда фотографии не
существовало.

**Предлагаю показывать** — `ProfileAvatar` вместо `ProfileOrb`, кнопки там нет
(рядом уже есть «Edit», ведущий на экран правки). Иначе лицо человека видно на
двух экранах, куда заходят редко, и не видно на том, который открывают чаще
всего. Правка — одна строка на месте.

### D4 · Целевой размер при выборе

Самое крупное место показа — 72 pt, то есть 216 px на 3x.

**Предлагаю 1024 px по большей стороне**, `quality: 0.9`. Это ~200–400 КБ:
с запасом под крупный показ, если он когда-нибудь появится, и вчетверо ниже
серверного потолка в 4096. Меньше (512) тоже хватило бы сегодня, но повторная
загрузка ради размера — это то, чего человек делать не станет.

## Состояние загрузки и отказ

Требование заглушки: фотография, которая «как будто загрузилась», — худший из
исходов. Значит:

- пока идёт загрузка, показывается **выбранный локальный файл**, а не старый
  аватар и не пустота: иначе человек нажал, подождал и не увидел ничего;
- сверху — индикатор, и «Change photo» на это время неактивна;
- при отказе локальный файл **убирается**, возвращается прежнее состояние, и
  под строкой встаёт фраза;
- фразы разные по коду (`AvatarRefusalCode`): «слишком большой файл», «такой
  файл не подойдёт», «слишком большая картинка» — это то, что человек может
  исправить. Отсутствие кода означает «попробуйте ещё раз», и только тогда
  повтор предлагается.

## Тесты

- `use-profile-photo` — выбор, загрузка, каждый код отказа, откат превью при
  отказе, недоступность кнопки во время загрузки.
- `ProfileAvatar` — фотография при `avatarId`, орб при `null`, орб при ошибке
  загрузки картинки (а не пустое место).
- `avatar-api` — форма запроса, разбор ответа схемой контракта.
- `profile-store` — `avatarId` приезжает из ответа на `PUT` и обнуляется после
  `DELETE`.
- Экраны — что `PhotoRow` подключён на обоих и что размеры те, что в дизайне.

## Что проверяем за серверную половину

Три пункта из `001`, ни один не виден из интерфейса:

1. при замене **старый объект в бакете исчезает** (смотреть в `aura-user-media`);
2. аватар появляется **в карточке контакта** на агентском столе;
3. **шов провижининга**: фотография, поставленная до первого разговора, уезжает
   столу в момент создания контакта.

## Чего в задаче нет

- **Кроп и редактор.** Пикер отдаёт что отдаёт; рамка кадрирования — отдельный
  разговор и отдельный нативный модуль.
- **Аватар рядом с сообщениями в чате.** Дизайн такого не рисует, и советник
  видит человека на своей стороне, а не человек себя.
- **Проактивная модерация** — решение владельца по серверной половине:
  реактивная, путь снятия построен.
