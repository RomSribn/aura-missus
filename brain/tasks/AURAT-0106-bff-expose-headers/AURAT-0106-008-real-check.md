# AURAT-0106-008 — проверка реальными запросами

2026-10-20. Владелец: «проверь реальные запросы на работоспособность и обратную
совместимость с мобайл флоу». В слоте стек не поднимаем — проверка без БД / Redis /
Chatwoot.

## Как

Одноразовый скрипт (scratchpad, в репо не попал): Nest-приложение через **продовый**
`configureApp` (helmet, rate-limit 120/мин, CORS — тот же порядок), реальные
`AdvisorsController` / `SessionsController` и глобальный `FirebaseAuthGuard`, сервисы
подменены. Слушает настоящий порт. Против него:
- **headless Chrome** (настоящая CORS-политика браузера) со страницы разрешённого origin
  и чужого: каталог, запрос с `Authorization` (через preflight), 401 по просроченному
  токену, 401 на закрытом маршруте, затем запросы до 429;
- **мобильный флоу** — `fetch` без `Origin`, как RN: те же запросы и 429.
Два дерева: feature и `develop` (копия слота с `web-origins.ts` из `develop` —
других отличий в коде нет); allowlist задан / пуст.

## Результат

Браузер, разрешённый origin — `develop`: `Date` = `null` на всех ответах, `Retry-After`
на 429 = `null`. Feature: `Date` читается на 200 / 401 / 429, `Retry-After` на 429 =
`"50"`. Статусы те же; preflight для запроса с токеном проходит.

Браузер, чужой origin — оба дерева: `TypeError: Failed to fetch` на всём. Ничего не
открылось.

Мобильный флоу:
- allowlist пуст (CORS-плагина нет) — заголовки ответов **идентичны** `develop`
  на 200 / 401 / 429;
- allowlist задан — единственная разница: `access-control-expose-headers: Date,
  Retry-After` (то, что описано в `007`); статусы, тела, `retry-after` на 429 и
  остальные заголовки без изменений. RN `fetch` CORS не применяет — заголовок ему
  безразличен.
- `/ws` не затронут: `isAllowedWsOrigin` не менялся, его тесты зелёные.

Живые стенды (только чтение, GET / OPTIONS, на коде `develop`):
- манор `:3010` (`WEB_ALLOWED_ORIGINS=http://localhost:5173`): `allow-origin` есть,
  `expose-headers` нет — пробел подтверждён; без `Origin` — CORS-заголовков нет.
- bff-dev: то же; прокси пропускает `access-control-*` как есть и своих CORS-заголовков
  не добавляет — значит, после выкладки `expose-headers` дойдёт до браузера.

## Замечено попутно (вне задачи)

Allowlist bff-dev сейчас содержит только `http://localhost:5173`: для
`Origin: https://dev.aura-web.app` `allow-origin` не выдаётся. Если веб-dev будет
открываться с этого домена — это настройка env bff-dev, не код. Решение — за владельцем.
