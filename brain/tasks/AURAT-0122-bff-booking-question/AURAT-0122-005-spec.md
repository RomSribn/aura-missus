## 1. Контракт — `@aura/contracts` `v0.24.0` (минорная)

**Запрос** `POST /v1/advisors/:advisorId/sessions` — `BookSessionRequest`:

```ts
question: z.string().trim().max(250).optional()
```

- необязательное; отсутствие, `""` и строка из одних пробелов — «вопроса нет» (не 400):
  клиенту не нужно отдельно чистить пустое поле;
- лимит 250 — как у Ask веба; считается после `trim`; длиннее — 400 с обычным сообщением
  валидации (без значения);
- работает и для слота (`startsAt`), и для «Now» (`startNow`).

**Ответ** — `Session` получает поле:

```ts
/** The question the user booked with (trimmed), or null. Theirs alone — never shown to anyone but them and the desk. */
question: z.string().nullable().default(null)
```

Поле ответа **необязательно на проводе** — по прецеденту README contracts (`sessionInvite`
`v0.14.0`, `reviews` `v0.15.0`, `firstSessionOffer` `v0.21.0`): клиент на `v0.24.0`
разбирает ответы BFF, где поля ещё нет, а после разбора оно всегда `string | null`.
Иначе приложение, поднявшее тег раньше выкатки BFF, не разобрало бы ни одной сессии.

Отдаётся везде, где отдаётся `Session`: ответ брони/переноса/продления, `GET /v1/sessions`,
`GET /v1/sessions/:id`, `GET …/active`, сокет `session.updated`. Нужен вебу для Booked
(«{name} has your question…»), Upcoming-карточки и детали `/sessions` (строка «Question»).
Старые клиенты новое поле игнорируют (zod срезает неизвестные ключи); приложение
(App ✗) ничего не шлёт — у его сессий `question: null`.

**OpenAPI** (`src/contracts/openapi.ts`, build rules BFF — контракт публикуется и через
OpenAPI): `question` в `bookSessionRequestOpenApi` (`string`, `maxLength: 250`, не в
`required`) и в `sessionOpenApi` (`string`, `nullable: true`). Через `sessionOpenApi` поле
попадает во все ответы с сессией.

**Повтор брони** (дописать в комментарий `BookSessionRequest`): тот же `idempotencyKey`
отвечает исходной сессией **с исходным вопросом**; вопрос повтора, как и слот/блок, не
сравнивается и не перезаписывает исходный (правило `AURAT-0109`, без 409).

## 2. Хранение

- Prisma `Session.question String?` + миграция `ADD COLUMN "question" TEXT` (nullable,
  без бэкфилла). Пишется один раз — в транзакции брони; перенос, отмена, продление его не
  трогают. Менять вопрос после брони нельзя (отдельного эндпоинта нет — вне скоупа).
- **Удаление аккаунта** (`AURAT-0042`): сессии остаются ради денег, но вопрос — личный
  текст человека → в том же `updateMany` `question: null` рядом с `conversationId: null`.
  Заметки с вопросом в Chatwoot уходят вместе с контактом при удалении аккаунта
  (`AURAT-0042`).

## 3. Как вопрос видит чаттер — только приватная заметка

- В **заметку стола** (`DeskNoteChannel`) о брони (`booked`) дописывается вопрос цитатой:
  ```
  Paid session booked — 30 min block, Thu 23 Oct, 14:00 UTC.
  Client's question:
  > …текст…
  ```
- Тот же вопрос — в заметке **`started`** (начало сессии): это и напоминание чаттеру в
  момент старта, и единственная заметка у моментальной брони («Now» рождается `ACTIVE` и
  `booked` не шлёт). Итого у запланированной брони вопрос в двух заметках (при брони и на
  старте), у «Now» — в одной. Заметки `rescheduled` / `cancelled` / `starting-soon` — без
  вопроса.
- Текст берётся из базы **в момент доставки** (канал и так перечитывает сессию) — в джобу
  Redis вопрос не кладём; вопрос, стёртый удалением аккаунта, уже не уйдёт.
- **Не** в служебный чат Telegram (`StaffChatNoticeChannel`): чат третьей стороны, правило
  «never the client» (build rule 3) — там остаётся как есть.
- **Не** сообщением в разговор: оно стало бы сообщением человека в его треде (дубль, если
  веб ещё и положит вопрос в composer) и ушло бы в историю чата. Человек вопрос в треде
  не получает ни в каком виде; видит его только в своих сессиях.

## 4. Логи и безопасность

- Текст вопроса не логируется нигде (тела запросов логгер не пишет — проверено; в новых
  местах — только id сессии). Ошибка валидации длины — без значения.
- Тест: заметка `booked`/`started` с вопросом и без; цитата многострочного вопроса
  (каждая строка с `> `).

## 5. Тесты (pure, в слоте)

- разбор `bookSessionRequestSchema` (в `aura-contracts` тест-раннера нет — только сборка
  и typecheck, поэтому поведение проверяют спеки BFF): `trim`, `""`, одни пробелы, ровно
  250 — принято, 251 — отказ; текст ошибки не содержит значения вопроса;
- разбор `sessionSchema`: ответ без `question` → `question: null`;
- `sessions.service.spec`: бронь с вопросом → репозиторий получает обрезанный текст, `""` →
  `null`; повтор с другим вопросом → исходная сессия и исходный вопрос; `toDto` отдаёт
  `question`;
- `desk-note.channel.spec`: `booked`/`started` с вопросом и без; остальные виды — без;
- `staff-chat.channel.spec`: вопроса нет в тексте;
- `prisma-account-erasure.repository.spec`: `question: null` в обновлении сессий.
- Живая проверка (бронь → заметка в Chatwoot, `GET /v1/sessions/:id`) — в маноре после
  мёржа.
