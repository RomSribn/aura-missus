# AURAT-0045-001 — Шрифты дизайна: их нет в приложении вовсе

Дата: 2026-08-28
Исполняет: половина приложения — `aura-app-manor`, slave-1,
ветка `feature/AURAT-0045-design-fonts`
Откуда: наблюдение владельца — «шрифт в приложении отличается от того, что
лежит в дизайне»
Критичность: визуальная, но сквозная — касается каждого экрана

## Что измерено

| проверка | результат |
|---|---|
| Файлы `.ttf` / `.otf` в репозитории | **ни одного** |
| `react-native.config.js` (линковка ассетов) | отсутствует |
| `UIAppFonts` в `ios/PsychoApp/Info.plist` | отсутствует |
| `android/app/src/main/assets/fonts/` | отсутствует |
| `theme.typography.fonts.display` / `.body` | `'System'` |

Тема единственная, где остался след умысла:

```ts
display: 'System', // Will be replaced with BricolageGrotesque when added
body: 'System',    // Will be replaced with HankenGrotesk when added
```

**Шрифты никогда не добавлялись.** Приложение рисуется системным: San Francisco
на iOS, Roboto на Android. Отсюда и второй, менее заметный эффект: один и тот же
кегль выглядит по-разному на двух платформах — это два разных шрифта.

Дизайн просит (`design_handoff_aura/README.md` §Typography):

- **Bricolage Grotesque** — заголовки, веса 700/800
- **Hanken Grotesk** — текст и интерфейс, веса 400/500/600/700

Файлы в хендоффе не передавались; прототип тянет их с Google Fonts. Обе —
**SIL Open Font License 1.1**, встраивание в приложение разрешено.

## Почему это не «положить два файла»

Решающее правило прочитано в исходнике RN 0.85
(`ReactAndroid/.../common/assets/ReactFontManager.kt`), а не в документации.

Для шрифтов, подключённых **как ассеты** (обычный путь `react-native-asset`),
Android знает ровно четыре начертания на семейство:

```kotlin
private val EXTENSIONS = arrayOf("", "_bold", "_italic", "_bold_italic")
```

а вес перед выбором файла схлопывается:

```kotlin
public val nearestStyle: Int
  get() = if (weight < BOLD /* 700 */) { NORMAL } else { BOLD }
```

То есть **400/500/600 → обычное, 700/800/900 → жирное**, и никаких промежуточных
весов. Синтетического утолщения на этом пути тоже нет: `apply()`, который на
API 28+ делает `Typeface.create(typeface, weight, italic)`, вызывается **только**
для второго пути (ниже), а не для ассетов.

### Что это значит для нашего кода

Замерено разбором стилевых блоков — какие веса стоят рядом с каким семейством:

| семейство | вес | мест | что станет на Android через ассеты |
|---|---|---|---|
| Display | 700 | 37 | жирное ✔ |
| Display | 800 | 3 | жирное — **800 неотличимо от 700** |
| Display | 600 | 1 | обычное — выпадает из ряда |
| Body | 700 | 44 | жирное ✔ |
| Body | 600 | 38 | **обычное — полужирный пропадает** |

Тридцать восемь мест полужирного текста на Android стали бы обычными, тогда как
на iOS остались бы полужирными. Это ровно то расхождение платформ, ради
устранения которого задача и заводится, — только заметное сильнее, чем сейчас.

## Два пути, и выбирать надо здесь

**A. Ассеты (`assets/fonts/`, `react-native-asset`).** Просто, нативного кода
нет. Цена — таблица выше: два начертания на семейство, полужирный на Android
теряется.

**B. `res/font` + XML-семейство + `addCustomFont`.** Документация в том же
исходнике говорит прямо: «To support multiple font styles or weights, you must
provide a font in XML format». Тогда работает ветка

```kotlin
if (customTypefaceCache.containsKey(fontFamilyName)) {
  return typefaceStyle.apply(customTypefaceCache[fontFamilyName])
}
```

а `apply()` на API ≥ 28 делает `Typeface.create(typeface, weight, italic)` —
настоящий подбор по весу. Цена: XML-ресурсы шрифтов и **одна строка нативного
кода** в `MainApplication.kt` на каждое семейство.

**Оговорка, которую надо знать:** `minSdkVersion` = 24. На API 24–27 (Android
7.0–8.1) `apply()` уходит в `Typeface.create(typeface, nearestStyle)` и веса
схлопываются даже при варианте B. То есть точные веса — это Android 9 и новее.

**Рекомендация: B.** Иначе задача чинит один симптом и заводит другой.

## Что я предлагал вчера и от чего отказываюсь

В разговоре я предположил, что придётся заводить `theme.typography.font(variant,
weight)` и переводить на неё **126 мест**, задающих вес. **Это не нужно.** При
варианте B существующие `fontWeight` продолжают работать как есть: подбор
делает платформа. Правок в 126 местах не будет — меняется тема (два имени
семейств) и сборочная обвязка.

Правильный объём в разы меньше, чем я назвал. Стоит записать, потому что оценка
была озвучена вслух.

## Объём

1. **Файлы шрифтов.** Статические начертания с Google Fonts (не вариативные —
   поддержка вариативных в RN на Android неровная). Display: 700, 800. Body:
   400, 600, 700. Пять файлов, порядка 50–150 КБ каждый.
2. **iOS**: файлы в проект + `UIAppFonts` в `Info.plist`.
3. **Android**: файлы в `res/font/`, по XML-семейству на каждое с `app:fontWeight`,
   и `addCustomFont` в `MainApplication.kt`.
4. **Тема**: `fonts.display` / `fonts.body` получают настоящие имена вместо
   `'System'`. Имя должно быть **одно на обе платформы** — на Android его
   выбираем мы (аргумент `addCustomFont`), значит подгоняем под то, которое
   отдаёт iOS.
5. **Две аномалии** в коде, которые стоит убрать заодно: единственное место с
   display/600 и единственное с явным body/600 выпадают из ряда весов дизайна.

## Что решить до кода

1. **Вес 500 у Hanken** дизайн называет, а код не использует ни разу.
   Не тащить файл ради нуля мест?
2. **Вариант A или B.** Рекомендация — B; A дешевле, но теряет полужирный на
   Android.
3. **Скачивание файлов** — это обращение к Google Fonts. Подтвердить.

## Риск и приёмка

Проверяется **только на устройствах, обеих платформах**, и глазами: юнит-тест
может подтвердить, что тема отдаёт имя семейства, но не то, что начертание
подхватилось. Отдельно проверить Android **9 и новее** — на 7–8 веса схлопнутся
по причине выше, и это не дефект сборки.

Отдельный риск: неверное имя семейства даёт **молчаливый откат на системный
шрифт** — не ошибку, не пустой экран, а просто прежний вид. То есть «не
сработало» и «не собралось» выглядят одинаково, и проверять надо глазами.
