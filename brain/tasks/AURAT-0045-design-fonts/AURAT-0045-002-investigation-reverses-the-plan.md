# AURAT-0045-002 — Разведка по файлам переворачивает выбранный вариант

Дата: 2026-08-28
Отменяет: рекомендацию из `-001` (вариант B: `res/font` + XML + `addCustomFont`)
Повод: решения владельца приняты (B, без веса 500, скачивание разрешено), и
первым шагом реализации оказалась проверка самих файлов

## Что нашлось в файлах

Google Fonts публикует обе гарнитуры **только вариативными** — статических
начертаний в `google/fonts` нет. Статика есть в апстримах
(`ateliertriay/bricolage`, `marcologous/hanken-grotesk`), оттуда и взята.
Скачано шесть файлов, ~608 КБ, лицензии OFL 1.1 рядом.

Затем — имена внутри файлов, прочитанные из таблицы `name`:

| файл | family (id 1) | typographic family (id 16) |
|---|---|---|
| BricolageGrotesque-Regular | `Bricolage Grotesque` | — |
| BricolageGrotesque-Bold | `Bricolage Grotesque` | — |
| **BricolageGrotesque-ExtraBold** | **`Bricolage Grotesque ExtraBold`** | `Bricolage Grotesque` |
| HankenGrotesk-Regular | `Hanken Grotesk` | — |
| HankenGrotesk-Bold | `Hanken Grotesk` | — |
| **HankenGrotesk-SemiBold** | **`Hanken Grotesk SemiBold`** | `Hanken Grotesk` |

Это обычное RIBBI-именование: под одним «старым» семейством умещаются только
Regular / Italic / Bold / BoldItalic, а остальные веса получают **собственное**
`family(1)`, и связывает их лишь id 16.

## Почему это ломает предпосылку варианта B

Вариант B держался на том, что одна строка `fontFamily` плюс `fontWeight`
работает на обеих платформах: Android подберёт вес через XML, iOS — сам.

**Вторая половина не подтверждается.** iOS ищет шрифт по имени, и
`fontNamesForFamilyName` возвращает начертания, зарегистрированные под *старым*
семейством. `Hanken Grotesk SemiBold` под `Hanken Grotesk` не попадает. Это
известная и до сих пор открытая история в RN (issues 20788, 42116), а
общепринятая практика — **указывать конкретное начертание как `fontFamily`**, а
не полагаться на `fontWeight`.

**Проверить это по исходнику отсюда нельзя:** в RN 0.85 реализация `RCTFont`
поставляется собранной, на диске только заголовки. Так что это не измерение, а
чужой опыт — но он согласуется с тем, что видно в самих файлах.

## Что предлагается вместо B

**Обращаться к каждому начертанию по имени, на обеих платформах, и не
использовать `fontWeight` для выбора файла.**

- **iOS**: `fontFamily: 'HankenGrotesk-SemiBold'` — прямое совпадение по имени,
  без подбора и без догадок.
- **Android**: обычные ассеты, где имя семейства = имя файла. Файл
  `HankenGrotesk-SemiBold.ttf` даёт семейство `HankenGrotesk-SemiBold`.

Следствия, и они хорошие:

1. **Вариант B больше не нужен** — ни XML-ресурсов, ни строки нативного кода в
   `MainApplication.kt`.
2. **Исчезает оговорка про API 28**: схлопывание весов было свойством
   `nearestStyle`, а при отдельном семействе на начертание схлопывать нечего.
   Работает начиная с `minSdk` 24.
3. Пропадает главный риск из `-001` — «молчаливый откат на системный шрифт»
   из-за неверно угаданного имени: имя берётся из самого файла.

## Цена, и это ровно то, от чего я отказывался в `-001`

Раз `fontWeight` перестаёт выбирать начертание, его нельзя оставлять рядом с
именем начертания — иначе iOS начнёт синтетически утолщать уже жирный шрифт.
Значит **правки в местах, задающих вес, всё-таки нужны**.

В `-001` я записал, что рефактор 126 мест не требуется. **Это было неверно**, и
неверно по той же причине, по которой была неверна первая оценка вслух: я
рассуждал об Android, проверив только Android, и распространил вывод на iOS.
Второй раз за задачу.

Честный объём: тема получает `font(variant, weight)` → имя начертания; общий
`Text` резолвит семейство из своего пропа `weight` в одном месте; локальные
стили, задающие `fontWeight`, переходят на неё. Точное число мест замерю до
кода и покажу, а не назову на глаз.

## Что нужно от владельца

Решение `-001` («вариант B») принималось до этих находок. Предлагаю заменить
его на схему выше — она проще, надёжнее и снимает оговорку про версии Android.
Ценой рефактора, которого я обещал избежать.
