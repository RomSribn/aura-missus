# AURAT-0052-001 — Регистрация FCM-токена сдаётся с первой попытки и молчит

Дата: 2026-09-01
Статус: заведена, не начата
Репозиторий: **aura-app** (половина приложения; на BFF делать нечего)
Приоритет: **P2** — ничего не сломано и не падает, но отказ невидим, а цена
отказа — весь сеанс без пушей
Происхождение: находка на полях `AURAT-0050` (BFF-манор). Сама гонка в
`ensureUser` починена и смержена (`aura-bff` `develop` @ `fa12225`); эта задача
про то, что вскрылось рядом и к BFF отношения не имеет

## Что сейчас

`src/features/push/model/push-registration.ts`, `usePushRegistration`:

```ts
try {
  await notifee.requestPermission();
  const token = await messagingService.getToken();
  if (!disposed) {
    await registerDevice(token, devicePlatform());
  }
} catch {
  // Permission denied or offline — background delivery just stays off.
}
```

Шапка хука обещает: «Registration failures are silent — the next sign-in / app
start retries». Обещание правдиво — и в нём же проблема: **внутри сеанса
второго шанса нет**. Одна неудачная попытка, и устройство остаётся
незарегистрированным до перезапуска приложения или ротации токена.

Рядом второе такое же место:

```ts
unsubscribeRefresh = messagingService.onTokenRefresh(token => {
  registerDevice(token, devicePlatform()).catch(() => {});
});
```

Тут тишина дороже: ротация означает, что старый токен уже мёртв, и провал
регистрации нового оставляет пользователя без пушей, даже если при старте всё
прошло.

## Почему это стоит чинить

Один `catch` смешивает четыре разных исхода, и сегодня они неотличимы:

1. **Отказ в разрешении** — терминальный. Тишина уместна, ретрай бессмысленен.
2. **Сеть / офлайн** — транзиентный. Холодный старт в метро выглядит ровно так.
3. **5xx от BFF** — транзиентный.
4. **4xx (кроме 401)** — наш баг. Ретраить нельзя, но и молчать нельзя: сейчас
   он не оставляет ни следа.

Обратной связи нет ни в одном из четырёх: приложение считает себя
подписанным, сервер о нём не знает, человек молча не получает то, ради чего
строилась связка вебхук → пуш.

Один из этих 5xx — `P2002` из `AURAT-0050` — теперь ушёл. Он был лишь одним из.

## Что исполнителю важно знать заранее

- **Ретрай безопасен, дублей не создаст.** `registerDevice` — это
  `PUT /v1/devices/:token`, на BFF это `DevicesService.register` →
  `devices.upsert(user.id, token, platform)`. Идемпотентно by design
  (правило сборки BFF #6).
- **Что именно прилетает в `catch`.** `BffApiError` несёт `status` и не несёт
  тела (в приложении есть правило: тела ответов не попадают в ошибки и логи —
  там может быть текст, который человек написал). Сетевой сбой прилетает
  ошибкой `fetch`, а не `BffApiError`, — по этому их и различать. **401 свой
  ретрай уже имеет**: `bffRequest` один раз повторяет запрос с принудительно
  обновлённым токеном, поэтому отдельной ветки на 401 не нужно.
- **Паттерны в проекте есть, новых заводить не надо.** Капнутый экспоненциальный
  бэкофф с джиттером — `src/shared/api/bff/ws-client.ts`. `AppState` —
  `src/features/push/model/notification-taps.ts` (соседний файл в этой же фиче)
  и `src/features/chat/model/ChatProvider.tsx`.
- **`NetInfo` в зависимостях нет.** Тащить его ради этой задачи — отдельное
  решение, не подразумевается. `AppState` + бэкофф закрывают основной сценарий
  (свернул–развернул после того, как сеть вернулась) без новой зависимости.
- **`unregisterCurrentDevice` не трогать.** Её `catch` осознан и подкреплён:
  BFF сам вычищает мёртвые токены по кодам FCM
  (`registration-token-not-registered`, `invalid-registration-token` —
  `fcm.sender.ts`). Выход из аккаунта не должен ждать сети.

## Что сделать

1. **Различить исходы** вместо одного глухого `catch`: терминальный отказ
   разрешения, транзиентная сеть/5xx, постоянный 4xx.
2. **Ретраить транзиентное** капнутым бэкоффом, пока пользователь залогинен и
   регистрация не удалась. Останавливаться на успехе, снимать таймеры при
   выходе и при размонтировании (в хуке уже есть `disposed` и отписки —
   продолжить в том же стиле).
3. **Переармить при возврате в форграунд** через `AppState`: если приложение
   провисело свёрнутым и сеть за это время вернулась, следующая попытка не
   должна ждать конца бэкоффа.
4. **`onTokenRefresh` пустить тем же путём**, а не отдельной веткой с
   `.catch(() => {})`. Ротация — тот же случай, только важнее.
5. **Оставить след для 4xx.** Что считать следом — решить в спеке: в проекте
   нет крашлитикса, и заводить его этой задачей не надо. Минимум — чтобы отказ
   был отличим от «всё хорошо» хоть где-то, а не растворялся.
6. **Поправить обещание в шапке хука** — после правки оно должно описывать то,
   что код действительно делает (`AURAT-0050` показал, чего стоит комментарий,
   верный только в одном режиме).
7. **Чистые юнит-тесты** на разбор исходов и на то, что успех останавливает
   ретраи: разрешение отклонено → попыток нет; 500 → повтор; 400 → повтора нет;
   успех со второй попытки → `registerDevice` вызван дважды и больше не
   вызывается. Без сети и без живого Firebase — это слейв.

## Чего НЕ делать

- Не заводить `NetInfo` без отдельного решения.
- Не ретраить отказ в разрешении — человек сказал «нет».
- Не логировать сам токен и не класть тела ответов в ошибки.
- Не блокировать вход и не показывать модалку: регистрация фоновая, её провал
  не повод останавливать человека на входе.
- Не переносить регистрацию в экран — она живёт на уровне сессии.
- Не трогать `unregisterCurrentDevice` и не трогать BFF.

## Проверка (манор app, после мержа)

- Холодный старт в офлайне: регистрация не удалась, приложение работает молча;
  сеть вернулась, приложение свёрнуто-развёрнуто → устройство
  зарегистрировано, пуш от советника доходит.
- Отказ в разрешении: попыток нет, батарея и сеть не тратятся.
- Ротация токена при недоступном BFF: после восстановления новый токен
  доезжает.
