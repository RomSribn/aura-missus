## 1. Что строим

Периодический проход по **Voided Purchases API**: раз в 15 минут спрашиваем у
Google, какие покупки нашего приложения он аннулировал, и на каждую, которую мы
когда-то зачислили, пишем **компенсирующую отрицательную запись** в журнал —
ровно на ту сумму, которая была начислена.

Ничего больше: исходная запись не трогается (триггер и не даст), доставленные
сессии не отбираются, баланс уходит в минус, если кредиты уже потрачены.

### Почему проход, а не Pub/Sub — и почему шагов владельца почти нет

Заглушка ставит RTDN первым источником, а проход — «за тем, что потерялось».
Проверка показала обратное (`004-context`):

- Voided Purchases API ходит тем же OAuth-scope
  `https://www.googleapis.com/auth/androidpublisher`, которым **уже ходит**
  `GooglePlayVerifier`;
- требует право *View financial data*, **уже выданное** сервисному аккаунту
  `play-billing-api@aura-2781b` на `cc.silvermind.aura` (`AURAS-0002` шаг 7,
  сделано 2026-08-19);
- `androidpublisher.googleapis.com` на `aura-2781b` включён с 2026-08-18.

То есть **учётные данные, права и включённый API на месте с августа**. Тема
Pub/Sub не нужна ни для работы, ни для проверки.

RTDN сверх этого даёт только скорость — секунды вместо ≤15 минут — и стоит
темы, прав на публикацию и либо новой зависимости `@google-cloud/pubsub` (pull),
либо публичного маршрута с проверкой подписанного OIDC-токена Google (push).
Публичный маршрут, который списывает деньги, при недоделанной проверке подписи —
это способ обнулить чужой кошелёк. При нынешнем объёме (две настоящие покупки)
покупать секунды такой ценой нечем.

**Рекомендация: только проход.** RTDN остаётся отдельной задачей и включается,
когда 15 минут станут дороги. Вопрос вынесен владельцу — §7.

## 2. Как это работает

### 2.1 Проход (без состояния)

Каждые 15 минут задача BullMQ:

1. Спрашивает `GET …/applications/{package}/purchases/voidedpurchases`
   с `startTime = now − 30 дней`, `type=0` (только разовые товары), идя по
   `tokenPagination` до конца.
2. Для каждого аннулированного `purchaseToken`:
   - **нет строки в `play_purchases`** → ничего. Покупка, которую мы никогда не
     зачисляли (отказ по состоянию, по чужому аккаунту, по неразобранному
     ответу), не должна порождать списание — иначе мы забираем деньги у того,
     кто их не получал;
   - **`refundEntryId` уже заполнен** → ничего, уже развёрнута;
   - иначе — списание (§2.2).

**Почему без курсора.** Каждый проход пересматривает всё 30-дневное окно
заново. Повтор бесплатен: идемпотентность (§2.3) делает повторную обработку
пустой операцией, а предварительная проверка `refundEntryId` не доводит дело
даже до ограничения в базе. Взамен нет ни таблицы курсора, ни миграции под
неё, и сервис, простоявший неделю, догоняет сам. Цена — один-два запроса на
проход, порядка сотни в сутки при квоте ~200k (`AURAS-0002` шаг 7).

Граница честная: окно API — 30 дней, `startTime` старше не принимается. Простой
дольше месяца означает пропущенный возврат. Это записывается в `TECH-DEBT`, а
не прячется.

### 2.2 Списание

Та же форма, что у зачисления (`AURAD-0004`), в одной транзакции:

```
$transaction:
  SELECT "balanceMinor" FROM "wallets" WHERE "id" = :walletId FOR UPDATE
  → перечитать play_purchases под замком (гонка с параллельным проходом)
  → ledgerEntry.create({ type: 'STORE_REFUND',
                         amountMinor: -creditedMinor,
                         balanceAfterMinor: balance - creditedMinor,
                         idempotencyKey })
  → play_purchases.refundEntryId = entry.id
  → wallets.balanceMinor = balance - creditedMinor
```

Сумма — из **сохранённой строки** `play_purchases.creditedMinor`, не из ответа
Google. Google возвращает деньги в своей валюте по своим правилам; наш журнал
разворачивает ровно то, что начислил, иначе `balance = Σ ledger` перестаёт
сходиться.

### 2.3 Идемпотентность

Ключ — `store-refund:<sha256(purchaseToken)>`, под уникальным
`(walletId, idempotencyKey)`. Форма повторяет `play:<sha256(token)>` у
зачисления.

**Ключ выбран не произвольно:** он **дословно совпадает** с ручной процедурой в
`AURAT-0030-002`. Если владелец уже применял возврат руками по той инструкции,
проход на него наткнётся и не спишет второй раз. Это единственная причина не
придумывать ключ покрасивее.

Три уровня, потому что каждый ловит своё: проверка `refundEntryId` (дёшево),
перечитывание под замком (гонка двух проходов), уникальное ограничение
(последнее слово базы). Нарушение уникальности ловится и считается «уже
развёрнуто», а не ошибкой.

### 2.4 Отрицательный баланс

Разрешён и не зажимается — `AURAD-0010`. Проверено в коде, что это уже так
работает и без нас: бронь отказывает по `balanceMinor < costMinor`
(`prisma-sessions.repository.ts:229`, `:380` → `InsufficientFundsError` → 402),
и зажима в ноль нет нигде на этом пути. Отрицательный баланс просто не даёт
покупать дальше.

## 3. Изменения в коде

### 3.1 Миграция `20260918120000_play_refunds`

```sql
-- 1. Имя для того, что сделал магазин. SESSION_REFUND — отменённая бронь,
--    внутреннее движение, и путать их нельзя: триггер запрещает UPDATE, так
--    что тип записи фиксируется навсегда в момент вставки (AURAT-0030-002).
ALTER TYPE "LedgerEntryType" ADD VALUE IF NOT EXISTS 'STORE_REFUND';

-- 2. Связь возврата с покупкой. Отдельный столбец, потому что ledgerEntryId
--    unique и 1:1 с зачислением — переиспользовать его нельзя.
ALTER TABLE "play_purchases" ADD COLUMN "refundEntryId" TEXT;
CREATE UNIQUE INDEX "play_purchases_refundEntryId_key"
    ON "play_purchases" ("refundEntryId");
ALTER TABLE "play_purchases"
    ADD CONSTRAINT "play_purchases_refundEntryId_fkey"
    FOREIGN KEY ("refundEntryId") REFERENCES "ledger_entries" ("id")
    ON DELETE RESTRICT ON UPDATE CASCADE;
```

**Безопасность для существующих записей на проде.** Обе операции
недеструктивны: добавление значения в enum ничего не переписывает, добавление
nullable-столбца даёт существующим строкам `NULL`, а уникальный индекс по
nullable-столбцу в Postgres допускает сколько угодно `NULL`. Покупки от
2026-09-17 не трогаются ничем. Одним файлом — можно: Postgres 16 запрещает
*использовать* новое значение enum в той же транзакции, а эта миграция его не
использует (прецедент и причина разделения — в
`20260814120000_scheduled_sessions_enums`).

`schema.prisma`: новое значение enum, `refundEntryId String? @unique` и
**именование существующей связи** (`@relation("PlayPurchaseCredit")`), потому
что теперь у `LedgerEntry` две связи с `PlayPurchase`. Имена связей — сторона
Prisma, на базу не влияют.

## 5. Чего в задаче нет

- **Возврат денег обратно в Google** из сервиса — открытый вопрос `AURAF-0009`,
  не трогаем.
- **Отбирание доставленных сессий** — прямо запрещено `AURAD-0010`.
- **Зажим баланса в ноль** — там же.
- **iOS / StoreKit** — `AURAF-0010-008`, отдельный рельс.
- **Показ возврата в приложении.** Проверено: эндпоинта истории кошелька в
  сервисе нет вообще — `GET /v1/wallet` отдаёт только
  `{ balanceMinor, currency, purchaseAccountId }`. Возврат виден как падение
  баланса и как отказ брони, и это всё. Полноценная история — новая поверхность
  в контрактах и экран в приложении, то есть отдельная задача с ID из
  `aura-app-manor`. Здесь — записать в `TECH-DEBT`.
- **RTDN / Pub/Sub** — см. §7 вопрос 1.

## 6. Как проверяется

**Слейв:** `npm run lint`, `typecheck`, `build`, `test`.

**Манор, после мёржа (с одобрения владельца):**

1. Миграция применяется на базе `development` — существующие `play_purchases`
   целы, `refundEntryId` у них `NULL`.
2. Сервис поднимается, планировщик зарегистрирован (в логе — проход со
   счётчиками, ноль списаний).
3. Владелец делает **тестовый возврат** в Play Console (§8).
4. В течение 15 минут: в `ledger_entries` появляется `STORE_REFUND` на
   `-creditedMinor`, `play_purchases.refundEntryId` заполнен, баланс уменьшен.
5. Сходимость — тем же запросом, что в restore drill `AURAS-0004`:

   ```sql
   SELECT w."id", w."balanceMinor", SUM(l."amountMinor") AS ledger
     FROM "wallets" w JOIN "ledger_entries" l ON l."walletId" = w."id"
    WHERE w."id" = :walletId GROUP BY w."id", w."balanceMinor";
   ```

6. Второй проход по той же покупке не меняет ничего.

**Прод:** релиз `develop` → `main` — только с одобрением владельца.

## 7. Вопросы владельцу

### Вопрос 1 — источник. Только проход или ещё и RTDN?

| | Что это значит |
|---|---|
| **A. Только проход** (рекомендация) | Задержка ≤15 минут. Шагов владельца по инфраструктуре — ноль, всё уже выдано в августе. Новых зависимостей нет, публичных маршрутов нет |
| B. Проход + RTDN (pull) | Задержка секунды. Нужны: тема Pub/Sub, права на публикацию сервисному аккаунту, зависимость `@google-cloud/pubsub`. Это ощутимо больше кода и ещё одна инфраструктура под присмотром |
| C. Проход + RTDN (push) | Задержка секунды, без новой зависимости, но появляется **публичный маршрут, который списывает деньги**. Требует безупречной проверки подписанного OIDC-токена Google. Не рекомендуется |

### Вопрос 2 — отрицательный баланс. Подтвердить `AURAD-0010`?

Владелец просил вынести это вариантами. Честный ответ: **это уже решено
ратифицированно** 2026-08-17 — баланс уходит в минус и остаётся там до
следующего пополнения, никогда не зажимается.

| | Что это значит |
|---|---|
| **A. Подтвердить** (рекомендация) | Как в `AURAD-0010`. `balance = Σ ledger` держится, бронь отказывает сама, доставленные сессии не отбираются |
| B. Обнулять в ноль | Ломает `balance = Σ ledger` — инвариант, который `AURAT-0010` проверял на устройстве, — и дарит человеку разницу. Требует нового `AURAD` (ID из `aura-app-manor`) |

### Вопрос 3 — первый проход смотрит на 30 дней назад

Первый же запуск применит **все** возвраты, которые Google зарегистрировал за
последний месяц, задним числом. На проде есть покупки от 2026-09-17.

| | Что это значит |
|---|---|
| **A. Применить как есть** (рекомендация) | Если какая-то покупка уже возвращена, кредиты за неё справедливо списываются. Ничего не теряется |
| B. Ограничить порогом даты деплоя | Возврат, случившийся до выкатки, останется незамеченным навсегда — его придётся делать руками по `AURAT-0030-002`. Нужен, только если среди сентябрьских покупок есть возврат, который списывать не надо |

## 8. Шаги владельца

Без первого задача **не проверяется**.

1. **Тестовый возврат в Play Console** — обязателен. Отменить покупку
   лицензионного тестировщика (или одну из собственных от 2026-09-17) на
   `cc.silvermind.aura`. Это единственный способ увидеть настоящее
   аннулирование: подделать его нечем.
2. **Проверить, нет ли уже возвращённых покупок за последние 30 дней** — если
   есть и списывать их не надо, ответить `B` на вопрос 3.
3. **Только если выбран вариант B или C в вопросе 1:** создать тему Pub/Sub в
   `aura-2781b`, указать её в Play Console как адрес Real-time developer
   notifications, дать сервисному аккаунту `play-billing-api@aura-2781b` права
   публикации (`AURAS-0002` шаг 8).
4. **Мёрж в `develop` и релиз в `main`** — отдельное одобрение в момент.

Права на чтение аннулированных покупок (*View financial data*) и включённый
`androidpublisher.googleapis.com` **уже есть** — заводить ничего не нужно.
