# AURAT-0077-016 — Разворот проверен на живом возврате Google

Дата: 2026-09-18, 19:06 CEST
Окружение: `bff-dev`, `develop` @ `fedbbac`

## Что сделали

Возврат заказа `GPA.3343-8577-4981-61365` (`aura.topup.usd25`, 2500) в Play
Console **с галочкой «Remove entitlement»** — так Google называет revoke, и
отсутствие этого знания стоило нам двух неудачных заходов (см. `015`).

## Лог `bff-dev`

```
PlayRefundService   (warn) Google voided play purchase cmtitf0mo006c01my2zilk6fl:
                    reversed 2500 minor units, balance now -300
PlayRefundProcessor (info) play refund notification handled   outcome=debited
```

Ни токена покупки, ни `orderId` — только внутренний id строки. Как и задумано.

## База

```
orderId           | GPA.3343-8577-4981-61365
refundEntryId     | cmu77nlmz000001ru0qidrnh2
type              | STORE_REFUND
amountMinor       | -2500
balanceAfterMinor | -300
idempotencyKey    | store-refund:d94e256e1c73a5339d51849a948e6ab2ec876bda420b46a6cb065b569ad89a81
balance_now       | -300
ledger_sum        | -300
```

Всё до единого поля совпало с предсказанием, сделанным **до** возврата
(`014`, «состояние до»: баланс 2200, ожидание −300).

### Что этим доказано

| | |
|---|---|
| RTDN дошёл, прошёл проверку OIDC, распознан как возврат | да |
| Компенсирующая запись создана с правильным типом | `STORE_REFUND` |
| Сумма взята из строки покупки, не от Google | −2500 |
| Связь покупки с разворотом проставлена | `refundEntryId` |
| **Баланс ушёл в минус и не зажат** (`AURAD-0010`) | −300 |
| **`balance = Σ ledger` держится на отрицательном балансе** | −300 = −300 |
| Ключ той же формы, что у ручной процедуры `AURAT-0030-002` | да |
| Токен и `orderId` не попали в логи | да |

Последние две строки таблицы — то, ради чего задача существовала, и теперь они
проверены живыми деньгами, а не рассуждением.

## Попутно подтверждено опытом

**RTDN тоже молчит без отзыва.** Возврат без «Remove entitlement» не породил ни
уведомления, ни записи в Voided Purchases API. То есть правило из `015` шире,
чем написано в документации API: без отзыва Google не считает возврат
аннулированием **ни по одному каналу**. Правило в `AURAS-0002` от этого только
крепче.

## Осталось

Проход в 19:23. Заказ теперь отозван, значит попадает в Voided Purchases API, и
проход его найдёт — но тронуть не должен: `refundEntryId` уже заполнен.
Ожидается `{"voided":1,"debited":0,"skipped":1}`.

Эта строка закроет разом: планировщик жив; проход видит отозванные возвраты;
два пути не списывают дважды. Лучшего теста идемпотентности на живых данных
специально не придумать.
