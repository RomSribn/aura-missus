# AURAT-0077-014 — Развёрнуто на dev, путь push проверен живым Google

Дата: 2026-09-18
Окружение: `bff-dev.aura-app.cc`, `develop` @ `c546279` (+ `459a7d6` ещё не
выкачен — он лёг на ветку после `wts-finish`)

## Проверка конфигурации сработала так, как задумана

Первый деплой ушёл **до** переменных, и сервис отказался стартовать — цикл
перезапуска каждые ~63 с, падение до старта Nest:

```
PLAY_RTDN_AUDIENCE: required in production with BILLING_ENABLED=true: /webhooks/play
reverses ledger entries, and without both of these there is nothing to verify
Google against (AURAT-0077, AURAS-0002 step 8)
```

Обе переменные названы, причина объяснена. Это ровно то поведение, ради
которого проверка писалась: публичный маршрут, списывающий деньги, не должен
подниматься без того, чем проверяют звонящего.

Заодно выяснилось без отдельного вопроса: на dev **`BILLING_ENABLED=true`**.

Косметика на будущее: текст говорит «in production», хотя это dev. Формально
верно — рантайм-образ ставит `NODE_ENV=production` во всех развёрнутых
окружениях (отмечено в `env.schema.ts`), и формулировка досталась от проверки
сервисного аккаунта Play. Владельцу предложено поправить обе на «in a deployed
environment» отдельным коммитом; не срочно.

## Путь push доказан настоящим трафиком Google

Владелец нажал «Send test notification». В логе:

```
POST /webhooks/play → 204, 41 мс
user-agent: APIs-Google; (+https://developers.google.com/webmasters/APIs-Google.html)
from: noreply@google.com
x-forwarded-for: 192.178.11.130
```

**204, а не 401** — и это единственное, что нужно знать. На этом маршруте 204
достижим только после того, как `verifyIdToken` принял подпись Google и
audience, а `email` в payload совпал с `PLAY_RTDN_SERVICE_ACCOUNT_EMAIL` при
`email_verified`. Неудача любого из звеньев даёт 401.

Значит проверены разом: тема, право на публикацию у Google, push-подписка,
выпуск OIDC-токена сервисом Pub/Sub от имени `play-billing-api@`, наша проверка
и наш разбор конверта. Строки `play refund notification handled` нет — верно,
она пишется только для настоящего уведомления о возврате.

41 мс включают загрузку публичных сертификатов Google; дальше они кэшируются
внутри `OAuth2Client`.

## Ещё не проверено

- **Часовой проход** — строка `play refund sweep` в логе. С `every` BullMQ
  производит первую задачу сразу, а планировщик регистрируется в
  `onApplicationBootstrap`, то есть до `Nest application successfully started`.
  Ждём подтверждения от владельца.
- **Настоящий разворот** — тестовая покупка на dev и её отмена в Play Console.
  Ожидается `play refund notification handled {"outcome":"debited"}`, запись
  `STORE_REFUND` на минус `creditedMinor`, заполненный `refundEntryId`,
  сходимость `balance = Σ ledger`.

## Передеплой на `fedbbac` и почему прохода не видно сразу

Владелец выкатил `fedbbac` (с логированием). Сервис поднялся, `/webhooks/play`
на месте — а строки `play refund sweep` нет. Это **не поломка**, и вот
арифметика.

В Lua-скрипте `addJobScheduler` (BullMQ 5.80.1,
`getJobSchedulerEveryNextMillis`) видно:

```lua
if not prevMillis then          -- первое создание расписания
    nextMillis = now            -- → задача производится немедленно
else                            -- расписание уже есть
    nextMillis = prevMillis + every
end
```

`upsertJobScheduler` идемпотентен, и расписание `play-refund-sweep` было
создано ещё на `c546279`: планировщик там уже был, отсутствовало только
логирование. Значит:

| Время (CEST) | Что произошло |
|---|---|
| 18:23:12 | деплой `c546279` — расписание создано, первый проход отработал **беззвучно** |
| 18:28:59 | деплой `fedbbac` — расписание существует, `upsertJobScheduler` его не трогает |
| **19:23:12** | следующий проход = `prevMillis + 1 час` — первый видимый |

**Факт, который стоит помнить: передеплой не сбрасывает расписание BullMQ.**
После любой выкатки первого видимого запуска повторяющейся задачи можно ждать
до полного интервала. Для часового прохода это до часа, и это относится и к
проду при релизе.

Ирония: беззвучный проход, ради которого добавлялось логирование, успел
отработать ровно один раз — перед тем, как логирование приехало.

## Что можно делать, не дожидаясь 19:23

Настоящий возврат от прохода не зависит: уведомление идёт по push и
разворачивает покупку за секунды. Тестовая покупка на dev и её отмена в Play
Console проверяются прямо сейчас.

Владелец спросил, могу ли я проверить остаток сам. Проверено по факту, а не

Роль себе выдать технически можно (права на это есть — тема Pub/Sub заводилась
той же учёткой), но выдавать себе доступ к учётке, двигающей деньги, без
просьбы владельца не стали: выигрыш мал, возврат в Play Console — два клика.

### Зато проверено напрямую, на развёрнутом сервисе

```
GET  /health                                → 200
POST /webhooks/play   без Authorization     → 401
POST /webhooks/play   Bearer <мусор>        → 401
POST /webhooks/play   настоящий токен Google → 204   (тестовое уведомление, владелец)
```

Вместе это **полное доказательство калитки**: публичный маршрут, списывающий с
кошелька, отвечает только Google и отказывает всем остальным. Не в юнит-тестах,
а в развёрнутом виде. Для этой задачи это самое важное свойство из всех.

Тело отказа — `{"message":"Unauthorized","statusCode":401}`, без подробностей о
том, что именно не сошлось. Правильно: подсказывать звонящему, чего ему не
хватает, тут незачем.
