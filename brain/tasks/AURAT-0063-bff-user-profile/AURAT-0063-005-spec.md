## Этап B · `aura-bff`

### B1 · Схема и миграция

`prisma/schema.prisma`, `model User` — четыре колонки:

```prisma
displayName    String?
email          String?
birthDate      DateTime? @db.Date
marketingOptIn Boolean   @default(false)
```

`prisma/migrations/20260908120000_user_profile/migration.sql` — четыре
`ALTER TABLE "users" ADD COLUMN`, написанные вручную, как здесь принято (SQL с
комментарием, объясняющим *почему*, — образец `20260821170000_message_idempotency_key`).
Индексов нет: `email` не уникален (не логин — логин по телефону) и ни по одной
из колонок не ищут. `birthDate` — `DATE`, а не `TIMESTAMP`: у дня рождения нет
часового пояса, и `DATE` не даст ему съехать на день.

`npx prisma generate` в слейве работает без БД (`prisma.config.ts` делает
datasource условным).

### B2 · Контракты в сервисе

- `src/contracts/profile.ts` — ре-экспорт из `@aura/contracts` в стиле
  `contracts/wallet.ts`, плюс **серверная надстройка**: `birthDate` не позже
  UTC-завтра (находка 2 в `004-context`). Граница живёт здесь, а не в пакете:

- `src/contracts/index.ts` — строка `export * from './profile'`.
- `src/contracts/openapi.ts` — `profileResponseOpenApi`, `profilePatchRequestOpenApi`.

### B3 · Модуль `profile`

По образцу `modules/wallet`, слои — по build rules 2 и 7:

```
src/modules/profile/
  profile.controller.ts        # тонкий транспорт: @Controller('me'), GET + PATCH
  profile.service.ts           # ensureUser → чтение/запись, нормализация
  profile.repository.ts        # абстракция + доменный ProfileRecord
  prisma-profile.repository.ts # единственное место, где живёт Prisma и Date
  profile.module.ts            # imports: [AuthModule]
```

Своя репозиторная абстракция, а не расширение `UsersRepository`: `auth` отвечает
за личность (`firebaseUid`, телефон из токена), `profile` — за то, что человек о
себе рассказал. `UserRecord` читают `chat` и `chatwoot`, и профильные поля им ни
к чему. Идентичность берётся через `UsersService.ensureUser` — ровно как
`WalletService`, — поэтому первый же `GET /v1/me` у нового пользователя создаёт
строку и возвращает профиль из `null`-ов, чего клиентские ворота и ждут.

Конверсия даты — та же пара функций, что в `prisma-tarot.repository.ts`
(`localDate DateTime @db.Date` уже решает эту задачу): в базу `YYYY-MM-DD` уходит
как UTC-полночь, обратно `toISOString().slice(0, 10)`. Выше репозитория дата —
всегда строка `YYYY-MM-DD`, и ни один слой не держит `Date`, который можно
прочитать не в той зоне.

`ProfileModule` добавляется в `app.module.ts`. Гарда своего нет: профиль — v1-free
поверхность, `BillingEnabledGuard` здесь не при чём; аутентификацию даёт
глобальный `FirebaseAuthGuard`.

### B4 · Правила валидации (сервер не верит клиенту)

| Поле | Принимается | Отклоняется |
|---|---|---|
| `displayName` | строка, после trim 2…64 | `''`, пробелы, `null`, >64 |
| `email` | адрес формы `Email`, ≤254, сохраняется в нижнем регистре; **`null` и `''` — оба «стереть»** | всё, что не проходит форму |
| `birthDate` | `YYYY-MM-DD`, существующая дата, ≥1900, не позже UTC-завтра; `null` — «стереть» | будущее, `1899-12-31`, `2026-02-31`, `1994-05-21T00:00:00Z` |
| `marketingOptIn` | `boolean` | всё прочее |
| `phoneE164` | — | **всегда 400** с явным текстом: приходит из проверенного токена, здесь не пишется |

Тело `{ birthDate }` из влитого гороскопа проходит по этим правилам без изменений —
это отдельный тест, а не наблюдение.

`.strict()` на схеме патча: любой незнакомый ключ — 400. Это то, что делает отказ
по `phoneE164` явным, а не молчаливым; для самого `phoneE164` текст ошибки
отдельный, чтобы в 400 было написано «read-only», а не «unrecognized key».

Пустое тело `{}` — 200 с текущим профилем: «ничего не менять» не ошибка. Клиент
такого не шлёт (кнопка мертва, пока ничего не изменилось).

`PATCH` отвечает **полным профилем**, не `204`: новый клиент его парсит, старый
намеренно игнорирует.

## Порядок и гейты

1. Пишу **этап A** (код контрактов, без коммита). Показываю diff.
2. **Гейт 1** — разрешение владельца: коммит + тег `v0.16.0` + пуш в
   `origin main`. Без пуша `npm install` в BFF не разрешит зависимость.
3. Пишу **этап B** целиком, `npm install`, `npm run lint`, `typecheck`, `test`.
   Показываю diff.
4. **Гейт 2** — разрешение владельца: коммит в `feature/AURAT-0063-user-profile`
   и `wts-finish slave-2` (мёрж в `develop` + пуш).
5. Проверка в маноре на живом стеке (миграция, оба маршрута, старое тело
   `{ birthDate }`).
6. Только после этого мёржится `AURAT-0062`.

*Если владелец не хочет пушить тег до просмотра всей работы*, есть запасной
порядок: контракты ставятся в BFF временно из локального клона
(`git+file://…#v0.16.0`), всё пишется и проверяется, и оба пуша идут одним
гейтом — ценой того, что `package.json`/`package-lock.json` придётся вернуть к
`github:`-ссылке перед коммитом.
