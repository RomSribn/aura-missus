# AURAT-0063-001 — Профиль пользователя на сервере

Дата: 2026-09-08
Статус: **заведена, не начата** — ждёт одобрения `AURAF-0015`
Репозиторий: **aura-bff** (исполняется в `aura-bff-manor`)
Фича: `AURAF-0015` · клиент: `AURAT-0062` (делать **после** этой)
ID выдан в `aura-app-manor` — он канонический источник номеров (`AURAD-0006`)

## Зачем

Приложение начинает спрашивать имя, емейл, дату рождения и согласие на
рассылку (`AURAF-0015`). Хранить их сегодня негде: в `prisma/schema.prisma` у
`User` есть только `firebaseUid`, `phoneE164` и чатвутовские идентификаторы, а
контроллера `me` нет вовсе — `grep` по `src/` даёт ноль. При этом приложение
**уже** ходит в `PATCH /v1/me { birthDate }` (`entities/horoscope/api`), и этот
запрос сейчас получает 404: шов спроектирован в `AURAT-0039`, серверная
половина не начата.

Эта задача строит недостающую половину.

## Что сделать

### 1. Схема

Четыре колонки в `User`, все необязательные:

| Колонка | Тип | Зачем |
|---|---|---|
| `displayName` | `String?` | имя, которым советник обращается к человеку |
| `email` | `String?` | необязательный контакт; **не уникальный** — это не логин, логин по телефону |
| `birthDate` | `DateTime? @db.Date` | дата, а не момент: часовой пояс к дню рождения отношения не имеет, и `Date` не даст ему съехать на день |
| `marketingOptIn` | `Boolean @default(false)` | согласие на рассылку |

Миграция по здешнему именованию: `20260908xxxxxx_user_profile`.

Про `marketingOptIn`: значение по умолчанию в базе — `false`, независимо от
того, что решит владелец про положение тумблера на экране (`AURAT-0062`, D3).
Строка, появившаяся до того, как человека спросили, согласия не выражает.

### 2. Маршруты

Новый модуль `src/modules/profile/` (`ProfileController` + `ProfileService`),
по образцу `modules/wallet`:

- **`GET /v1/me`** → `{ displayName, email, birthDate, phoneE164, marketingOptIn }`.
  Читателя раньше не было — теперь есть: экран правки профиля показывает
  сохранённое, и ворота на входе решают по `displayName`, есть имя или нет.
  Это снимает довод `AURAT-0039-004`, по которому `GET` не строили (правило 8:
  нет читателя — нет маршрута).
- **`PATCH /v1/me`** — частичное обновление тех же полей. Тело валидируется
  `ZodValidationPipe`, схема — в `src/contracts/profile.ts`.
  **Совместимость: тело `{ birthDate }` обязано продолжать работать** — так
  ходит уже влитый гороскоп.

`phoneE164` только читается: он приходит из проверенного Firebase-токена, и
попытка его записать должна отклоняться, а не игнорироваться молча.

Идентичность — `ensureUser` из `modules/auth` (идемпотентен, гонку решает
уникальный `firebaseUid`, `AURAT-0050`), так что первый же `GET /v1/me` у
нового пользователя создаёт строку, как это делает `GET /v1/wallet`.

### 3. Валидация

Сервер не верит клиенту:

- `displayName` — trim, 2…64 символа после трима, пустая строка отклоняется;
- `email` — формат, ≤254, приводится к нижнему регистру; `null` — законное
  значение, «стереть»;
- `birthDate` — `YYYY-MM-DD`, не в будущем, не раньше 1900 (те же границы, что
  на клиенте в `shared/lib/birth-date.ts`);
- `marketingOptIn` — boolean.

### 4. Контракты

`src/contracts/profile.ts` + строка в `contracts/index.ts` + OpenAPI-схемы в
`contracts/openapi.ts`. Тег `@aura/contracts` — следующий после `v0.15.0`,
то есть **v0.16.0**; приложение подтягивает его в `package.json` в `AURAT-0062`.

### 5. Не в этой задаче

- **Аватар.** Ни колонки, ни загрузки, ни раздачи — отдельная работа размером
  с `AURAT-0031` (см. `AURAF-0015`, «не в объёме»).
- **Гороскоп по знаку.** `GET /v1/horoscope` — это по-прежнему `AURAT-0039`,
  и он остаётся не построенным. Эта задача даёт только `birthDate`, из которого
  знак когда-нибудь выведется. Приложение к отсутствию гороскопа готово: 404
  переводит секцию в терминальное `disabled`.
- **Рассылка.** Куда `marketingOptIn` уезжает дальше (Mailchimp, свой список) —
  вопрос за пределами BFF. Здесь он только хранится.

## Порядок

Эта задача мёржится **первой**. `develop` в `aura-bff` — это боевой деплой
(`AURAS-0004`), поэтому клиент, влитый раньше, будет собирать емейл в никуда.
Та же последовательность, что в `AURAF-0014`: `AURAT-0058` (сервер) →
`AURAT-0059` (клиент).
