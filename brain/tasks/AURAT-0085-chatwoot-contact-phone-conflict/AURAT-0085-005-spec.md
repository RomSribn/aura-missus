# AURAT-0085-005 — Спека: конфликт номера при создании контакта Chatwoot

Дата: 2026-10-12
Статус: done 2026-10-12 — вариант B, смержено в develop @ f130686
Репозиторий: **aura-bff**, ветка `feature/AURAT-0085-chatwoot-contact-phone-conflict`
Закрывает: **TECH-DEBT #34**

## Проблема (из 004)

`ensureChatwootIdentity`: `findContactByIdentifier(uid) ?? createContact({identifier: uid,
phone})`. Новый UID + старый контакт с тем же номером → Chatwoot 422 (номер уникален
Rails-валидацией) → ошибка летит наверх → 500 на `PUT /v1/advisors/:id/conversation` и
422 на отправку. Навсегда: каждый следующий запрос делает ровно то же.

Попутно найдено: параллельные первые запросы одного **нового** пользователя (без
конфликта номера) сегодня тоже роняют проигравшего — второй `POST /contacts` с тем же
identifier получает 422 (валидация) или 500 (`RecordNotUnique` Chatwoot не
перехватывает). Лечится тем же местом.

## Главное решение: что делать с чужим контактом — два варианта

### Вариант B — «освободить номер» (рекомендую)

Стереть `phone_number` у контакта, который держит номер, и создать свой контакт.
Ровно то, что владелец сделал руками на dev 2026-10-12.

- Инвариант «**один Firebase UID = один контакт, identifier = UID**» сохраняется. На нём
  стоит `AURAT-0042`: `deleteContactsOf(uid)` ищет контакт по identifier.
- В нашей БД ничего отвязывать не нужно: старая строка `users` держит **свой** старый
  контакт (теперь без номера), новая — свой новый. Два пользователя один контакт не
  делят по построению.
- Удаление аккаунта (`AURAT-0042`) работает без изменений: удаление новой строки сносит
  только новый контакт; операторское удаление по номеру (`findByPhone` вернёт **обе**
  строки — в `users` номер остаётся) сносит у каждой её собственный контакт.
- Нет слияния аккаунтов. BFF уже сегодня считает новый UID новым человеком (новая
  строка `users`, пустая история в приложении) — Chatwoot становится с этим согласен.
  Решение **O5** (смена номера / слияние) не трогаем и не предрешаем.
- Перепрошитый оператором номер (другой человек получил тот же номер у оператора связи)
  не получает чужую историю даже на стороне чаттера.
- Цена: чаттер видит **два** контакта с одним именем; история со старым контактом не
  «переезжает». Это честно отражает то, что видит приложение.

### Вариант A — «перепривязать контакт» (как в брифе)

Найти контакт по номеру, переписать `identifier` на новый UID, отвязать старую строку
`users` (обнулить `chatwootContactId`/`chatwootSourceId`).

- По сути **слияние** старой личности с новой на стороне desk: старые диалоги контакта
  (`conversations` старой строки) оказываются у нового человека в списке у чаттера, а
  в приложении нового человека их нет. Ответ чаттера в таком старом диалоге уйдёт
  **старой** строке (карта `conversations` по-прежнему её) — молча потеряется.
- Новый диалог с тем же адвайзором создаётся вторым тредом на том же контакте —
  у чаттера два треда «Mia» у одного контакта.
- Нужно дополнительно: метод репозитория «отвязать контакт у других строк», транзакция
  отвязки vs. параллельной привязки, и проверка, что `AURAT-0042` при удалении старой
  строки уже не тронет контакт (держится только на отвязке).
- Это решение уровня **O5** → по build rules нужен `AURAD` (минтится в `aura-app-manor`)
  до кода.

**Рекомендация: B.** Дешевле, не трогает нашу БД, не требует нового `AURAD`, не ломает
`AURAT-0042`, и не может «смешать» двух людей. Если владелец хочет непрерывность
истории у чаттера — это вариант A, но тогда сначала `AURAD` по O5.

## Код (вариант B)

### Адаптер — `chatwoot.client.ts` (только модуль `chatwoot`)

- `findContactByPhone(phoneE164): Promise<ChatwootContact | null>` — тот же
  `POST /contacts/filter`, `attribute_key: 'phone_number'`, `equal_to`. Общий приватный
  `filterContacts(key, value)` вместо копипасты с `findContactByIdentifier`.
- `clearContactPhone(contactId): Promise<void>` — `PUT /contacts/:id {phone_number: null}`
  (`allow_blank`; `custom_attributes` при `PUT` Chatwoot сливает, как уже работает у
  `updateContactName`).

### Сервис — `provisioning.service.ts`

```
contact = findContactByIdentifier(uid) ?? createContactResolvingConflicts(user)

createContactResolvingConflicts:
  try create
  catch ChatwootApiError e:
    1. winner = findContactByIdentifier(uid); если есть → вернуть   // проигранная гонка
    2. если e.status != 422 или номера нет (null / не E.164) → throw e
    3. holder = findContactByPhone(phone)
       если нет, или holder.identifier == uid → throw e             // не наш случай
    4. clearContactPhone(holder.id); warn {contactId: holder.id}     // без номера/UID
    5. ещё ОДИН create; на ошибке — снова findContactByIdentifier(uid), иначе throw
  иные ошибки (таймаут, сеть) → throw как сейчас
```

- **Гонки.** Две параллельные первые попытки: обе могут дойти до шага 4 — стирание
  номера идемпотентно; на шаге 5 одна создаёт, вторая ловит 422/500 и находит
  победителя по identifier (уникальный индекс в БД Chatwoot — дубликата не будет). Обе
  запоминают одинаковую пару в `users`. Та же идиома, что `AURAT-0050`.
- **Ограничение.** Ровно одно освобождение и один повтор — без циклов; если номер
  опять занят (историческая пара дублей — уникальность номера в Chatwoot только
  валидацией), бросаем исходную ошибку как сейчас.
- **Номер null / невалидный.** `validE164` уже не отправляет такой номер → 422 не про
  номер → шаг 2 бросает. Ищем по тому же значению, что отправляли.
- **Тело 422 не читаем** (может содержать PII, build rule 3) — различаем повторными
  поисками.
- Лог: `warn` с id контакта, без номера и UID.

### Что НЕ меняется

- Схема БД, миграции, `UsersRepository`, `AURAT-0042` (код удаления).
- Старая строка `users`, её диалоги и контакт (кроме стёртого номера) — сиротское
  состояние после удаления Firebase мимо BFF было и остаётся; уборка таких строк — не
  эта задача.

## Тесты (чистые)

`provisioning.service.spec.ts`:

1. **Регрессия #34 (падает на старом коде):** `createContact` → 422, затем успех;
   `findContactByPhone` → `{id: 6, identifier: 'old-uid'}` → `clearContactPhone(6)`,
   второй `createContact`, в `users` запомнен **новый** контакт, разговор создан.
2. Гонка: `createContact` → 422 (и отдельно 500), повторный `findContactByIdentifier`
   отдаёт победителя → используем его, номер не ищем и не стираем.
3. Номер `null` и номер не E.164 → 422 пробрасывается, `findContactByPhone` не вызван.
4. По номеру никто не найден → исходная ошибка.
5. Держатель номера — контакт с нашим же UID → не стираем, исходная ошибка.
6. Повтор после освобождения снова 422, победителя нет → ошибка; `clearContactPhone`
   вызван ровно один раз.
7. Не-`ChatwootApiError` (сеть) → пробрасывается без поисков.

`chatwoot.client.spec.ts`: тело фильтра по номеру; `PUT` с `phone_number: null`.
