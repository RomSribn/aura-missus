# AURAT-0042-008 — Спека половины BFF: удаление аккаунта

Дата: 2026-09-16
Пишет: `aura-bff-manor` / `slave-3`
Статус: **draft — решения Q1–Q4 приняты владельцем 2026-09-16 (`009`), ждёт утверждения**
Опирается на: `001` (скоуп), `002` (ограничения), `003` (надгробие), `007` (код)

## Что получит приложение

```
DELETE /v1/me            Firebase-authed, НЕ за billing_enabled

204  аккаунт удалён — и на повторный вызов тем же токеном тоже 204
409  { code: 'account_has_live_sessions' }   ← есть SCHEDULED или ACTIVE (Q1)
401  { code: 'account_deleted' }             ← любой ДРУГОЙ маршрут и WS (4401)
                                               тем же uid после удаления
```

После 204 приложение **не** вызывает `DELETE /v1/devices/:token`: токены уже
удалены на сервере, и вызов получит 401. Приложению остаётся только локальный
выход. Коды и описание уходят в `@aura/contracts` **v0.19.0** (`account.ts`)
и в OpenAPI.

## Как устроено

### 1. Запрос: одна транзакция в базе и запись о внешних шагах

`AccountDeletionService.deleteAccount(auth)`:

1. Строка по `firebaseUid` ищется **без** `ensureUser`: строку, которую
   собираются удалить, заводить незачем.
   - Строки нет, а отметка стирания (п. 2) есть → это повтор, **204**.
   - Нет ни строки, ни отметки → человек ни разу не дошёл до API. Личность в
     Firebase удаляется сразу, ставится отметка, **204**.
2. **Отметка стирания** ставится в Redis **до** транзакции, чтобы закрыть
   находку 1 из `007`: `erased-identity:<sha256(uid)>`, TTL 24 ч. Сам uid в
   Redis не лежит.
3. Одна транзакция в одном репозитории (`PrismaAccountErasureRepository`,
   правило из `007` §5):
   1. `SELECT … FROM users WHERE id = $1 FOR UPDATE` и `FOR UPDATE` на кошелёк,
      если он есть. Бронирование берёт тот же замок кошелька, поэтому
      параллельная бронь либо уже видна, либо ждёт и потом падает на FK.
      Дальше `firebaseUid` перечитывается: если он уже надгробие, значит,
      победил параллельный вызов, и ответ **204**.
   2. Есть сессия SCHEDULED или ACTIVE → **отказ** (Q1): транзакция
      откатывается, отметка снимается, ответ **409**.
   3. `device_tokens` пользователя удаляются.
   4. `messages` его переписок удаляются, каскадом уходят
      `message_attachments` и `tarot_spreads`.
   5. `sessions`: `conversationId → NULL`. Строки остаются, `002` §3.
   6. `conversations` удаляются. RESTRICT от `sessions` здесь работает как
      проверка: если сессию не отвязали, транзакция падает.
   7. `user_daily_cards` удаляются.
   8. `advisor_reviews` **обезличиваются, звёзды остаются** (Q2):
      `authorName = 'Anonymous'`, `quote = ''`, `quoteStatus = PUBLISHED`,
      `userId = NULL`, `sessionId = NULL`. `ratingTenths` и `published` не
      меняются, так что агрегаты `advisors` пересчитывать не нужно.
      `PUBLISHED` выбран потому, что так `nextQuoteStatus` уже обращается с
      отзывом без слов: строка уходит из очереди модерации, а не висит там
      пустой. `anonymous` остаётся как был. Имя `'Anonymous'` без запроса на
      анонимность — уже существующее состояние (человек без имени,
      `review-quote.ts:19-23`), и выдумывать за человека просьбу не
      подписываться нельзя.
   9. **Надгробие** (`003`): `firebaseUid = 'deleted:<cuid>'`. `phoneE164`,
      `displayName`, `email`, `birthDate`, три колонки аватара,
      `chatwootContactId` и `chatwootSourceId` становятся `NULL`,
      `marketingOptIn = false`. `id` не меняется.
   10. Строка **`account_erasures`** хранит то, что понадобится вне базы и
       иначе было бы уже стёрто: `userId`, `firebaseUid`,
       `chatwootContactId`, `requestedAt`.
   11. `wallets`, `ledger_entries`, `play_purchases` **не трогаются**:
       триггер не срабатывает, потому что в реестр ничего не пишется.
4. После коммита сервис ставит джобу `account-erasure` (`jobId` по id
   записи), закрывает WS-сокеты пользователя кодом 4401, пишет лог
   `{ userId } 'account erased'` и отвечает **204**.

### 2. Джоба: внешние удаления, каждое повторяемо

Процессор тонкий, логика в `AccountDeletionService.completeErasure(id)`:

1. **Firebase:** `deleteUser(uid)`. `auth/user-not-found` считается успехом.
   После успеха TTL отметки сокращается до **1 ч**: это верхняя граница жизни
   токена, выпущенного до удаления, а новых после удаления не будет.
2. **Chatwoot** (Q3): `DELETE /contacts/{id}`. 200 с пустым телом и
   404 считаются успехом, 422 «online» и 5xx идут на повтор.
3. **R2:** удаляется весь префикс `avatar/<userId>/`, а не один ключ, потому
   что сбой стирания при замене аватара проглатывался и сироты возможны
   (`007`). Если хранилище в деплое не настроено, шаг пропускается.
4. Запись закрывается: `firebaseUid` и `chatwootContactId` → `NULL`,
   `completedAt = now`. Строка остаётся как след «удалено тогда-то» без
   персональных данных.

Повторы — экспоненциальные, попыток много. Страховка на случай потерянной
постановки или исчерпанных попыток — **sweep раз в 10 минут**, по образцу
сверки при вебхуке. Он ставит заново записи без `completedAt` старше
5 минут и продлевает их отметки. Так отметка не истечёт, пока личность в
Firebase ещё жива, и не повиснет навсегда, если процесс упал между
отметкой и транзакцией.

### 3. Закрытие окна старого токена (`007`, находка 1)

- `FirebaseAuthGuard`: после `verifyIdToken` проверяется отметка. Если она
  есть, ответ **401 `account_deleted`**. Исключение — обработчик с
  `@AllowErasedIdentity()`, такой ровно один: `DELETE /v1/me`, ради
  идемпотентного повтора.
- `ChatGateway`: та же проверка в рукопожатии, закрытие 4401.
- Стоимость — один `EXISTS` в уже открытое соединение Redis на запрос.
- **Redis недоступен → fail-open с предупреждением в лог.** Иначе падение
  Redis превращается в 503 на всех маршрутах. Цена — окно не закрыто на время
  аварии, и то лишь для аккаунта, удалённого в последний час.

### 5. Миграция `20260916120000_account_deletion` — только expand

1. `ALTER TABLE "sessions" ALTER COLUMN "conversationId" DROP NOT NULL`.
   FK остаётся RESTRICT.
2. `CREATE TABLE "account_erasures"`: `userId` уникален, FK RESTRICT на
   `users`; частичный индекс по `completedAt IS NULL` для sweep.

Оба шага безопасны для `prisma migrate deploy` на старте контейнера. Старый
код колонку не читает и `NULL` не пишет, так что откат образа без отката
схемы работает. Фазы contract нет.

## Решения владельца (2026-09-16, `009`)

| | Решение | Что это значит в коде |
|---|---|---|
| **Q1** Живые сессии | **Отказ 409**, пока есть SCHEDULED или ACTIVE | Деньги при удалении не двигаются незаметно. Предстоящую сессию человек отменяет существующим путём и видит возврат по правилу 24 ч, активная заканчивается сама |
| **Q2** Отзывы | **Звёзды остаются, обезличенными** | §1 п. 3.8: имя `'Anonymous'`, текст стёрт, `userId`/`sessionId` → `NULL`. Счётчик и рейтинг на профиле советника не меняются |
| **Q3** Копия у стойки | **Контакт удаляется через API** | §2 п. 2. Остаются строки enterprise-`audits` с атрибутами переписок (без текстов) и анонимные rollup'ы. Это оговорка в политике |
| **Q4** Остаток кошелька | **Сгорает, проводки нет** | Кошелёк надгробия не трогается. Сумму до удаления показывает экран подтверждения в приложении |

## Принятые по умолчанию (владелец может переиграть при утверждении)

- **D1. Удаление отдельной переписки не строится.** Строка privacy §07 «or
  earlier if you delete a conversation» уходит по карте `AURAT-0040-013`,
  это половина `aura-app-manor`.
- **D2. Личность в Firebase удаляет BFF** (рекомендация `001`/`002`), SMS на
  повторный вход не нужна.
- **D3. Кредит первой сессии ($5) заново зарегистрированный номер получит
  снова.** Хэш телефона ради защиты от этого не хранится: политика обещает
  стирание, а цена злоупотребления — новая SIM и SMS на каждые $5.
- **D4. Дампы (30 дней, `AURAS-0004`) удаление не достаёт.** В политике это
  оговорка. В рунбук восстановления добавляется правило: после восстановления
  повторить стирания из лога `account erased` за время после дампа. `id`
  надгробия равен `id` исходной строки, поэтому CLI из D5 найдёт её.
- **D5. CLI для оператора:** `account:erase -- --user <id> | --phone <E164>`,
  та же процедура и те же отказы, по образцу `reviews:*`. Это закрывает
  письмо на `info@` и **веб-путь для Play** («попросите удалить»), которому
  тогда не нужен свой сервер, а также повтор после восстановления из D4.
- **D6.** Отметка в Redis работает fail-open (§3).
