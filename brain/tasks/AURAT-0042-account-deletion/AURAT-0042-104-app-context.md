Дата: 2026-09-16
Пишет: `aura-app-manor` / `slave-0`
Сверено: `aura-app` `develop` @ `506a318`; `aura-bff` `slave-3` @ `1a1003c`

## 1 · Куда встаёт строка

- terms §04 обещает удаление **«from the profile screen in the app»**, privacy
  §08 — **«from the app's profile screen»**. Значит строка — на
  `screens/profile`, не на Edit Profile и не в отдельных настройках.
- Экран сегодня: карточка профиля → меню (`Terms of Use`, `Privacy Policy`) →
  `Sign out` (коралловый, иконка `logout`) → версия. Строки меню открывают
  внешние страницы (`openMenuRow` → браузер), так что удаление в меню —
  чужеродная строка; его место — под `Sign out`, тише его (`001`, п. 1).
- В хендоффе экрана удаления **нет** (`README`, `PROFILE_FORMS`, `prototype/`,
  `screens/` 01–41, `rn/`).

## 2 · Из чего собирать подтверждение

`screens/session-detail/ui/CancelSessionSheet.tsx` (дизайн 25/27) — готовый
язык деструктивного подтверждения в этом приложении: `BottomSheet`,
заголовок-вопрос, абзац, белая карточка с иконкой и оговоркой, строка ошибки,
две кнопки `ghost` «Keep it» / коралловая с `loading`. Удаление аккаунта
ложится на ту же форму без новых атомов и токенов.

Тост после удаления есть на чём показать: `ToastProvider` стоит **над**
навигатором (`AURAT-0066`), поэтому переживает `leaveApp` и виден на экране
входа.

## 3 · Путь выхода уже есть — почти целиком

`use-profile.ts` `signOut`: `unregisterCurrentDevice()` →
`authService.signOut()` → `profileStore.reset()` + `horoscopeStore.reset()` →
`leaveApp(root)`. Остальные сторы (`wallet`, `advisor`, `daily-card`, отзывы,
расклады, чат, сессии) сбрасываются сами — все слушают `onAuthStateChanged`.

Для удаления два отличия:

- `unregisterCurrentDevice()` **лишний и вредный по порядку**: токены
  устройства удаляет сервер (`006`), а вызов после удаления уйдёт с токеном
  удалённой личности (см. 5).
- **Кеш вложений на устройстве** (`shared/api/bff/attachment-cache.ts`,
  `CacheDir/aura-attachments`) не чистится ни при выходе, ни где-либо ещё.
  Фотографии, голосовые и файлы из переписки удалённого аккаунта остались бы
  на телефоне. Обещание privacy «erase the data» телефон не покрывает
  юридически, но оставлять это молча — не то же, что решить.

## 4 · Клиент BFF и коды отказа

`bffRequest` (`shared/api/bff/http-client.ts`) бросает `BffApiError(status)`
**без `code`** — код отказа разбирает только `upload.ts` (`AURAT-0032`,
`profile-photo/lib/refusal-copy.ts`). Если маршрут удаления будет отказывать
с кодом (например, «идёт оплаченная сессия»), `bffRequest` придётся научить
читать `code` — это правка `shared`, а не слайса.

`401` ретраится один раз с принудительным обновлением токена; если обновить
нельзя — `BffApiError(401)`.

## 5 · Находка на стыке половин: токен удалённой личности всё ещё проходит

`aura-bff` `common/guards/firebase-auth.guard.ts:50` →
`FirebaseAdminService.verifyIdToken(idToken)` — **без `checkRevoked`**.

Удаление личности через Admin SDK не отзывает уже выданные ID-токены: они
живут до часа. Без `checkRevoked` гард их принимает, а за гардом почти каждый
модуль зовёт `ensureUser` → `upsertByFirebaseUid(uid)`. Старая строка уже
носит надгробие (`003`), `upsert` её не найдёт и **заведёт новую строку со
старым uid и номером телефона из токена.**

Кто пошлёт такой запрос — не гипотеза: чат держит сокет и дозапрашивает дельты
на переподключении, сторы синкаются, пуш перерегистрируется на
`onTokenRefresh`. Всё, что вылетело между ответом маршрута и `signOut`, —
кандидат.

Приложение окно **сужает** (гасить сессию сразу, не звать
`unregisterCurrentDevice`), но **закрыть не может**: уже отправленный запрос не
отзовёшь. Закрывается на сервере — `checkRevoked: true` в гарде (цена — сетевой
вызов на каждый запрос, либо кеш), или проверка в `ensureUser`, или процедура,
не дающая воскресить uid. **Это половина BFF.**

*Дописано после чтения `007-context` половины BFF (появился в `slave-3`, пока
писался этот шаг):* там та же находка, найдена независимо и шире — ещё
рукопожатие `ChatGateway` (`chat.gateway.ts:44`) и `DELETE
/v1/devices/:token` из `unregisterCurrentDevice` с `ensureUser` на входе.
Передавать не нужно, она уже в их спеке.

## 5а · Что из `007` половины BFF ложится на приложение

| Находка BFF | Следствие для приложения |
|---|---|
| §2 — к удалению не должно быть живых сессий (решение владельца, их Q1) | Вероятен **отказ с кодом**; подтверждение должно его объяснить, а не показать «try again» |
| §4 и таблица — остаток кошелька становится недостижим (их Q4) | Если остаток > 0, подтверждение **называет сумму**, которая сгорит |
| Таблица — отзывы удалённого (их Q2) | Строка в «что остаётся» зависит от ответа |
| §6 — внешние шаги (Firebase, Chatwoot, R2) делает повторяемая джоба | Успех маршрута = коммит базы; приложение не ждёт внешних шагов |
| Таблица — `ChatGateway` не умеет закрыть сокеты пользователя | Сокет гасит **само приложение**: `signOut` сразу после успеха (чат слушает смену личности) |
| Таблица — коды ошибок в `ApiError { code, message }`, контракты `v0.19.0` | `bffRequest` должен научиться читать `code` (п. 4) |

## 6 · Target и окружения

Сборка для internal testing — `staging` (`env/.env.staging` → `bff-dev`),
`AURAT-0068`. Мёрж BFF в `develop` деплоит в `development` (`AURAS-0004`).

приложении зовёт маршрут, которого нет, и получает `404`.
