## Проблема (из 004)

`book()` проверяет запрос (блок → слот/lead/горизонт → советник), потом создаёт диалог в
Chatwoot и кошелёк, и только внутри транзакции ищет повтор по ключу. Ответ первой
(прошедшей) брони потерялся → клиент повторяет с тем же ключом → слот уже ближе lead (или
сменили `SESSION_BLOCK_MINUTES`, или у советника пропала цена) → 400/404 → оба клиента
считают это окончательным, сбрасывают ключ → человек выбирает другое время и платит второй
раз. У `extend()` то же самое с `requireAllowedBlock`.

## Решение

### 1. `book()` — сначала повтор

Новый порядок в `SessionsService.book()`:

1. `users.ensureUser(auth)` — тот же вызов, что и сейчас, только раньше. Строка `users` для
   нового входа создаётся так же, как на любом другом маршруте; Chatwoot и кошелёк не
   трогаются.
2. `sessions.findBookReplay({ userId, advisorId, idempotencyKey })` — нашли → сразу
   `{ session, balanceMinor }`: ничего не планируется, не пушится, не уведомляется (как и у
   сегодняшнего `replayed: true`).
3. Не нашли → всё как сейчас: `requireAllowedBlock` → `requireBookableSlot` →
   `requireAdvisor` → `ensureConversation` → кошелёк → транзакция.

Новый метод репозитория `findBookReplay` — одно чтение вне транзакции:
`session.findFirst({ where: { idempotencyKey, conversation: { userId, advisorId } } })`.
Диалог уникален по `(userId, advisorId)`, так что это ровно тот же ключ
`conversationId_idempotencyKey`, что ищется в транзакции, — без отдельного похода за
диалогом. Баланс — текущий, из строки кошелька пользователя (сессия без кошелька
невозможна: `book()` создаёт его до транзакции; если нет — падаем громко, как `toRecord`).

**Повтор внутри транзакции остаётся** — он закрывает гонку: два одновременных запроса с
одним ключом оба не находят повтор снаружи, второй ждёт замка и находит его внутри.
`convergeBookRace` тоже без изменений.

### 2. `extend()` — сначала повтор

Новый порядок в `SessionsService.extend()`:

1. `requireOwnedSession` — владение остаётся первым (чужая сессия неотличима от
   несуществующей, 404). Следствие: чужая сессия + неверные минуты теперь 404, а не 400.
2. Кошелёк (`getOrCreateByUserId`, как сейчас).
3. `sessions.findExtendReplay({ sessionId, walletId, minutes, idempotencyKey })` — нашли →
   сразу ответ; `IdempotencyKeyReusedError` → 409 через `toHttpError`.
4. Не нашли → `requireAllowedBlock` → `sessions.extend()` как сейчас.

`findExtendReplay` — те же правила, что сейчас в `extendLocked`, вынесенные в один приватный
помощник, которым пользуются оба пути (снаружи — `this.prisma`, внутри — `tx`), чтобы правила
не разошлись:
- ключ брони этой сессии против extend → `IdempotencyKeyReusedError`;
- запись журнала `(walletId, key)` есть: не `SESSION_CHARGE` или сумма ≠
  `minutes × priceMinorPerMinute` сессии → `IdempotencyKeyReusedError`; иначе повтор с
  текущим состоянием сессии и текущим балансом;
- записи нет → `null`.

**Повтор после конца сессии:** уже работает — в репозитории повтор проверяется до состояния
сессии; вынос наружу это сохраняет. Закрепляется тестом.

### 3. Повтор с другим телом — оставить как есть (рекомендую)

Бронь с тем же ключом и другим слотом/блоком (тот же советник) возвращает исходную сессию,
без 409.

- Веб (`AURAT-0107-005` §4) **на это опирается**: после сбоя сети человек может сменить слот,
  ключ не сбрасывается. С 409 было бы: первая бронь прошла → повтор с новым слотом → 409 →
  «окончательно» → ключ сброшен → вторая бронь списывает ещё раз. Тот же дефект другой
  дорогой.
- Ответ всегда честный: клиент получает **ту** сессию, которая реально куплена, и показывает
  её, а не выбор в UI.
- Фиксирую это комментарием в `SessionsRepository.findBookReplay` (поведение — часть
  обещания API). Записать это в `@aura/contracts` — пробел №2 веба, за `aura-app-manor`; здесь
  контракты не трогаю.

Альтернатива — 409 `IdempotencyKeyReused` на несовпадение тела: строже, но ломает веб и
требует, чтобы оба клиента научились отличать этот 409 от «слот занят» (сейчас кодов причин
нет — пробел №3). Не рекомендую.

`extend` с другими минутами под тем же ключом и сейчас отвечает 409 (сумма не совпала) —
не меняю: это прежняя семантика, продление клиенты шлют одним и тем же телом.

### 4. Что не меняется

- Ключ того же пользователя у **другого** советника — не повтор (другой диалог), путь
  прежний: проверки → транзакция → P2002 на журнале → 409.
- `BillingEnabledGuard` на контроллере — повтор его не обходит.
- Повтор отдаёт **текущее** состояние сессии (может быть уже `ACTIVE`/`FINISHED`/
  `CANCELLED`) и текущий баланс — как сегодняшний повтор в транзакции.

## Тесты (чистые, в слоте)

`sessions.service.spec.ts`:
- повтор брони возвращает исходную сессию и баланс, когда слот запроса уже внутри lead; не
  вызываются `advisors.findById`, `ensureConversation`, `getOrCreateByUserId`,
  `sessions.book`; ничего не ставится в очередь и не пушится;
- то же для минут, которых больше нет в `SESSION_BLOCK_MINUTES`, и для советника без цены;
- то же для `startNow` (и `closeSpentSession` не зовётся);
- без повтора — прежний путь (существующие тесты, `findBookReplay` → `null`);
- `extend`: повтор с минутами вне блоков и повтор после конца сессии возвращают исходный
  результат без `sessions.extend`; `IdempotencyKeyReusedError` из повтора → 409; чужая
  сессия — 404 до повтора.

`prisma-sessions.repository.spec.ts` (Prisma на моках):
- `findBookReplay`: запрос по ключу и `conversation: { userId, advisorId }`, баланс из
  кошелька; `null`, когда нет;
- `findExtendReplay`: ключ брони → ошибка; запись с той же суммой → повтор; с другой
  суммой или другого типа → ошибка; нет записи → `null`.

Плюс `lint`, `typecheck`, `build`, весь `jest`.

## Проверка в маноре (после merge)

На живом стеке (Postgres + Redis + dev Chatwoot), пользователь с деньгами:
1. Бронь слота → 201, баланс уменьшился на цену.
2. Тот же ключ, `startsAt` в прошлом (или минуты, которых нет в блоках) → 201 с **той же**
   сессией и тем же балансом; в `ledger_entries` одна запись `SESSION_CHARGE`.
3. Тот же ключ на другого советника → 409 (без изменений).
4. Продление → 201; повтор того же продления после `finish` сессии → 201 с тем же
   результатом, второго списания нет.
Выкладка на `bff-dev` — по правилам `aura-bff-manor`, после проверки в маноре.
