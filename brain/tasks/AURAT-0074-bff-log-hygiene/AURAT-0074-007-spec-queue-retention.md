## Что сегодня (проверено в коде и исходниках)

### BFF — BullMQ 5.80.1, `src/jobs/queues.ts`

- Все 9 очередей чистятся **только по счёту**: `removeOnComplete` 1 000 /
  `removeOnFail` 5 000 (у `reconciliation` 10/100, у `presence` 100/100). Срока
  нет. Redis пишет `dump.rdb` на диск, в бэкап R2 не входит, удаление аккаунта
  очереди не чистит.
- **Данные задач с личным:**
  - `chatwoot-webhook` / `ingest` — `AgentDeskMessageEvent`: текст ответа
    оператора, ссылки вложений;
  - `fcm-fanout` / `ping` — FCM-токены в `tokens` на повторах (`AURAT-0070`).

  Остальные очереди несут только id — так задумано и записано в комментариях к
  типам данных.
- Поток событий очереди (`…:events`) хранит id, имя задачи и причину сбоя, но
  не данные задачи. Его не трогаем.
- **`age` в BullMQ ленивый** (`moveToFinished-14.lua:181`,
  `removeJobsByMaxAge.lua`). Старые выполненные удаляются, только когда в **той
  же** очереди завершится следующая задача. Старые упавшие — только когда
  следующая **упадёт**. В тихой очереди запись живёт сколько угодно дольше
  срока, а упавшие почти всегда лежат в тихом множестве.
- Честную границу даёт только `Queue.clean(grace, limit, type)` по расписанию.
- `jobId` для схлопывания дублей (`wh-…`, `announce-…`, `spread-picked-…`,
  `erase-…`) действует, пока запись хранится. Повторная постановка у всех
  производителей и так защищена базой: переход состояния случается один раз,
  запись идемпотентна. Счёт 1 000 уже давал то же свойство, срок его не меняет.

### Chatwoot — Sidekiq 7.3.1, `config/sidekiq.yml` (`5ce6e00`)

- `:max_retries: 3`: повторы проходят за минуты, после чего задача уходит в
  **dead set** вместе с аргументами (телефоны, тексты). Хранится
  **180 дней / 10 000 записей** — это умолчания Sidekiq (`config.rb:37-38`), в
  конфиге Chatwoot их нет.
- Переменной окружения для этих настроек нет: ERB в `sidekiq.yml` читает только
  `SIDEKIQ_CONCURRENCY`.
- **Чистка тоже ленивая:** старые мёртвые удаляются, только когда умирает
  следующая задача (`job_retry.rb:264`). Даже `:dead_timeout_in_seconds` в
  конфиге не дал бы границы в тихий период.
- Выполненные задачи Sidekiq не хранит; retry-множество живёт минуты.

## Что делаю (при рекомендуемых ответах)

### BFF

1. **Один источник сроков** в `queues.ts`: `KEEP_COMPLETED_SECONDS`,
   `KEEP_FAILED_SECONDS`. Каждая очередь получает `age` рядом со своим
   `count`: счёт остаётся потолком по памяти, срок — границей по времени.
2. **Ежечасная чистка:**
   - отдельная очередь `queue-retention` и планировщик
     `upsertJobScheduler({ every: 1 ч })` — по образцу
     `account-erasure.scheduler.ts`;
   - тонкий процессор отдаёт работу сервису, который по каждой очереди из
     одного списка зовёт `clean(срок, limit, 'completed')` и
     `clean(срок, limit, 'failed')`.

   Граница: **срок + 1 час**, в том числе в тихой очереди.
3. **Тесты (без Redis):**
   - сервис чистит каждую очередь обоими типами с нужными сроками;
   - список очередей для чистки совпадает со всеми очередями из `queues.ts`,
     чтобы новую очередь нельзя было забыть;
   - у каждой очереди в `defaultJobOptions` есть `age`, равный общему сроку;
   - планировщик не регистрируется при `NODE_ENV=test`;
   - `app.module.spec` поднимает граф.

   Сам `clean` проверяется в маноре.
4. README: абзац о сроках хранения в разделе про джобы.

### Chatwoot

5. **Ежедневная задача Coolify** (Scheduled Task в панели, контейнер `sidekiq`,
   без правки образа и без монтирования):

   ```
   bundle exec rails runner 'Sidekiq::DeadSet.new.each { |j| j.delete if j.at < 7.days.ago }'
   ```

   Это настройка панели, а не репозитория. Команду, контейнер и расписание
   записываю в `AURAS-0004`; включает её манор или владелец после проверки
   командой один раз вручную. Релиза `main` она не ждёт.

## Решения владельца

### Q3. Сроки в очередях BFF

- **A (рекомендую): одинаково для всех** — выполненные **сутки**, упавшие
  **7 дней**. Одна фраза в политике. Выполненные задачи никто не читает — у
  сервиса нет панели очередей. Упавшие нужны для разбора, неделя закрывает
  выходные.
- **B: строже для очередей с личным** — `chatwoot-webhook` и `fcm-fanout`:
  выполненные **1 час**, упавшие **3 дня**; остальные — сутки / 7 дней. Меньше
  срок у текстов, но две цифры в политике.

### Q4. Граница честная или ленивая

- **A (рекомендую): `age` + ежечасная `clean()`** — граница «срок + час» при
  любом трафике.
- **B: только `age`** — одна строка на очередь, без новой очереди и
  планировщика. Границы нет: в тихой очереди запись живёт до следующей задачи,
  упавшая — до следующего сбоя.

### Q5. Dead set Chatwoot (180 дней с аргументами)

- **A (рекомендую): ежедневная задача Coolify** удаляет мёртвые старше
  **7 дней**. Без монтирования, но живёт в панели, поэтому записывается в
  runbook. Цена: мёртвую задачу старше недели нельзя переотправить из Sidekiq
  UI.
- **B: только честная строка** — «до 180 дней, до 10 000 записей».
- (Отклонено: `:dead_timeout_in_seconds` через сгенерированный в `command`
  конфиг. Хрупко, как монтирование, и всё равно лениво.)

- `dump.rdb` в бэкап R2 не входит и так (`AURAT-0042-115`, п. 6).
