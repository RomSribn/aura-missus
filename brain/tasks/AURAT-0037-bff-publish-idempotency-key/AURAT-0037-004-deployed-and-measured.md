## Измерено, а не предположено

После мержа `fc62f29` прогон против боевого BFF, ожидание до появления нового
поля в ответе:

```
новая сборка отвечает (попытка 3)
поле в ответе присутствует: true
сообщений просмотрено: 124
из них с ключом: 12
с ключом и НЕ нашего направления: 0
```

Три факта: поле в проде; ключи настоящие (12 из 124 — те, что приложение
отправляло с ключом, остальные от чаттера и из времён до ключей); гейт по
направлению держит — `source_id`, который Chatwoot пишет себе, наружу не идёт.

**Значит приложение уже видит новый ответ.** Поведение по-старому, если оно ещё
наблюдается, объясняется не отсутствием деплоя.

## Что осталось для сквозной приёмки

Ровно один прогон, и теперь он осмыслен: авиарежим посреди отправки, при
развёрнутых **обеих** половинах. Ожидание — «Not delivered» гаснет **само**.

Прежний прогон владельца был до мержа половины BFF, поэтому и показал симптом.
Более поздняя проверка («жму ещё раз, прогружается, в одном экземпляре»)
подтверждает ключ и отсутствие дубля, но не автоматическое гашение — там
нажимали.

## Одна деталь реализации, которую легко упустить

**Ключ приезжает дельта-синком истории, а не сокетом.** Фан-аут по сокету идёт
только при `direction === 'advisor'`, то есть наше собственное сообщение,
подобранное опросом, по сокету не приходит вообще. `mergeServerMessages` обязан
читать ключ из ответа `GET /v1/advisors/:advisorId/messages`.

Судя по записке, у вас это так и сделано — фиксирую, чтобы следующий читатель не
начал искать событие в сокете.
