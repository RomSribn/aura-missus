# AURAT-0035-005 — Спецификация

Дата: 2026-08-21
Задача: `AURAT-0035-app-chat-attachments`
Фича: `AURAF-0011`, строки 001–005
BFF-половина: `AURAT-0031` (закрыта, `aura-bff` @ `c9f129c`)
Решение по транспорту: `AURAD-0011`
Статус: **на утверждение**

## Что делаем

Приложение показывает вложения, которые BFF уже доставляет: картинку, файл,
голосовое и видео. Байты забираются с `GET /v1/attachments/:attachmentId`
собственным аутентифицированным запросом и кэшируются в файловой системе
устройства.

Сегодня такое сообщение приходит **пустым баблом** — и это не косметика:
`Message.parse` на контрактах `v0.7.0` срезает `attachments` до того, как
данные дойдут до UI.

## Что закрывает

| # | Строка `AURAF-0011` | Чем закрывается |
|---|---|---|
| 001 | картинка в переписке + полноэкранный просмотр | инлайн-превью в баббле, тап → просмотрщик |
| 002 | файл с именем и размером, можно открыть | строка файла, открытие системным просмотрщиком |
| 003 | голосовое | плеер в баббле: играть/пауза, длительность, прогресс |
| 004 | видео | превью с кнопкой играть, воспроизведение |
| 005 | доходит пушем, сокетом и опросом | ничего нового — вложения едут внутри того же `Message` (жёсткое правило 5) |

## Решения, уже принятые — не переспрашивать

- **`AURAD-0011`**: BFF проксирует, адрес хранилища приложению не выдаётся.
  В сообщении едет непрозрачный `id`, а не URL.
- **Скачивание в файловый кэш**, а не `<Image>` с заголовком (владелец,
  2026-08-21). Заголовок умеет только картинки, не даёт открыть файл и не имеет
  повтора на протухшем токене.
- **Все четыре типа сразу**, с дизайном (владелец, 2026-08-21).

## Порядок работ

1. **Контракт.** `@aura/contracts` `v0.7.0` → `v0.9.1`. Правка добавляющая,
   ломать ничего не должна — но `Message` меняет форму у **всех** сообщений,
   поэтому существующие тесты чата прогнать первыми.
2. **Модель.** `MessageAttachment[]` в `ChatMessage`, перенос в `mapMessage`.
   Вложение без подписи (`content: ''`) перестаёт быть «пустым сообщением» —
   проверить, что ничто ниже по потоку не считает такое сообщение мусором.
3. **Транспорт (ядро задачи).** Аутентифицированное скачивание в кэш:
   `shared` получает путь для бинарных ответов рядом с `bffRequest`, с тем же
   ретраем 401 через `authService.getIdToken(true)`. Один запрос на файл,
   повторный показ берёт из кэша. Состояния: качается / готово / **не удалось +
   повтор**. Молчаливого отказа быть не должно — вся фича заведена ровно из-за
   молчаливого отказа на другом конце.
4. **Дизайн.** См. отдельный раздел ниже. Идёт **до** UI-кода.
5. **UI.** Рендерер на каждый из четырёх типов + полноэкранный просмотр
   картинки. `MessageBubble` остаётся render-only (жёсткое правило 4):
   загрузка, кэш и повтор живут в `model/`, форматирование размера — в `lib/`.
6. **Превью в списке чатов.** `previewOf` (`ChatListRow.tsx:24`) у вложения без
   подписи даёт пустую строку. Заменить на подпись по типу («Фото», «Файл»,
   «Голосовое», «Видео») — с подписью сообщения показывать текст.
7. **Тесты.** Обязательно: вложение без текста рисуется; отказ скачивания даёт
   видимую ошибку и повтор; повторный показ не качает второй раз; неизвестный
   `kind` из будущего контракта не роняет экран.
8. **Post-execute.** Таблица скоупа `AURAF-0011`: 001–005 → `✓` по `UI` и `BE`.

## Дизайн — отдельный, именованный результат

Дизайна на вложения нет вообще: в `design_handoff_aura` они упомянуты один раз,
как назначение иконки. Значит это не «дорисовать баббл», а спроектировать.

Что должно появиться:

- **`.claude/design_handoff_aura/CHAT_ATTACHMENTS.md`** — по образцу
  `SESSIONS_BOOKING.md`: шапка с палитрой и типографикой, поэлементная
  спецификация, состояния, моушн-токены.
- **Рендеры в `design_handoff_aura/screens/`**, нумерация продолжает
  существующую (последний — `27-sheet-cancel-late.png`).

Что дизайн обязан покрыть, включая нелюбимое:

- баббл с картинкой (одна, несколько), соотношение сторон, скругления, как
  ведёт себя `width`/`height: null` — размеров может не быть;
- строка файла: иконка по типу, имя (длинное — как обрезается), размер;
- голосовое: играть/пауза, дорожка прогресса, длительность;
- видео: превью, кнопка играть;
- полноэкранный просмотр: фон, закрытие, жесты;
- **состояния**: скачивается, не удалось + повтор, файла больше нет (BFF на
  удалённый файл отвечает 404);
- вложение **с подписью** и **без** — у второго `content: ''`;
- обе стороны переписки: своё вложение (коралловое) и от советника (белое).

Правило двух тонов остаётся: коралл — действие, тил — коммуникация.

## Открытые вопросы — решить в ходе задачи

- **Зависимости.** Скачивание в файл и воспроизведение — новые нативные пакеты,
  то есть пересборка обеих платформ. Кандидаты проверить на совместимость с
  RN 0.85 и новой архитектурой: `react-native-blob-util` (скачивание + fs),
  `react-native-video` (умеет и аудио, и видео — один пакет вместо двух).
- **Политика кэша**: предел размера, вытеснение, живёт ли кэш между запусками.
- **Открытие файла**: системный просмотрщик через share sheet или свой экран.

## Приёмка

Советник шлёт из Chatwoot картинку, pdf, голосовое и видео — все четыре видны в
переписке и открываются. Вложение без подписи выглядит осмысленно, а не пустым
баблом. При выключенной сети видна ошибка и есть повтор, а не тишина. В списке
чатов последняя строка не пустая.
