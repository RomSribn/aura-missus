## Этап A · `@aura/contracts` v0.17.0

Репозиторий `/Volumes/Work/personal/ai-manors/aura-contracts` (ветка `main`,
**вне манора**; пуш тега — внешнее необратимое действие, идёт через разрешение).

Правится `src/profile.ts` — аватар это часть профиля, и держать его отдельным
файлом значило бы развести по двум местам одну форму ответа. (Тот же выбор, что
в `chat.ts`, где `AttachmentLimits` живёт рядом с сообщением.)

| Экспорт | Что это |
|---|---|
| `AvatarId` | `/^[A-Za-z0-9_-]{1,64}$/` — форма один в один с `AttachmentId`, и по той же причине: строгая проверка того, что пришло с устройства, на пути внутрь |
| `AvatarLimits` | `maxBytes: 8 * 1024 * 1024`, `maxPixelsPerSide: 4096`, `acceptedTypes: ['image/jpeg', 'image/png', 'image/webp']` |
| `AvatarRefusalCode` | `avatar_empty`, `avatar_too_large`, `avatar_type_not_accepted`, `avatar_too_many_pixels` — форма `SendRefusalCode`: отказ, с которым человек должен что-то сделать, отличается от того, который надо просто повторить |
| `ProfileResponse.avatarId` | `z.string().nullable().default(null)` |

**Почему эти числа.**

- **8 МБ.** Устройство после ресайза шлёт 200–400 КБ; потолок нужен не для него,
  а для сборки, которая ресайза не делает. Он же обязан оставаться заметно ниже
  15 МБ, которые принимает `Avatarable` у Chatwoot, — иначе мы примем файл,
  который стол потом отвергнет **на фоновой задаче**, то есть тихо.
- **4096 px по стороне.** Байты мы не декодируем, а стол декодирует: он строит
  вариант шириной 250 px. PNG 20000×20000 весом меньше 8 МБ — обычное дело.
  4096 — вдвое больше того, что мы просим у устройства.
- **Три типа, а не четыре.** `image/gif` стол принимает, но анимированный аватар
  — решение, которого никто не принимал, и на клиенте это развилка «первый кадр
  или анимация». Исключён сознательно. `image/heic` невозможен: его нет в
  `ALLOWED_AVATAR_CONTENT_TYPES`.

Список обязан быть **подмножеством** списка `Avatarable`; в спеке контракта это
записано комментарием, в тесте — утверждением.

**Расширение `ProfileResponse` безопасно для уже стоящих сборок**: схема не
`.strict()`, а поля с `.default(null)`. Сборка на `v0.16.0` просто отбросит
`avatarId` вместо падения на `.parse`. Это проверено, а не предположено — ровно
тот риск, который в `AURAT-0062` стоил дня разбора.

## Этап B · `aura-bff`

### B1 · Схема и миграция

`model User` — три колонки:

```prisma
avatarId          String?
avatarKey         String?
avatarContentType String?
```

Индексов нет: по ним не ищут, поиск идёт по `avatarId` только в одном маршруте и
через строку пользователя.

**Три колонки, а не одна выводимая.** Ключ можно было бы собирать из `avatarId`
по шаблону — и тогда раскладка бакета замёрзла бы навсегда. `AURAD-0012`
записало обратное: развязка — это база. `avatarContentType` хранится, чтобы
отдавать байты и пересылать их столу, ни разу не нюхая их повторно.

Все три `null` у подавляющего большинства: `ProfileOrb` остаётся видом по
умолчанию навсегда, и это дизайн, а не отсутствие данных.

Миграция `prisma/migrations/20260908<hh mm ss>_user_avatar/migration.sql` пишется
руками (в слейве базы нет) и сверяется с канонической через
`prisma migrate diff --from-empty --to-schema` — приём из `AURAT-0058`.

### B3 · Общее: сниффер переезжает, к нему добавляется измеритель

`src/modules/chat/attachment-sniffer.ts` → **`src/common/media/content-sniffer.ts`**
(вместе со своим спеком). Импорт из `modules/chat` в `modules/profile` был бы

Рядом — **`src/common/media/image-dimensions.ts`**: ширина и высота из заголовка,
без декодирования. JPEG (маркеры `SOF0…SOF2`), PNG (`IHDR`), WebP
(`VP8` / `VP8L` / `VP8X`). Около шестидесяти строк, в том же духе, что сниффер:
руками, потому что список закрыт и мал, и потому что это можно проверить тестом.

> Если владелец сочтёт измеритель лишним — он снимается один в один вместе с
> кодом отказа `avatar_too_many_pixels`, и тогда единственным, кто защищён от
> картинки-бомбы, остаётся сам Chatwoot. Записано как выбор, а не как данность.

### B4 · Модуль хранения

```
src/modules/storage/
  object-storage.port.ts        # put / delete, доменные типы, никакого S3
  r2-object-storage.service.ts  # единственное место, где живут SDK и имя бакета
  storage.module.ts
```

Порт отдельно от реализации — по той же причине, по которой в `chatwoot`
запечатано «где физически лежит файл»: остальной код не должен знать, что
хранилище вообще S3-совместимое. Зависимость `@aws-sdk/client-s3` — первая
внешняя за долгое время, и она названа в `AURAD-0013` как цена решения.

Переменные окружения в `src/config/env.schema.ts`:

```
AVATAR_STORAGE_ENDPOINT          # https://<account>.r2.cloudflarestorage.com
AVATAR_STORAGE_BUCKET            # приватный, отдельный от aura-assets
AVATAR_STORAGE_ACCESS_KEY_ID
AVATAR_STORAGE_SECRET_ACCESS_KEY
```

**Обязательны в production, необязательны в остальном** — тем же
`superRefine`, что уже стоит для `GOOGLE_PLAY_*` (`env.schema.ts:209`), и по той
же логике. Требовать их всюду значит запретить поднимать стек без токена R2;
не требовать нигде — дать проду принимать фотографии, которые некуда положить.
Без переменных маршруты аватара отвечают 404, как это делают кошельковые при
`BILLING_ENABLED=false`.

Ключ: `avatar/<userId>/<avatarId>.<ext>`. Не плоско, как у карт: там ключей 78 и
они вечные, здесь по объекту на человека и они меняются, а префикс по
пользователю делает уборку за удалённым аккаунтом одним запросом.

### B5 · Маршруты (в `modules/profile`, не отдельным модулем)

`avatar.controller.ts` + `avatar.service.ts` рядом с профильными: это тот же
домен и та же строка в базе. Отдельный модуль дал бы третий репозиторий поверх
`users`.

| Маршрут | Что делает |
|---|---|
| `PUT /v1/me/avatar` | multipart, ровно один файл в поле `avatar`. Отвечает **полным `ProfileResponse`** |
| `DELETE /v1/me/avatar` | снимает фотографию. Отвечает `ProfileResponse` |
| `GET /v1/avatars/:avatarId` | байты, `Cache-Control: private, max-age=86400, immutable` |

**Почему раздача по `avatarId`, а не `GET /v1/me/avatar`.** Адрес обязан
меняться вместе с картинкой, иначе `immutable` — ложь, и устройство показывает
старое лицо после замены. Тот же приём, что у вложений, и клиентский кэш
(`attachment-cache.ts`) уже ключуется именно так.

**Проверка владения обязательна, хотя id непрозрачен.** Непрозрачность — не
авторизация. Правило то же, что у вложений: существующий, но чужой — это 404, а
не 403.

`PUT` отвечает профилем целиком, а не одним полем: ровно как `PATCH /v1/me`,
и по той же причине — экран показывает то, что сервер хранит, а не то, что
отправил.

### B6 · Порядок операций при замене

1. Приём и проверки (B7). Ничего не записано.
2. `put` нового объекта под новым `avatarId`.
3. Строка пользователя переставлена на новый ключ.
4. Старый объект удалён. **После**, а не до: упавшее удаление оставляет мусор,
   упавшая запись после удаления оставляет человека без фотографии.
5. В очередь — задача на отправку столу.

Пятый шаг **не входит в успех загрузки**. Стол недоступен — фотография у
владельца всё равно есть.

### B7 · Правила приёма (сервер не верит клиенту)

| Что | Принимается | Отклоняется |
|---|---|---|
| Форма | ровно один файл в поле `avatar` | ноль файлов, второй файл |
| Тип | по **байтам**, из `AvatarLimits.acceptedTypes` | всё прочее — `avatar_type_not_accepted`, 415. Заявленный тип в текст ошибки не попадает |
| Размер | ≤ 8 МБ | больше — `avatar_too_large`, 413 |
| Стороны | ≤ 4096 px | больше — `avatar_too_many_pixels`, 413 |
| Пустой файл | — | `avatar_empty`, 400 |

Файл **буферизуется**, а не стримится дальше — тот же довод, что записан в
`attachment-intake.ts`: оборванная загрузка иначе доезжает до хранилища
обрезанной и выглядит успешной. Потолок в 8 МБ — то, что делает буферизацию
ограниченной.

### B8 · Отправка столу

В `chatwoot.client.ts`:

- `setContactAvatar(contactId, { bytes, contentType, fileName })` —
  `PUT /contacts/:id`, multipart, поле `avatar`.
- `deleteContactAvatar(contactId)` — `DELETE /contacts/:id/avatar`.

Сегодняшний `postMultipart` зашит под `POST /messages` (`message_type`,
`attachments[]`); понадобится соседний метод с той же дисциплиной — `FormData`,
без ручного `content-type`, с таймаутом.

Очередь `avatar` (BullMQ, как в пяти других модулях), задачи `push` и `purge`,
повторы с отступом.

**Шов, который легко пропустить.** `User.chatwootContactId` пуст, пока человек
не начал первый разговор: контакт заводится при провижининге. Значит:

- задача с пустым `chatwootContactId` — не ошибка, а **no-op**;
- `provisioning.service.ts` при создании контакта обязан приложить аватар, если
  он уже есть. Иначе у всех, кто поставил фотографию до первого чата, стол её не
  увидит никогда.
