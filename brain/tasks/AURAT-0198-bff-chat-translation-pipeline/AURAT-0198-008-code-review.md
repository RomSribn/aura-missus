## Дефекты

1. **[high] Сбой Redis вешает ответ отправки.** `chat.service.ts` ждёт `enqueueDeskNote` → `queue.add`. Корневое
   соединение BullMQ работает с `maxRetriesPerRequest: null`, поэтому промис при сбое не отклоняется. При сбое Redis
   `forDesk` даёт `note`, пост и upsert проходят, а HTTP-ответ висит. Нарушен §7 п. 3 спеки. Нужно не ждать постановку
   или ограничить её сроком, и тест с `queue.add`, который не завершается.
2. **[medium] Репозиторий не проверен.** Тесты `ChatService` пропускают мок насквозь. Нужна спека
   `PrismaMessagesRepository` на моке `PrismaService`:
   - аргументы `listTranslationsFrom`;
   - `cursorPosition = null` → `[]` без запроса;
   - `emptyLiveRow` → `messageTranslation.deleteMany`;
   - `toRecord`: без перевода у `USER` / `SYSTEM`, `TRANSLATED` без `content` → `failed`.

   Второй предохранитель — `direction === 'advisor'` в `toDto`. Пункты §7.6 и §7.9 — в тесты или явно в план проверки
   в маноре.
3. **[low] Сторож ставит `requeued` до постановки.** Если процесс убит или Redis отказал между двумя записями,
   перевод останется помеченным без задачи и через 10 мин станет `FAILED`. Сначала `queue.add`, потом пометка;
   `try/catch` на каждую запись пачки.
4. **[low] Ответ длиннее 8000 знаков.** `validateRequest` бросает `RangeError` — 4 повтора и ~2,5 мин ложного
   «Translating…». Не создавать `pending` и/или `RangeError` → сразу `FAILED`. Тест.
5. **[low] Повтор с тем же `idempotencyKey` во время перевода.** Ключ проверяется до `forDesk`, кэш пишется после
   вызова → двойная оплата, дубль на столе, 500 на P2002. Повторить `findByIdempotencyKey` перед постом; маркер «в
   работе» на ключе кэша (`SET NX PX`), чтобы второй запрос не звал модель.
6. **[low] Повтор задачи после оплаченного перевода платит снова.** `deskNote` платит до `postPrivateNote`, `reply` —
   до `settleTranslation`. Перевод по `messageId` в Redis (~1 ч) до побочного шага.
7. **[low] Тесты сроков.** Ветка «осталось < `MIN_CALL_MS`» не покрыта; тест «the call gets only what is left» упасть
   не может. Фейковые таймеры или шпион; тест «слот освободился, осталось < 1 с → `timeout`, 0, адаптер не вызван».

## Из живой проверки на bff-dev

8. **Код и тип ошибки API в лог.** При отказе в логе было только `reason: provider`. Причину (400
   `invalid_request_error`, «key not scoped to a workspace») нашли отдельным вызовом. Писать в структурную строку
   `status` и `errorType`, без `message`.
   Дополнение координатора (прогон кампаний, `AURAT-0192-013-live-run.md`): `ms` в строке `translation` считается от
   входа в `translate()`, вместе с ожиданием слота. При параллельности 3 он рос от 7,4 до 66,6 с при вызове ≈ 7,5 с —
   для p95 (задача 6) это вводит в заблуждение. Писать раздельно: `waitMs` (ожидание слота) и `callMs` (вызов).
9. **Проба предохранителя.** После паузы первый вызов — проба, остальные сразу получают отказ `provider`. Кампания на
   23 языка перевела 1, 22 получили отказ. Правка на выбор (записать): ждать итога пробы в пределах своего срока, или
   повторять отказ «пробует» после пробы. Для чата: ответ в окно пробы не должен стать окончательным `FAILED`.
