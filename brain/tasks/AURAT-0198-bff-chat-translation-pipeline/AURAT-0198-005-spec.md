# AURAT-0198-005 — spec: конвейер перевода сообщений чата

Дата: 2026-11-08 · Статус: **черновик, ждёт ревью координатора и одобрения владельца** · slave-1
Фича `AURAF-0024` (строки 001, 002), задача 5 разбивки `AURAI-0012` (§1.2–§1.4, §3, §7). Контракт —
`@aura/contracts` v0.31.0 (`AURAT-0195-005`). Решения в силе: 3, 4, 5, 6, 7, 10 `AURAI-0012`; `AURAT-0196` (все А).
Тип: задача, без отдельного файла фичи. Факты — `004-context.md`.

## Что получится

Два направления перевода, **у каждого свой выключатель, оба выключены по умолчанию**. Включаются по очереди, сначала
«человек → чаттер» (решение 8):

1. **Человек → чаттер.** Человек пишет по-немецки, а чаттер в Chatwoot видит английский перевод. Оригинал открывается
   по «View original». Если перевод не удался, сообщение уходит как есть, а следом приходит приватная заметка с
   переводом. **Отправка не ломается ни при какой ошибке перевода.**
2. **Чаттер → человек.** Ответ советника доставляется сразу, как сейчас, с `translation: pending`. Перевод
   дописывается отдельной очередью, после чего приходит WS `message.translated`. Фоновый клиент догоняет переводы
   через `translatedFrom`.

**Переводит сервер только когда выполнено всё сразу** (в обе стороны, проверяется и при постановке, и в момент
перевода):
- выключатель направления включён;
- профиль `chat` модуля перевода не `off`;
- `translationActive(user)`: переключатель и согласие текущей версии;
- `chatLanguage` не `null` и не `en` (решение 4);
- язык не выключен `DISABLED_LANGUAGES` и его поддерживает адаптер.

Иначе чат работает ровно как сегодня. Старые сборки согласие не дают, поэтому перевод у них не включается никогда.

**Платных вызовов в задаче нет.** Тесты идут на `FakeTranslator` и моках. Модель, бюджет и ключ предлагаются (§6),
а включает их владелец.

## 1. Модуль перевода — профиль `chat` и цель `en`

- `TRANSLATION_PROFILES = ['campaign', 'chat']`. `readTranslationConfig` и `requireTranslationProfiles` получают
  набор `TRANSLATION_CHAT_*` — те же правила «всё или ничего», что у кампаний. `fake` при `NODE_ENV=production` —
  отказ загрузки.

  | Переменная | По умолчанию | Смысл |
  |---|---|---|
  | `TRANSLATION_CHAT_PROVIDER` | `off` | `off` / `fake` / `claude` |
  | `TRANSLATION_CHAT_MODEL` | — | обязательна при `claude` |
  | `TRANSLATION_CHAT_EFFORT` | `low` | |
  | `TRANSLATION_CHAT_THINKING` | `off` | Opus при `off` адаптер отвергает при старте (`0191`) |
  | `TRANSLATION_CHAT_TIMEOUT_MS` | `6000` | срок одного вызова; у отправки он же — срок всего перевода вместе с ожиданием слота (§2.2) |
  | `TRANSLATION_CHAT_CONCURRENCY` | `4` (1–8) | семафор профиля и параллельность воркера очереди |
  | `TRANSLATION_CHAT_MONTHLY_BUDGET_USD` | — | обязательна при `claude` |
  | `TRANSLATION_CHAT_TO_DESK` | `false` | выключатель «человек → чаттер» |
  | `TRANSLATION_CHAT_REPLIES` | `false` | выключатель «чаттер → человек» |

  Выключатели отделены от профиля намеренно. Профиль решает, **чем** переводить (модель, бюджет, ключ), а
  выключатели — **что** переводить. Так можно включить профиль и одно направление, не трогая второе. Смена — env и
  перезапуск, как у профиля.
- **Перевод в `en`.** Сейчас его запрещают три места: `supports()` обоих адаптеров исключает `en`, `enabled` в
  `onModuleInit` тоже, а `validateRequest` отвергает цель вне `supported`.
  - Правка: адаптеры отдают все `LANGUAGES`, а `supported` профиля = их список минус `DISABLED_LANGUAGES`.
  - Запрет `from === to` остаётся. Кампании `en` не просят: они переводят **из** `en`.
  - Промпт Claude к цели `en` уже готов: `registerBlock` возвращает для неё пусто, глоссарий пропускается.
- **Срок ожидания слота.** `Semaphore.acquire(signal?)`: отмена снимает ждущего из очереди.
  - `translate(profile, request, { timeoutMs, waitSignal })` при отмене ожидания бросает
    `TranslationUnavailableError('timeout', true)` со стоимостью 0.
  - Нужно отправке: если очередь занята переводами ответов, человек не должен ждать дольше срока.
- `ChatTranslationService` — в модуле `chat`, а не `translation`. Ему нужны сообщения, пользователи, доставка и
  стол, а модуль перевода остаётся общим (кампании). `ChatModule` импортирует `TranslationModule`, цикла нет.

## 2. Человек → чаттер (отправка)

### 2.1 Где в `sendMessage`

Порядок: `ensureConversation` → `recordSendLanguage` → проверка `idempotencyKey` (ранний выход — без перевода) →
**`deskTranslation = chatTranslation.forDesk(…)`** → `postUserMessage(…, deskTranslation)` → upsert → **при сбое
перевода — задача `desk-note`**.

`forDesk` **никогда не бросает**: любая ошибка (модуль, Redis, база) логируется и даёт «без перевода».

### 2.2 `forDesk`

1. Условия из «Что получится». Пользователь читается **после** `recordSendLanguage`, поэтому язык этой отправки уже
   действует.
2. **Локальная проверка до вызова.** Есть текст, и в нём, без ссылок, есть хотя бы одна буква (`\p{L}`). Эмодзи,
   число или голая ссылка уходят без вызова. Детектор языка не нужен: при `chatLanguage = en` вызова нет вообще
   (решение 4), а английский текст при немецком интерфейсе модель вернёт с `sourceLanguage: en` (п. 5).
3. **Кэш** — только когда есть `idempotencyKey`:
   - ключ Redis `chat-translation:desk:<sha256(conversationId, idempotencyKey, текст)>`;
   - значение `{ text, engine }`, TTL 24 ч.

   Повтор отправки, у которой пост прошёл, а ответ до телефона не дошёл, второй раз не платит. Сырых id и текста в
   ключе нет.
4. **Вызов** — `translate('chat', …)`:
   - `from: 'auto'`, `to: 'en'`;
   - одна позиция `form: 'message'`;
   - `speaker: { role: 'client' }`;
   - `context` — до 4 предыдущих сообщений разговора, только текст, каждое обрезано до 500 символов, без метаданных;
   - срок — `TRANSLATION_CHAT_TIMEOUT_MS` на всё, ожидание слота включено (§1).
5. **Итог:**
   - `translated` → текст для стола и запись в кэш;
   - `sourceLanguage === 'en'` или позиция `rejected` → без перевода, без заметки;
   - `TranslationUnavailableError`, у которого `retryable` (таймаут, 429, провайдер, открытый предохранитель) → без
     перевода **и** задача `desk-note`;
   - нет бюджета, нет кредита, `auth`, отказ модели → без перевода, без заметки: заметка упала бы так же. Персоналу
     пишет уже модуль (`0191`).

### 2.3 Стол — запечатано в адаптере `chatwoot`

- Порт: `postUserMessage(conversationId, { content, sourceId?, attachment?, deskTranslation? })`. Доменное поле,
  ни слова о Chatwoot.
- Клиент:
  - JSON — `content_attributes: { translations: { en: deskTranslation } }`;
  - multipart — поле `content_attributes` JSON-строкой (`safe_parse_json` в `message_builder.rb`, `AURAI-0012` §1.1).
- `content` — всегда оригинал человека. В BFF и в приложении сообщение человека остаётся оригиналом.
- Известное ограничение (проверка стола): **превью в списке разговоров показывает оригинал**. Поменять это нельзя, не
  потеряв оригинал: пузырь берёт `translations[локаль агента]`, а без неё первый ключ. Уведомление агенту проверяется
  в маноре.

### 2.4 `desk-note` — заметка при сбое

- Очередь `chat-translation`, задача `desk-note`, данные `{ messageId }`, `jobId = dn-<messageId>`.
- 3 попытки, пауза от 30 с с удвоением.
- Процессор тонкий → `ChatTranslationService.deskNote(messageId)`.
- Сервис:
  1. перечитывает строку. Нет её, удалена, не `user`, старше 1 ч или условия больше не выполнены (например, согласие
     отозвано) → выход без вызова;
  2. переводит, как в §2.2;
  3. ставит приватную заметку `Translation (EN): <текст>` (`postPrivateNote`, без упоминания).
- Нормализатор режет приватные сообщения, поэтому в приложение заметка не попадёт.
- **Переводы сообщений человека в Postgres не хранятся.** Это отступление от `AURAI-0012` §1.2: задаче строка
  `MessageTranslation(en)` не нужна (дедуп — `jobId`), а лишняя копия текста — против минимизации (§6 п. 7).
  Остаются кэш в Redis на 24 ч и сама заметка на столе.

## 3. Чаттер → человек (приём)

### 3.1 Данные — миграция `20261108120000_message_translations` (только файлом)

```prisma
enum MessageTranslationStatus { PENDING TRANSLATED FAILED }

model MessageTranslation {
  id        String                   @id @default(cuid())
  messageId String
  message   Message                  @relation(fields: [messageId], references: [id], onDelete: Cascade)
  language  String                   // the person's chatLanguage when the reply arrived
  status    MessageTranslationStatus
  content   String?                  // TRANSLATED only
  engine    String?                  // ours (`claude:…`); never leaves the server
  requeued  Boolean                  @default(false) // the watchman re-queued it once
  createdAt DateTime                 @default(now())
  updatedAt DateTime                 @updatedAt
  @@unique([messageId, language])
  @@index([status, updatedAt])
}
// Message: translations MessageTranslation[]
```

- `messages` по-прежнему таблица приёма, которую потом никто не меняет: состояние перевода живёт отдельно.
- Стирание аккаунта удаляет сообщения (`deleteMany`), переводы уходят каскадом. Удаление столом (`emptyLiveRow`)
  удаляет переводы в той же транзакции.
- SQL — `CREATE TYPE`, `CREATE TABLE`, FK `ON DELETE CASCADE`, уникальный ключ и индекс. Сверяется офлайн с
  `prisma migrate diff`. `generate` — в слоте, `migrate deploy` — только в маноре.

### 3.2 Приём

`ingestResolved` (вебхук и сверка — один путь):
1. `toUpsert` дополнительно отдаёт `captionIsFallback`: текст — подпись-заглушка парсера токена («Choose a card»,
   «Continue this reading privately»), клиент показывает своё слово.
2. Строка советника с текстом, без заглушки, и выполнены условия → upsert несёт `translation: { language }`. Это
   **вложенный create** `PENDING` в том же `messages.create`, то есть в той же транзакции. Повтор вебхука проигрывает
   гонку на уникальном ключе сообщения и до перевода не доходит.
3. `inserted` → **сначала** fan-out (DTO с `translation: { status: 'pending', language }`), **потом** задача
   `reply` с `jobId = tr-<messageId>`. Обратный порядок дал бы шанс `message.translated` обогнать `message.new`.
   Ставит только вставивший, поэтому сверка за перевод не борется. Сбой постановки логируется, задачу подберёт
   сторож (§3.4).
4. Пуш не меняется: пинг без текста.

### 3.3 Задача `reply`

- Очередь `chat-translation`, данные `{ messageId }`.
- 5 попыток, пауза от 10 с с удвоением: окно около 2,5 мин.
- Параллельность воркера — `TRANSLATION_CHAT_CONCURRENCY`.
- Процессор передаёт сервису только `lastAttempt` (учёт попыток — его забота).

`ChatTranslationService.translateReply(messageId, { lastAttempt })`:
1. Строка и её перевод. Нет строки, удалена, перевод не `PENDING` → выход.
2. Условия ещё раз — на **языке из `pending`-строки**, даже если язык чата сменился. Не выполнены (перевод выключен,
   согласие отозвано, язык выключен, выключатель или профиль off) → `FAILED` без вызова.
3. Вызов `translate('chat', …)`:
   - `from: 'en'`, `to: <язык>`;
   - `speaker: { role: 'advisor', gender: Advisor.gender }`;
   - `context` — как в §2.2.
4. Итог:
   - `translated` → `TRANSLATED`, `content`, `engine`;
   - `rejected` (токены, глоссарий, типографика) → `FAILED`;
   - `TranslationUnavailableError`:
     - `retryable` и не последняя попытка → бросить, строка остаётся `PENDING`, BullMQ повторит;
     - иначе → `FAILED`.
5. Запись **условная**: `UPDATE … WHERE status = PENDING`. Только тот, кто её сделал, шлёт
   `delivery.pushMessageTranslated` — WS, без пуша, из перечитанной строки (правило 5).

### 3.4 Сторож — в конце прохода сверки

Отдельный `try/catch`: сбой сторожа не ломает сверку. Пачка — до 100 строк.
- `PENDING` старше 10 мин и `requeued = false` → `requeued = true`, задача `jobId = tr-<messageId>-r`. Нужен новый
  `jobId`: прежний держит запись выполненной задачи 24 ч.
- `PENDING` старше 10 мин и `requeued = true` → `FAILED` и `message.translated`.

Итог: `pending` живёт не дольше ~20 мин, и **`failed` всегда окончательный** (решение 1).

### 3.5 Что видит приложение

- **`toDto`** (история, `message.new`, сверка — один маппер): у `advisor`, если есть перевод:
  - `{ status: 'pending', language }`;
  - `{ status: 'translated', language, content }`;
  - `{ status: 'failed', language }`.

  `engine` не уходит. У `user` и `system` поля нет. Перевод едет в `MESSAGE_INCLUDE`, без N+1.
- **`translatedFrom` → `translations`**: `listTranslationsFrom(conversationId, fromId, 200)`.
  - Отбор: сообщения советника на этой позиции и после, не удалённые, с переводом.
  - Порядок — **`chatwootMessageId` по возрастанию, старые первыми**, как `deletedIds`. Предел тот же
    (`DELETED_IDS_LIMIT` → общий `CATCH_UP_LIMIT = 200`).
  - Незнакомый id даёт `[]`.
  - Без `translatedFrom` поля нет (контракт: отсутствие = «не догоняет»).
- **WS `message.translated`** — `{ advisorId, messageId, translation }`, только `translated | failed`.
- **OpenAPI:** `Message.translation`, параметр `translatedFrom`, `HistoryResponse.translations` (с порядком),
  событие в описании сокета.

## 4. Что не переводится (обе стороны)

| Что | Как |
|---|---|
| Токены чаттера `::…::` | Режутся в `toUpsert` до перевода. Новые токены в выходе модели → `rejected` (`checkItem`) → `FAILED` |
| Подписи-заглушки | `captionIsFallback` → без перевода |
| Маркеры сессии (`system`) | Не переводятся никогда |
| Вложение без подписи, пустой текст, нет букв | Без вызова |
| Язык `en` / `null`, нет согласия, выключено | Без вызова, как сегодня |
| Удаление столом | Перевод удаляется в транзакции удаления; задача видит удалённую строку и выходит |
| Правка столом | Сейчас не обрабатывается вовсе — перевод не меняется |

## 5. Журнал и приватность

- В логах только `profile`, `engine`, `to`, `reason`, `costUsd`, `ms` (модуль) и `messageId` / `conversationId`
  (конвейер). Ни текста, ни языка вместе с UID.
- В данных задач только `messageId`, текста нет. Кэш Redis — 24 ч, ключ — хэш.
- Провайдеру уходит текст, до 4 предыдущих сообщений, код языка и род персоны. Имени, телефона, id и вложений нет
  (`AURAI-0012` §6).

## 6. Решения (рекомендация первой)

1. **Окончательный `failed` (из ревью `0197`).**
   - **А:** `failed` всегда окончательный. Всё, что ещё может дозаполниться, — `pending`: повторы BullMQ ~2,5 мин, один
     перезапуск сторожем, итого не дольше ~20 мин. Дозаполнения после восстановления предохранителя нет.
     - Контракты: **только JSDoc** (без тега, как `54407ea`) — «`failed` окончателен; `translatedFrom` — самое
       старое `pending`»; плюс порядок `translations` (решение 4).
     - Приложению — малая задача: якорить догонку только на `pending`.
     - Цена: ответы, пришедшие во время долгого сбоя (больше ~20 мин), останутся английскими.
   - **Б:** у `failed` новое поле `final?: boolean` (contracts minor v0.32.0), сервер дозаполняет неокончательные
     `failed` моложе 24 ч после восстановления (`AURAI-0012` §1.3 п. 6). Сложнее (раунды, окно, поле), клиент якорит
     на `pending | failed без final`.
2. **Переводы сообщений человека в Postgres — не хранить** (§2.4). Б — `MessageTranslation(en, translated | failed)`
   без текста, как в `AURAI-0012` §1.2.
3. **Модель и бюджет профиля `chat` — предложение, решают владелец и eval** (решения 1, 2):
   - **старт на staging:** `claude-haiku-5-5`, `THINKING=off`, `EFFORT=low`, бюджет **$20 в месяц**, таймаут 6 с,
     параллельность 4. По `AURAI-0012` §4 Haiku `off` стоит ≈ $1,4 / $4,3 / $14 при трафике ×1 / ×3 / ×10. Вместе с
     кампаниями ($25) и eval (~$10) это укладывается в кредит $100;
   - **если eval (задача 6) покажет, что Haiku не тянет** (mt, ga, обращение): `claude-sonnet-5-5` `off`,
     ≈ $30 / $90 при ×1 / ×3, бюджет $60 — тогда кампании и чат вместе почти выбирают кредит;
   - Opus 5.5 — только эталон eval.

   Ключ (решение 9): тот же `ANTHROPIC_API_KEY`, что у кампаний, отдельный workspace staging / прод со своим spend
   limit. В этой задаче ключа нет, выключатели и профиль — `off`.
4. **Порядок `translations` — старые первыми** (по `chatwootMessageId`), закрепить в JSDoc контракта и в OpenAPI.
   JSDoc — в клоне `aura-contracts`, ветка `feature/AURAT-0198-translation-jsdoc` от `main` `fa56e89`, застейджено
   без коммита. Тег не нужен, коммит в `main` — координатор (как `54407ea`). При Б решения 1 это становится v0.32.0
   с тегом.
5. **Срок отправки — 6 с по умолчанию** (ожидание слота включено). Б — 3 с: быстрее отправка, чаще заметка вместо
   перевода. Точное значение — по p95 замера на staging (задача 6).

## 7. Проверки в слоте (без стека, без платных вызовов)

`prisma validate` / `generate`, `lint`, `typecheck`, `build`, `jest`. Чистые тесты:

1. **Модуль:** профиль `chat` из env, правила «всё или ничего», `fake` в проде — отказ; цель `en` поддерживается,
   `en → en` — `RangeError`; `Semaphore.acquire(signal)` — отмена снимает ждущего, слот не теряется; `translate` с
   отменённым ожиданием → `timeout`, стоимость 0, адаптер не вызван.
2. **Условия** (таблица): выключатель, профиль, `translationActive`, `en` / `null`, выключенный язык, нет букв,
   ссылка, эмодзи, заглушка, `system`, вложение без подписи.
3. **Отправка:**
   - перевод уходит в `postUserMessage`;
   - кэш: второй вызов с тем же ключом и текстом не зовёт адаптер, с другим текстом — зовёт;
   - `sourceLanguage: en` → без перевода;
   - таймаут или провайдер → пост без перевода плюс `desk-note`;
   - бюджет → без заметки;
   - ошибка Redis, базы или модуля → отправка проходит;
   - повтор по `idempotencyKey` → ранний выход без вызова.
4. **Адаптер стола:** JSON и multipart несут `content_attributes.translations.en`; без перевода — как сейчас.
5. **`desk-note`:** заметка с переводом; удалена / старше часа / согласие отозвано → без вызова.
6. **Приём:**
   - `pending` в том же create;
   - повтор вебхука — без второй задачи;
   - fan-out раньше постановки;
   - сбой постановки не роняет приём;
   - «N+1 раньше N» — порядок строк и догонка не зависят от порядка переводов.
7. **`reply`:** `translated` / `rejected` / retryable не на последней попытке (бросает, `PENDING`) / на последней
   (`FAILED`) / условия пропали (`FAILED` без вызова); условная запись — поздний дубль не перезаписывает и не шлёт
   событие; событие из перечитанной строки.
8. **Сторож:** перезапуск один раз с новым `jobId`, второй раз — `FAILED` и событие; сбой сторожа не ломает сверку.
9. **`toDto` / история:** поле только у советника, без `engine`; `translations` старые первыми, предел, незнакомый id,
   без `translatedFrom` — поля нет; удаление чистит перевод.
10. **Регрессия:** существующие спеки чата, сверки, доставки, модуля перевода и кампаний.
