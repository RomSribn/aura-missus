# AURAT-0090-001 — Веер запросов на список чатов упирается в собственный rate-limit

Дата: 2026-10-16
Статус: **заведена**, не начата, слэйв не назначен
Репозитории: `aura-bff` (эндпоинт), `aura-app` (вызов)
Повод: `AURAI-0005` — разбор первой рекламной кампании; найдено в логах прода.

## Что видно в проде

Логи BFF за 48 часов (15–16 октября) — **117 ответов 429 «Rate limit exceeded,
retry in 23 seconds»**, `statusCode 429`, `context: ExceptionsHandler`:

| Эндпоинт | Штук |
|---|---|
| `/v1/advisors/*/sessions/active` | 82 |
| `/v1/wallet` | 9 |
| `/v1/advisors/*/sessions/pricing` | 9 |
| `/v1/advisors/*/sessions/availability` | 9 |
| `/v1/advisors/*/messages` | 8 |

Все — с **одного** клиента (`user-agent: okhttp/4.12.0`, то есть Android).
Для этого человека экран бронирования и кошелёк не загрузились.

## Причина

`src/features/paid-session/model/use-active-sessions.ts` в `aura-app`
разворачивает **один запрос на каждого советника в списке** при каждом
возврате фокуса на вкладку чатов. В комментарии это описано честно:

> The BFF has no sessions-list read, only `GET /v1/advisors/:id/sessions/active`
> per advisor, so this fans out one request per thread. […] (BFF `TECH-DEBT #12`)

В проде 8 советников (`advisors`: ivan, alisher, sunshine, may, marta, olivia,
labsang, veronica). Значит один переход на вкладку — 8 одновременных запросов.
Плюс экран бронирования добавляет `pricing`, `availability`, `active` и
`/v1/wallet`. Несколько переключений подряд — и лимитер срабатывает.

Шапка rate-limit в прод-контейнере в env не задана (значения по умолчанию
`@fastify/rate-limit`); окно, судя по «retry in 23 seconds», минутное.

## Что сделать

1. **`aura-bff`: добавить список.** `GET /v1/sessions/active` — активные блоки
   по всем советникам текущего пользователя одним ответом. Это закрывает
   `TECH-DEBT #12` в BFF, ради которого веер и существует.
2. **`aura-app`: перевести `use-active-sessions` на новый эндпоинт** — один
   запрос вместо N. Веер оставить как запасной путь только если это дёшево;
   иначе удалить вместе с `serverEnabled`-ветками, которые нужны были вееру.
3. **Проверить лимиты на экране бронирования.** Даже после пункта 2 открытие
   брони шлёт `pricing` + `availability` + `active` + `wallet` разом. Либо
   поднять окно/порог для чтений с авторизацией, либо не дёргать `wallet`
   отдельно, если баланс уже есть в состоянии.
4. **Лимитер не должен ронять экран.** Сейчас 429 всплывает как ошибка. Чтение
   списка советников и цен стоит делать с повтором после `retry-after`, а не
   показывать пустой экран.

## Критерии приёмки

- Открытие вкладки чатов при 8 советниках — **один** сетевой запрос за
  активными сессиями.
- Прогон экрана бронирования десять раз подряд не даёт ни одного 429 в логах.
- В логах прода за сутки после выкатки — 0 ответов 429 на `/v1/*` от
  приложения.

## Чего не делать

- Не поднимать общий лимит «чтобы не мешал»: лимитер защищает от перебора
  кодов и чужих токенов. Чинить надо источник веера.
