# AURAT-0071-005 — Спека

Дата: 2026-09-14
Тип: задача, без отдельного `AURAF` (инфраструктурная правка deploy-файла)
Статус: **draft — ждёт одобрения владельца**

## Решение: один файл, два параметра с прод-значениями по умолчанию

В `deploy/coolify/chatwoot.compose.yml`:

```yaml
    FRONTEND_URL: ${CW_FRONTEND_URL:-https://chat.aura-app.cc}
...
    networks:
      coolify:
        aliases: ['${CW_RAILS_ALIAS:-chatwoot-rails}']
```

- **Прод** (приложение из `main`) ничего в панели не задаёт. Без переменных
  Compose подставляет ровно нынешние `chatwoot-rails` и
  `https://chat.aura-app.cc`. Единственный видимый след: при следующем деплое
  из `main` Coolify заведёт в панели `CW_FRONTEND_URL=https://chat.aura-app.cc`
  и положит её в контейнер. На работу это не влияет.
- **Dev** (приложение из `develop`) задаёт в панели:
  - `CW_RAILS_ALIAS=chatwoot-dev-rails` — добавить **руками**: Coolify не
    заводит переменные, упомянутые только в `aliases`;
  - `CW_FRONTEND_URL=https://chat-dev.aura-app.cc` — Coolify заведёт её сам со
    значением по умолчанию (прод-домен), и его **нужно заменить**;
  - dev-BFF: `CHATWOOT_BASE_URL=http://chatwoot-dev-rails:3000`.

### Почему не отдельный `chatwoot-dev.compose.yml`

- **Dev перестаёт проверять прод-файл.** Правка compose, опробованная на dev,
  не гарантирует того же в проде, и наоборот. Две копии по ~170 строк
  расходятся на первом же обновлении образа или новой переменной.
  Пример из истории — `AWS_REQUEST_CHECKSUM_CALCULATION`: забытая в dev-копии,
  она молча ломает вложения.
- `extends` из второго файла не годится: списки `aliases` при слиянии
  объединяются, и dev получил бы оба alias, то есть ту же коллизию. Теги
  `!override`/`!reset` рискованно пропускать через `Yaml::parse` Coolify.
- Отклонено и `FRONTEND_URL: ${SERVICE_URL_RAILS}` (домен из панели Coolify).
  Это магия Coolify, которая меняется от версии к версии: при отсутствии домена
  она сама генерирует sslip-домен. Явная `CW_*` согласуется с остальным файлом.

### Цена выбранного пути — названа

Корректность dev держится на двух переменных в панели. Если забыть
`CW_RAILS_ALIAS`, dev займёт `chatwoot-rails`, и прод-BFF начнёт через раз
попадать в dev. Тихой утечки не будет (у разных установок разные токены,
ответ 401), но прод будет частично сломан. Страховка — проверка в маноре из
`001`: у `chatwoot-rails` в сети `coolify` ровно один контейнер. Её
обязательно выполнить **до** провижининга dev.

## Что меняется

1. **`deploy/coolify/chatwoot.compose.yml`**
   - две строки выше;
   - комментарии, которые описывают один экземпляр: шапка («exactly one
     production compose» → два приложения Coolify из одного файла, prod из
     `main`, dev из `develop`, различие только в `CW_RAILS_ALIAS` и
     `CW_FRONTEND_URL`); комментарий у alias (у каждого экземпляра свой,
     `CHATWOOT_BASE_URL` BFF того же окружения называет его); комментарий о
     webhook (`bff.aura-app.cc` → публичный хост BFF своего окружения:
     `bff.` для прода, `bff-dev.` для dev); Postgres/Redis — «общие с BFF **того
     же окружения**»; `chatwoot` как имя роли и базы не конфликтует, потому что
     у экземпляров разные серверы Postgres.
2. **`deploy/chatwoot/provision-prod.rb`** — поведение для dev не меняется,
   правка небольшая и её можно вычеркнуть:
   - `AURA_WEBHOOK_URL` **обязателен** (`ENV.fetch` без умолчания). Нынешний
     дефолт `http://bff:3000/…` никогда не работал, `AURAS-0004` уже
     предупреждает о нём;
   - пункт 2 шапки переписать под реальность: публичный webhook, SSRF-защита
     включена;
   - в шапке — строка про второй экземпляр (ниже).
   Guard против `Aura (dev)` остаётся: тестовый inbox с этим именем лежит в
   прод-экземпляре.
3. **Как провижинить dev-экземпляр** (записать в шапку скрипта и в `007`):
   ```
   docker exec -i -e AURA_INBOX_NAME=Aura \
     -e AURA_WEBHOOK_URL=https://bff-dev.aura-app.cc/webhooks/chatwoot \
     <rails-контейнер dev> bundle exec rails runner - < deploy/chatwoot/provision-prod.rb
   ```
   Отдельная установка, поэтому `AURA_SERVICE_USER_EMAIL` и имя бота по
   умолчанию ни с чем не пересекаются. Аккаунт нужно сначала создать в UI dev
   (скрипт берёт первый существующий).
4. **Документы в `missus`** — только в папке задачи. `AURAS-0004` →
   *Environments* ведёт `aura-app-manor` вместе с `AURAD-0016`. Чтобы не
   конфликтовать с ним, абзац про `CW_RAILS_ALIAS`/`CW_FRONTEND_URL` и строку в
   *When it breaks* добавляю **в конце задачи**, поверх свежего `missus`. Если
   `aura-app-manor` возьмёт это на себя, не добавляю вовсе.

Код в `src/` не меняется: `chatwoot-rails` там не встречается,
`CHATWOOT_BASE_URL` уже приходит из окружения.

## Проверка

- **В слоте:** `docker compose config` по файлу **до** и **после** правки с
  пустым `.env` — вывод побайтно совпадает (прод не изменился); с dev-`.env` —
  `chatwoot-dev-rails` и `https://chat-dev.aura-app.cc`. `ruby -c` для скрипта,
  если ruby есть. `lint`/`build` BFF не затронуты.
- **В маноре, после мёржа в `develop` и создания dev-приложения:** у alias
  `chatwoot-rails` в сети `coolify` ровно один контейнер (прод), у
  `chatwoot-dev-rails` один (dev); прод-BFF отвечает; `chat-dev.aura-app.cc`
  открывается.

## Порядок и ограничения

- Мёрж в `develop` — только после подтверждения владельца. Прод-Chatwoot, по
  данным `aura-app-manor`, уже на `main`, поэтому мёрж его не перезапустит.
- Правка дойдёт до прода только при релизе `develop` → `main` и ничего там не
  изменит (значения по умолчанию).
- Создание dev-приложения в Coolify, DNS, бакет R2 и провижининг — в маноре.
