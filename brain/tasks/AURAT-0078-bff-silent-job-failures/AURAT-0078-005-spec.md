# AURAT-0078-005 — Спека: падение фоновой задачи оставляет строку

Дата: 2026-09-18
Статус: **done** (одобрена в `006`, закрыта в `009`)
Ветка: `feature/AURAT-0078-bff-silent-job-failures`
Закрывает: `TECH-DEBT.md` #31

## Задача одной строкой

Падение задачи в любой из **одиннадцати** очередей пишет строку с именем
очереди, именем задачи и текстом ошибки — и **никогда** с `job.data`.

## Решение развилки: базовый класс

Владелец просил решить: одиннадцать почти одинаковых `@OnWorkerEvent('failed')`
или общий базовый класс. **Базовый класс.**

Довод не в том, что копий меньше. Довод в том, **что именно копии не умеют**:
задача возникла из-за процессора, который забыли снабдить обработчиком. Одиннадцать
копий оставляют ровно ту же дверь открытой для двенадцатого — и открытой молча.
Базовый класс закрывает её компилятором: `extends WorkerHost` → `extends
LoggingWorkerHost`, и наследник **обязан** позвать `super(ИМЯ_ОЧЕРЕДИ)`.

Что это рабочий вариант, а не надежда — проверено по исходникам (`004-context`):
`@nestjs/bullmq` сканирует **цепочку прототипов**, метаданные `@OnWorkerEvent`
лежат на самой функции, обработчик привязывается к экземпляру наследника.

Отвергнутое:
- **Одиннадцать копий** — см. выше; плюс одиннадцать мест, где разойдётся формат.
- **Глобальный слушатель поверх всех воркеров** (обойти `allQueueOptions` и
  навесить `worker.on('failed')`) — пришлось бы лезть к `WorkerHost.worker`
  снаружи процессора и дублировать то, что `@nestjs/bullmq` уже делает
  декоратором.
- **`try/catch` в каждом `process()`** — проглотил бы ошибку и **отменил повторы**.
  Хуже, чем молчать.

## Что появляется

`src/jobs/logging-worker.host.ts`:

```ts
export abstract class LoggingWorkerHost extends WorkerHost {
  protected readonly logger: Logger;

  protected constructor(protected readonly queueName: string) {
    super();
    this.logger = new Logger(this.constructor.name);
  }

  @OnWorkerEvent('failed')
  onFailed(job: Job | undefined, error: Error): void {
    // Имя задачи, счёт попыток, текст ошибки. `job.data` — никогда:
    // там текст сообщения человека, токены устройств, токен покупки
    // (build rule 3).
    const attempts = job?.opts?.attempts ?? 0;
    const made = job?.attemptsMade ?? 0;
    const willRetry = made < attempts;
    const where = { queue: this.queueName, jobName: job?.name, attempt: made, attempts };
    const line = `${this.queueName} job failed: ${error.message}`;
    willRetry ? this.logger.warn(where, line) : this.logger.error(where, line);
  }

  @OnWorkerEvent('error')
  onWorkerError(error: Error): void {
    this.logger.error({ queue: this.queueName }, `${this.queueName} worker error: ${error.message}`);
  }
}
```

### Почему уровень зависит от попытки

`FcmFanoutProcessor` бросает **намеренно**: при частичной доставке он сужает
список токенов и роняет попытку, чтобы BullMQ назначил повтор. Обработчик «всё
в `error`» давал бы три строки уровня `error` на каждый частично доставленный
пуш — и уровень `error` перестал бы что-либо значить ровно в тот момент, когда
по нему захочется настроить оповещение.

Поэтому: **есть ещё попытки → `warn`; попытки кончились → `error`.**

Счёт сходится с BullMQ: на момент события `attemptsMade` уже увеличен на
текущую попытку, а решение о повторе принималось как `attemptsMade + 1 <
attempts` до увеличения — то есть `made < attempts` после. Очереди с
`attempts: 1` (`reconciliation`, `queue-retention`, `presence`, `play-refund`)
дают `error` **с первого падения**, что и требуется: за ними ничего нет.

Это будет закреплено тестом, а не оставлено на веру.

### Почему заодно `error` воркера

Обрыв Redis и ошибка планировщика повторяемых задач приходят в событие `'error'`
воркера. Слушателя нет, и `bullmq` в итоге делает `console.error(err)` — сырая
строка мимо pino: без `context`, без структуры, невидимая для любого разбора
логов. Один обработчик в том же базовом классе ставит её в общий строй.

**Это единственный пункт спеки шире буквальной формулировки задачи.** Если
владелец предпочтёт не трогать — выкидывается одним методом, остальное не
меняется.

### Что сознательно **не** делается

- **`stalled`** — задача, у которой истёк замок, возвращается в очередь и
  заканчивается либо успехом, либо `failed`, который мы уже ловим (BullMQ сам
  переводит её в `failed` после `maxStalledCount`). Отдельный обработчик добавил
  бы шум, не добавив покрытия.
- **Панель очередей, метрики, оповещения** — не в этой задаче. Строка уровня
  `error` со стабильной формой сообщения **и есть** то, по чему оповещение
  настраивается снаружи; своего кода это не требует.
- **Логирование успешных проходов.** Проверено: `ReconciliationService.sweep()`
  уже пишет строку, когда что-то добрала, и ловит ошибку каждого разговора
  отдельно. Единственная дыра там — падение всего прохода целиком, ровно как в
  `AURAT-0077`; её закрывает этот обработчик.

## Одиннадцать процессоров

| Процессор | `super(...)` | Убрать свой `logger` |
|---|---|---|
| `ReconciliationProcessor` | `RECONCILIATION_QUEUE` | — (его и не было) |
| `QueueRetentionProcessor` | `QUEUE_RETENTION_QUEUE` | да |
| `PresenceProcessor` | `PRESENCE_QUEUE` | — |
| `SessionsProcessor` | `SESSIONS_QUEUE` | да |
| `AccountErasureProcessor` | `ACCOUNT_ERASURE_QUEUE` | да |
| `FcmFanoutProcessor` | `FCM_FANOUT_QUEUE` | — |
| `ChatwootWebhookProcessor` | `CHATWOOT_WEBHOOK_QUEUE` | — |
| `AvatarProcessor` | `AVATAR_QUEUE` | да |
| `ContactNameProcessor` | `CONTACT_NAME_QUEUE` | да |
| `TarotProcessor` | `TAROT_QUEUE` | да |
| `PlayRefundProcessor` | `PLAY_REFUND_QUEUE` | да, **и убрать свой `onFailed`** |

Шесть собственных `logger` уходят: базовый объявляет `protected`, и наследник с
`private readonly logger` просто не скомпилируется. Имя класса в `context`
записи сохраняется — базовый берёт его из `this.constructor.name`.

`PlayRefundProcessor` теряет свой обработчик в пользу общего. Его сообщение
меняется с `play refund job failed:` на `play-refund job failed:` — имя очереди
теперь ровно то, что стоит в Redis и в конфигурации. Тесты в
`play-refund.processor.spec.ts` правятся под это.

Итог по объёму: **+1 файл, −6 объявлений логгера, −1 обработчик, +11 строк
`super(...)`**.

## Тесты

### 1. `logging-worker.host.spec.ts` — поведение обработчика

- пишет имя очереди, имя задачи и текст ошибки;
- **`job.data` не попадает в запись** — проверяется на трёх настоящих формах
  нагрузки: текст сообщения (`chatwoot-webhook`), токены устройств
  (`fcm-fanout`), токен покупки (`play-refund`); утверждение — как в образце:
  `JSON.stringify(calls)` не содержит секрета;
- `warn`, пока повторы есть; `error`, когда кончились; `attempts: 1` → `error`
  с первого раза;
- переживает событие без `job`;
- ошибка воркера пишется как `error`.

### 2. `processors.spec.ts` — сторож, чтобы это не расползлось обратно

По образцу `queues.spec.ts`, который ловит забытую очередь. Читает каталог
`src/jobs/`, берёт **каждый** файл `*.processor.ts` и для каждого утверждает:

- класс наследует `LoggingWorkerHost`;
- `Cls.prototype.onFailed === LoggingWorkerHost.prototype.onFailed` — то есть
  никто не переопределил обработчик.

Второе утверждение закрывает единственную ловушку наследования: наследник,
переопределивший `onFailed` **без** своего декоратора, не зарегистрирует
обработчик **вообще** — и тоже молча. Тест `it.each` называет каждый процессор
отдельной строкой, так что владелец видит в отчёте все одиннадцать имён — как и
просил «тест на каждый процессор».

Каталог читается с диска намеренно: двенадцатый процессор попадает под тест в
момент появления файла, а не когда кто-то вспомнит дописать его в список.
