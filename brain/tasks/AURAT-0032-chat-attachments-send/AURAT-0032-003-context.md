# AURAT-0032-003 — Разведка: три факта, меняющие постановку

Дата: 2026-08-21
Основание: исходники Chatwoot **v4.15.1** (версия сверена с живым — `GET /api`
вернул `4.15.1`), код BFF, код приложения, эмпирическая проверка Fastify.

## Факт 1. Chatwoot не проверяет наши файлы ВООБЩЕ

```ruby
# app/models/attachment.rb:186-199
def should_validate_file?
  return unless file.attached?
  # we are only limiting attachment types in case of website widget
  return unless message.inbox.channel_type == 'Channel::WebWidget'
  true
end
```

Наш инбокс — `Channel::Api`. Значит **ни проверки размера, ни проверки типа не
выполняется**. Знаменитые 40 МБ и `ACCEPTABLE_FILE_TYPES` — только для
веб-виджета.

**Это опровергает мою же запись в `002-check`** («нижняя граница задана
снаружи») и утверждение в `001-initial` («сверить с `ACCEPTABLE_FILE_TYPES` —
иначе он отвергнет уже принятый нами файл»). Внешнего пола нет. Пределы —
целиком наше решение, и если мы их не поставим, их не поставит никто.

## Факт 2. Опрос превращает «отклонили» в дубликат

Самое важное, и оно ломает обе исходные альтернативы, а не одну.

`ReconciliationService.sweep()` каждые 60 секунд перечитывает **все** разговоры;
`normalizeRestMessage` отображает REST `message_type: 0` в `'user'`, а
`ingestResolved` сохраняет **независимо от направления**.

Отсюда: если multipart дошёл до Chatwoot и **закоммитился**, а наша половина
упала — обрыв соединения после коммита, ошибка записи в Prisma, передеплой
посреди запроса, 15-секундный таймаут Rails пока ActiveStorage грузит в R2 —
то приложение показывает «не доставлено, нажмите чтобы повторить», **а через
минуту опрос молча сохраняет и доставляет этот же файл**. Пользователь жмёт
повтор — чаттер получает два.

**На этой кодовой базе не существует чистого отказа отправки.** Ни в одном из
двух вариантов.

## Факт 3. Приложение уже умеет то, ради чего предлагалась очередь

В `aura-app-manor` уже есть `status: 'pending' | 'failed'`, оптимистичная
вставка, «Not delivered · Tap to resend» и `retry()`. Требование
`AURAF-0011-009` закрыто на клиенте — для текста; на вложения оно
распространяется само, потому что файл лежит у пользователя в галерее.

## Прочее, проверенное и полезное

| факт | следствие |
|---|---|
| `POST …/messages`, multipart, поле **`attachments[]`** (массив), `content` может быть пустым, `message_type: incoming` работает | форма запроса известна точно |
| до 15 вложений на сообщение; отказ — `422` со строкой Ruby в теле | «постоянный отказ» отличим от «попробуй ещё» только по телу |
| `bodyLimit` Fastify **не применяется** к потоковым парсерам — проверено запуском | глобальный лимит поднимать не нужно и вредно; единственный шлюз — `limits.fileSize` у `@fastify/multipart` |
| `file-type@21.3.4` уже стоит как зависимость `@nestjs/common` | сниффер по содержимому — ноль новых пакетов, но объявить прямой зависимостью обязательно |
| `source_id` Chatwoot проходит насквозь через `MessageBuilder` и **отдаётся** в JSON сообщения | туда можно записать свой ключ и прочитать его обратно и вебхуком, и опросом |
| приложение **не импортирует** `SendMessageRequest` — строит `{ content }` руками | ослабление схемы запроса не ломает выпущенное приложение |
| HEIC Chatwoot относит к `file`, не к `image` | фото с айфона придёт чаттеру как безымянный файл, если приложение не сконвертирует |
| ширина/высота при создании **всегда null** — анализ ActiveStorage фоновый | геометрию картинки можно узнать только в момент загрузки |
| счётчик платной сессии — по стенным часам | 40 секунд загрузки внутри оплаченного блока сжигают оплаченные минуты |
| в сервисе **нет ни одного пути удаления** чего-либо, кроме FCM-токена | хранить байты у себя было бы первым персональным данным без пути удаления |
