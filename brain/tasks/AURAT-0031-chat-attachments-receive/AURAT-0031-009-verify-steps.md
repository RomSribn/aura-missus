# AURAT-0031-009 — Как проверить руками

Дата: 2026-08-21
Коммит: `c9f129c` на `feature/AURAT-0031-chat-attachments-receive`

## Сначала о том, чего на девайсе сегодня НЕ увидеть

Приложение вложения **не рисует** — это половина `aura-app-manor`, и она не
сделана. Картинка на экране не появится.

Поэтому проверка на девайсе сегодня отвечает на другой вопрос, и он не менее
важный: **не ломает ли новый ответ уже выпущенное приложение.** Оно на
контрактах `v0.7.0`, а теперь получает сообщения с пустым `content` и
незнакомым полем `attachments`.

## В маноре — по порядку, порядок не случайный

### 1. Образ. До всего остального

Меняется тег git-зависимости, а на этом `AURAT-0034` чуть не уронил прод.

```
docker build --target runtime -t aura-bff:0031 .
docker run --rm aura-bff:0031 node -e "require('@aura/contracts'); console.log('ok')"
```

Должно напечатать `ok`. Если падает — пакет приехал несобранным (`prod-deps`
ставит с `--ignore-scripts`, и `prepare` не отрабатывает); лечится копированием
из стадии `build`, оно в Dockerfile уже есть.

### 2. Миграция на населённой базе

```
docker compose -f deploy/docker-compose.prod.yml run --rm bff-migrate
```

Ожидается `message_attachments` и тип `AttachmentKind`. Существующие сообщения
не трогаются — правка чисто добавляющая.

### 3. Файл доезжает от чаттера до базы

Чаттер отправляет из Chatwoot **картинку без подписи** — именно без, это
сломанный случай.

```
GET /v1/advisors/<advisorId>/messages
```

(токен — `manor/secrets/mint-id-token.cjs`)

Ожидается сообщение с `"content": ""` и `attachments[0]` с `id`, `kind`,
`contentType`, `fileName`, `fileSizeBytes`.

**И проверить, чего там нет:** ни `chat.aura-app.cc`, ни `active_storage`, ни
`sourcePath`. Достаточно грепнуть тело ответа.

### 4. Байты. Единственное, что не проверено вообще ничем

```
GET /v1/attachments/<attachments[0].id>
```

Должен вернуться файл. **Это главный риск задачи:** BFF пойдёт в
`http://chatwoot-rails:3000/rails/active_storage/...` — маршрут Rails, в который
этот сервис никогда не ходил. Неизвестно, как там поведут себя host
authorization и `FORCE_SSL`.

Если вернулась 502 — смотреть логи BFF: скорее всего Rails ответил не тем, чего
мы ждём. Подстраховка есть (редиректы следуются, отбивка на публичный хост
доедет), но это рассуждение, а не факт.

### 5. Чужому — отказ

Тот же запрос с токеном **другого** пользователя → **404**, не 403 и не 200.

### 6. Опрос подхватывает, если вебхук сорвался

Остановить BFF → чаттер отправляет файл → поднять BFF. В течение ~60 секунд
вложение обязано появиться в истории. Это то, чего у вложений не было вовсе.

### 7. Повторная доставка ничего не удваивает

Переслать тот же вебхук ещё раз (или дождаться дубля от бота). В истории —
одно сообщение, одно вложение, второго пуша нет.

### 8. Пропавший файл — это 404, а не 500

Удалить вложение в Chatwoot, запросить его снова. Должна быть **404**.
Пятисотка означала бы, что приложение будет повторять то, что не может
получиться.

## На девайсе

1. Приложение свёрнуто, чаттер отправляет файл → **пуш приходит**.
2. Открыть тред: приложение **не падает и не показывает ошибку**. Пустой пузырь
   или отсутствие пузыря — нормально; вложения оно рисовать пока не умеет.
3. Обычная переписка текстом работает как раньше — это проверка на регресс,
   форма сообщения изменилась у всех сообщений, не только у вложений.

Если пункт 2 даёт сбой — сообщить: значит правка не настолько добавляющая, как
показали тесты, и приложение придётся обновлять одновременно, а не в своём
темпе.
