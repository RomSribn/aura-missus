# AURAT-0031-005 — Спецификация: приём вложений (сторона BFF)

Дата: 2026-08-20
Слот: `slave-1`, ветка `feature/AURAT-0031-chat-attachments-receive`
Закрывает: `AURAF-0011` строки 001–005, **колонку BE**. Колонка UI остаётся `✗`
— рисование в ленте делает `aura-app-manor` своей половиной той же задачи.

## Что меняется, одним абзацем

Сообщение перестаёт быть обязательно текстовым. Вложение приезжает вместе с ним
из Chatwoot, ложится в свою таблицу рядом с сообщением, едет в приложение как
непрозрачный `attachmentId` — и байты приложение забирает отдельным
аутентифицированным запросом к BFF, который сам ходит за файлом на сторону
Chatwoot (`AURAD-0011`). Ни адрес хранилища, ни имя бакета, ни хост Chatwoot на
устройство не попадают.

## 1. Контракт — `@aura/contracts` v0.9.0

Правка **чисто добавляющая**, приложение на `v0.7.0` не ломается.

```ts
export const AttachmentKind = z.enum(['image', 'audio', 'video', 'file']);

export const MessageAttachment = z.object({
  id: z.string(),              // непрозрачный id BFF — им и только им забираются байты
  kind: AttachmentKind,
  contentType: z.string(),     // MIME, для выбора отрисовки
  fileName: z.string(),
  fileSizeBytes: z.number().int().nonnegative().nullable(),
  width: z.number().int().positive().nullable(),
  height: z.number().int().positive().nullable(),
});

Message = z.object({ …, attachments: z.array(MessageAttachment).default([]) });
```

Решения по форме:

- **`content` не трогаем.** Он уже `z.string()` и пустую строку принимает; у
  сообщения-вложения текст будет `''`. Это и делает правку добавляющей.
- **Адреса в контракте нет ни в каком виде** — ни публичного, ни подписанного
  (`AURAD-0011`: подписанный протух бы в кэше ленты).
- **`fileSizeBytes`, а не `fileSize`** — единица в имени, как `balanceMinor` и
  `ratingTenths` по всему контракту. Отход от чернового имени в шаге 004,
  осознанный.
- **`nullable`, а не `optional`** у размеров: Chatwoot присылает `width`/`height`
  как `null` для не-картинок, и честнее возить `null`, чем прятать поле.
- **Ослаблять свой выход не будем, но и строже чужого входа делать не станем**
  (ловушка из шага 004): всё, что приходит не целым числом или отрицательным,
  нормализатор превращает в `null` — схема не нарушается никогда, потому что
  гарантию даёт граница, а не валидатор.
- `thumb_url` **не забираем и не храним**: это второй прокси-путь на каждое
  вложение ради превью, которое приложение и так умеет ужимать. Если лента
  начнёт тяжелеть — отдельный follow-up.

Пакет: `v0.8.2 → v0.9.0`, тег пушится, зависимость BFF поднимается.

## 2. Хранение — миграция Prisma

```prisma
enum AttachmentKind { IMAGE AUDIO VIDEO FILE }

model MessageAttachment {
  id                   String  @id @default(cuid())
  messageId            String
  message              Message @relation(fields: [messageId], references: [id], onDelete: Cascade)
  chatwootAttachmentId Int
  kind                 AttachmentKind
  contentType          String
  fileName             String
  fileSizeBytes        Int?
  width                Int?
  height               Int?
  sourceUrl            String
  createdAt            DateTime @default(now())

  @@unique([messageId, chatwootAttachmentId])
  @@map("message_attachments")
}
```

**Идемпотентность (жёсткое правило 6) — конструкцией, а не проверкой.**
Вложения пишутся вложенным `create` **внутри той же вставки сообщения**, которая
уже идемпотентна по `(conversationId, chatwootMessageId)`. Повторный вебхук
падает на `P2002` по сообщению и до вложений просто не доходит. `@@unique` —
ремень поверх этого, а не основной механизм.

`sourceUrl` — того же класса, что уже лежащие рядом `chatwootConversationId` и
`chatwootMessageId`: идентификатор чужой системы в нашей таблице, который
**разыменовывает только адаптер**. Сервис его не парсит и не показывает.

## 3. Нормализатор — снять отсев

`buildMessage` сейчас первой же строкой выкидывает сообщение без текста, и через
него идут **оба** пути — вебхук и REST опроса. Новое правило:

```
text = typeof content === 'string' ? content : ''      // при вложении приходит null
attachments = нормализовать(wire.attachments)
if (text === '' && attachments.length === 0) return null   // прежнее поведение сохранено
```

То есть: активности, шаблоны, приватные заметки и по-настоящему пустые
сообщения по-прежнему не проходят — меняется ровно один случай, «текста нет, но
есть вложение».

Нормализация одного вложения:

- `file_type` вне `image|audio|video|file` — **вложение выбрасывается**
  (`location`, `share`, `story_mention`, `fallback`, `contact` — «не в scope» по
  `AURAF-0011`). Если после этого у сообщения не осталось ни текста, ни
  вложений — выбрасывается всё сообщение.
- `contentType`: из `content_type`, иначе выводится из `extension` по
  небольшой таблице, иначе `application/octet-stream`. Причина запаса: живой
  payload шага 003 `content_type` содержит, но REST-диалект Chatwoot его может и
  не отдавать — проверять форму по факту, а не по документации.
- `fileName`: последний сегмент пути `data_url`, декодированный. Санитизация
  обязательна — имя уезжает в заголовок `Content-Disposition`: убрать разделители
  пути, управляющие символы и перевод строки, ограничить длину. Запасное имя —
  `attachment.<ext>`.
- Оба диалекта (`CwMessageWire`, `CwWebhookMessageWire`) получают
  `attachments?: CwAttachmentWire[]`; `thumb_url` в интерфейсе **не объявлен** —
  что не объявлено, то не может утечь (тот же приём, что с `user` в typing).

## 4. Отдача байтов — `GET /v1/attachments/:id`

- **Транспорт** (`attachments.controller.ts`, модуль `chat`): Firebase-токен уже
  проверяет глобальный guard; контроллер валидирует id и делегирует.
- **Сервис** (`attachments.service.ts`): грузит вложение → сообщение →
  разговор, сверяет `conversation.userId` с текущим пользователем. Чужой или
  несуществующий — **404, не 403**: эндпойнт не должен подтверждать, что такое
  вложение вообще есть.
- **Адаптер** (`ChatwootClient.fetchAttachment`): единственное место, которое
  разыменовывает `sourceUrl`. Три вещи здесь неслучайны:
  - **Наш служебный токен Chatwoot в этот запрос не идёт.** Адрес публичный, и
    отправлять на него заголовок аутентификации незачем и опасно.
  - **Проверка происхождения** — origin адреса обязан совпасть с
    `CHATWOOT_BASE_URL`, иначе отказ. Это защита от SSRF: даже подписанный
    вебхук не должен уметь заставить сервер сходить куда угодно.
  - **Стрим, а не буфер**: тело ответа Chatwoot переливается в ответ клиенту,
    файл целиком в память не попадает.
- Отдаём **сохранённый** `contentType`, а не заголовок Chatwoot: приложение уже
  приняло решение, как рисовать, по тому, что мы объявили в сообщении — отдать
  другое значит сделать это решение неверным.
- `Cache-Control: private, max-age=…, immutable` — содержимое по id неизменно.

**Новых переменных окружения не появляется.** Токен R2, который предполагал
`AURAD-0011`, не нужен: адрес публичный, и ходит по нему только сервер (шаг
003). Уточнение будет дописано в сам `AURAD-0011`, чтобы брейн не расходился с
реальностью.

## 5. Доставка — не меняется

Пуш и сокет по-прежнему кормятся одним и тем же сохранённым сообщением
(жёсткое правило 5). Вложение приезжает внутри того же `MessageDto`; отдельного
пути доставки у него нет. FCM остаётся data-only пингом.

## 6. Тесты (слэйв — чистые, без БД/Redis/Chatwoot)

- вебхук с вложением и `content: null` **проходит** и несёт вложение;
- по-настоящему пустое сообщение по-прежнему выбрасывается;
- вложение неподдерживаемого типа выбрасывается, а сообщение с текстом — нет;
- сообщение только из неподдерживаемого вложения выбрасывается целиком;
- `data_url` и `thumb_url` **не появляются** в DTO (проверка на строку, как с
  `Real Agent` в существующем тесте);
- имя файла: восстановление, декодирование, санитизация;
- `contentType`: из payload, из `extension`, запасной;
- повторная ингестия не создаёт второе вложение (на фейковом репозитории);
- `GET /v1/attachments/:id` чужого пользователя → 404;
- отказ адаптера на адрес чужого происхождения.

- `AURAD-0011` — приписка про ненужный токен R2.

## Что эта задача сознательно НЕ делает

- **Не рисует ничего в приложении** — это половина `aura-app-manor`.
- **Не даёт отправлять вложения** — это `AURAT-0032` (там же придётся снять
  `.min(1)` у `SendMessageRequest.content`).
- **Не возвращает 13 потерянных файлов.** Они не были сохранены вообще, а
  водяной знак опроса ушёл вперёд по более поздним текстовым сообщениям —
  обычный опрос до них уже не дотянется. Достать их можно разовым глубоким
  перечитыванием разговора с нуля: ингестия идемпотентна, так что вставится
  только недостающее. Но каждая такая вставка — «новое» сообщение, то есть
  **пуш пользователю за позавчерашний файл**. Решение владельца, отдельным
  шагом после мержа.

| Риск | Что делаем |
