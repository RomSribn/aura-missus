# AURAT-0127-001 — Разметка воронки: от приглашения на сессию до оплаты

Дата: 2026-10-23
Статус: **заведена**, не начата, слэйв не назначен
Репозитории: `aura-app` (события), `aura-bff` (приём и хранение), веб — когда дойдёт
Повод: `AURAI-0005`. За восемь дней рекламы 115 человек получили приглашение на
платную сессию, заплатили **2**. Где отваливаются остальные 113 — измерить нечем.

## Что мы знаем и чего не знаем

Концы воронки в базе есть, середины нет:

| Шаг | Чем измеряется сейчас |
|---|---|
| Приглашение отправлено | `messages.sessionInvite` ✓ |
| Открыл экран бронирования | **нечем** |
| Выбрал длительность и слот | **нечем** |
| Увидел цену | **нечем** |
| Денег не хватило → открылся Top Up | **нечем** |
| Выбрал тир, ушёл в кассу магазина | **нечем** |
| Касса вернула результат | **нечем** |
| Кредит начислен | `play_purchases`, `ledger_entries` ✓ |
| Сессия забронирована | `sessions` ✓ |

Три разных диагноза — «не дошёл до бронирования», «увидел цену и передумал»,
«застрял в кассе» — требуют трёх разных лечений, а различить их нельзя.

## Что сделать

### События (минимальный набор, который отвечает на вопрос)

| Событие | Поля |
|---|---|
| `booking_opened` | `advisorId`, `source`: `invite` / `profile` / `chat` / `quick` |
| `booking_slot_chosen` | `minutes`, `instant: bool` |
| `booking_price_seen` | `costMinor`, `balanceMinor`, `needsTopUp: bool`, `offerPct` |
| `topup_opened` | `shortfallMinor` |
| `topup_tier_selected` | `sku` |
| `topup_checkout_started` | `sku` |
| `topup_checkout_result` | `sku`, `outcome`: `success` / `cancelled` / `failed` |
| `booking_confirmed` | `sessionId` |
| `booking_failed` | `reason` — брать готовый `ConfirmError` из `use-booking-confirm.ts`: `slotTaken` / `slotGone` / `notBookable` / `failed` |

Никакого свободного текста: только перечисления, суммы и идентификаторы, которые
у нас и так есть.

### Хранение

Первой стороной, у себя, а **не** только в Meta: нам нужно джойнить с `users`,
`wallets`, `sessions` и считать по когортам. Таблица вида `app_events`
(`id`, `userId`, `name`, `props jsonb`, `clientTs`, `serverTs`, `platform`,
`appVersion`) со сроком хранения — как у остальных данных в проекте.

### Не сделать хуже

- **Батчить.** Запрос на событие удвоит тот самый веер, из-за которого живёт
  `AURAT-0090` (120 запросов в минуту на IP, глобально). Копить и отправлять
  пачкой в фоне; отдельный лимит для этого маршрута.
- **Не ронять экран.** Падение отправки событий не должно влиять ни на что.

## Что это задевает за пределами кода

**Инвентарь в `AURAT-0040-006` утверждает: «Ни Crashlytics, ни Sentry, ни
analytics… нет».** Это надо перепроверить (после `AURAT-0088` там уже Meta SDK)
и после задачи привести в соответствие:

- политика приватности на `aura-app.cc/privacy/`;
- **Data safety** в Play Console;
- **App Privacy** в App Store Connect.

`AURAT-0088` уже один раз показал, что новое событие обнуляет декларации в
обоих магазинах и отправляет их на повторное ревью. Заложить это в работу,
а не обнаружить после.

## Критерии приёмки

Одним SQL-запросом получить по когорте дня: сколько человек получили
приглашение → открыли бронирование → увидели цену → открыли Top Up → начали
оплату → оплатили → забронировали. С долями между шагами.

На этих числах должен быть виден ответ: где именно теряются те 113.
