# AURAT-0050-005 — Спека: идемпотентный `ensureUser` под параллелью

Дата: 2026-09-01
Статус: draft — ждёт аппрува
Репозиторий: **aura-bff**, ветка `feature/AURAT-0050-ensure-user-race`

## Причина (из 004, проверено на Prisma 7.8.0)

`update: { phoneE164: data.phoneE164 ?? undefined }` при `phoneE164 === null`
схлопывается в пустой объект. Пустой `update` Prisma не умеет положить в
`DO UPDATE SET`, поэтому бросает нативный `INSERT … ON CONFLICT` и уходит на
find-then-create в транзакции: `SELECT` → `INSERT`. Два параллельных первых
запроса оба видят «строки нет» и оба вставляют — второму прилетает P2002.
Гипотеза «Prisma требует уникальное поле в обеих ветках» не подтвердилась:
важна **непустота** `update`, а не то, какое поле в нём лежит.

## Решение — оба конца, а не один

Владелец предложил выбрать: ловить P2002 либо вернуть нативный `ON CONFLICT`.
Предлагаю сделать **и то и другое**, и вот почему это не перестраховка ради
перестраховки: это два разных по природе средства.

1. **Вернуть нативный `ON CONFLICT` — лечение.** Гонки не остаётся вовсе: одна
   инструкция, атомарность обеспечивает сам Postgres, а не наш код. Одно
   обращение к БД вместо транзакции с тремя `SELECT` на каждом запросе. Это
   ровно то, чего требует правило сборки #6 — идемпотентность на шве, а не в
   надежде на удачу.
2. **`catch P2002` → перечитать строку — страховка.** Выбор плана живёт внутри
   Prisma и в нашем файле не виден: сегодня он зависит от непустоты `update`,
   завтра — от чего-нибудь ещё. Ровно так этот баг и появился. Ловушка держит
   обещание идемпотентности **независимо от того, какой план выбрала Prisma**, и
   это та же идиома, что уже стоит в четырёх репозиториях проекта (карта дня,
   сообщения, беседы, кошелёк).

Только (1) — обещание, завязанное на невидимую в коде деталь. Только (2) —
оставляет на горячем пути транзакцию с тремя `SELECT` при каждом запросе
пользователя без телефона в токене.

### Код

`src/modules/auth/prisma-users.repository.ts`:

```ts
async upsertByFirebaseUid(data: {
  firebaseUid: string;
  phoneE164: string | null;
}): Promise<UserRecord> {
  try {
    return await this.prisma.user.upsert({
      where: { firebaseUid: data.firebaseUid },
      create: { firebaseUid: data.firebaseUid, phoneE164: data.phoneE164 },
      // firebaseUid переписывается своим же значением намеренно: только
      // непустой update компилируется в INSERT … ON CONFLICT DO UPDATE.
      // Пустой (а он пуст, когда в токене нет телефона) роняет Prisma на
      // find-then-create, который два одновременных первых запроса
      // проигрывают оба (AURAT-0050).
      update: {
        firebaseUid: data.firebaseUid,
        phoneE164: data.phoneE164 ?? undefined,
      },
    });
  } catch (error) {
    // Инструкция выше этого дать не может — но план выбирает Prisma, не мы.
    // Проиграть гонку здесь не ошибка, а штатный исход: читаем строку
    // победителя и отдаём её.
    if (isUniqueViolation(error)) {
      const existing = await this.prisma.user.findUnique({
        where: { firebaseUid: data.firebaseUid },
      });
      if (existing) {
        return existing;
      }
    }
    throw error;
  }
}
```

плюс модуль-локальный `isUniqueViolation` — ровно тот, что уже лежит в
`prisma-sessions.repository.ts` и `prisma-wallets.repository.ts`.

`phoneE164: … ?? undefined` остаётся как есть: токен без клейма телефона не
должен затирать сохранённый номер.

### Что НЕ меняется

- Сигнатуры `UsersRepository` / `UsersService`, все 14 точек вызова.
- Розыгрыш карты дня — он гонку держит, трогать нечего.
- Схема БД и миграции: констрейнт `users_firebaseUid_key` и так делает ровно
  то, что нужно, — он тут не виноват, он тут работает.

## Тесты (чистые, без БД / Redis / Chatwoot)

Новый `src/modules/auth/prisma-users.repository.spec.ts`:

1. **Параллельный `ensureUser` — тот самый тест.** Поддельный `PrismaService`
   моделирует медленный путь: `upsert` читает «есть ли строка», уступает
   планировщику, потом вставляет; второй вставляющий получает P2002, как
   настоящий Postgres. Четыре одновременных вызова → четыре ответа, **один и
   тот же `id`**, **одна строка** в хранилище. Без правки тест падает с P2002 —
   это и есть страховка от возврата регрессии.
2. **План остаётся нативным.** Настоящий генерированный клиент Prisma на
   поддельном драйвер-адаптере (тот же приём, которым в 004 доказана причина;
   БД не нужна) — проверяем, что и с телефоном, и с `phoneE164: null`
   `upsert` компилируется в **одну** инструкцию с `ON CONFLICT`, без
   транзакции. Именно этот тест ловит возврат пустого `update` — то есть
   причину, а не только симптом.
3. Ошибка не-P2002 пробрасывается; P2002 без строки при перечитывании
   пробрасывается тоже (иначе мы проглотим настоящую поломку).

## Комментарий над `ensureUser`

Сейчас: «Idempotent: repeat calls for the same Firebase UID converge on one
row» — верно последовательно, неверно параллельно. После правки утверждение
становится честным, но само по себе оно ничего не объясняет; перепишу так,
чтобы было видно, **чем** оно обеспечено и где это проверяется.

## TECH-DEBT

Одна новая строка (#26): после правки `ensureUser` **пишет** строку `users` на
каждом аутентифицированном запросе — `ON CONFLICT DO UPDATE` всегда попадает в
`DO UPDATE` и двигает `updatedAt`. Для пользователей с телефоном в токене это
уже сегодняшнее поведение, для остальных станет таким же. Это осознанная цена
одной атомарной инструкции; когда запись на каждый запрос станет заметна
(autovacuum, WAL), путь известен — читать сначала, писать только при отличии.

## Находка за границей задачи (чинить не здесь)

`aura-app`, `src/features/push/model/push-registration.ts:31` — `catch {}` без
ретрая. После этой правки конкретно P2002 оттуда уйдёт, но дыра остаётся: любой
5xx на регистрации токена всё так же молча стоит человеку пушей до следующего
запуска приложения. Это половина приложения и **другой** манор — ID под неё
минтит `aura-app-manor`. Выношу как рекомендацию владельцу, здесь не трогаю.
