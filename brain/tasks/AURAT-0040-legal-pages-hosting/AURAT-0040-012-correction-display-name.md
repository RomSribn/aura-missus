# AURAT-0040-012 — Поправка: имя пользователя собирается. Расхождений десять

Дата: 2026-08-28
Правит: `AURAT-0040-007`, пункт **B1**
Поднято: `slave-0` из `aura-app-manor`, 2026-08-28; проверено здесь по коду

## Что было написано неверно

`007` B1 утверждал: «`the display name you choose` — имени не существует…
`getUserDisplayName()` падает в захардкоженную константу… пользователь ничего не
выбирает». Из этого следовало «вычеркнуть» — и это попало в `AURAS-0002` как
указание **не включать** имя в Data Safety.

## Как на самом деле

```
src/screens/profile/model/use-profile.ts:127
  await authService.getCurrentUser()?.updateProfile({ displayName: trimmed });
```

Шит «Edit profile» сохраняет введённое пользователем имя.
`DEFAULT_DISPLAY_NAME = 'Vasya'` — **фолбэк на пустое значение, а не значение**:
`get-display-name.ts:7` читает `displayName` у Firebase и подставляет литерал,
только когда имени нет. `slave-0` подтвердил на устройстве — профиль показывал
введённое имя, поле редактирования было им заполнено.

Имя хранится в **Firebase Auth, то есть у Google**. В нашей базе его нет и не
будет: в этот сервис оно не отправляется вовсе.

## Почему промах случился, и это важнее самого промаха

Вывод о **сборе** был сделан из схемы `prisma` и из пути **чтения** в
приложении. Ни то, ни другое сбор не определяет.

**Авторитет — путь записи.** И он может уходить мимо нашего API целиком: тут
приложение пишет напрямую третьей стороне по маршруту, которого наша схема не
видит и увидеть не может. Перечень, построенный по схеме БД, такие данные
пропускает **систематически**, а не случайно.

Проверено, нет ли той же дыры где-то ещё — прошёл по всему, что приложение
пишет напрямую наружу: `updateProfile` **единственный** такой вызов, `photoURL`
не ставится, ни analytics, ни crash-репортинга в зависимостях нет. Промах ровно
один, но метод был неверен, и это записано здесь именно поэтому.

## Что меняется

- **Расхождений десять, а не одиннадцать.** §02 «the display name you choose» —
  политика была права.
- Остальные три пункта блока B `007` (дата рождения; модель устройства / версия
  ОС / версия приложения / язык / IP / краши; Apple) **остаются в силе** — они
  проверялись по пути записи (`devices-api.ts` шлёт `{ platform }` и всё) и по
  списку зависимостей, а не по схеме. `slave-0` отдельно подтвердил, что дата
  рождения сегодня действительно не собирается.
- **Data Safety: `Personal info → Name` — отдельная строка, вычёркивать нельзя.**
  `AURAS-0002` поправлен на месте: это живой рунбук, по нему заполняется форма, и
  ошибка в нём стоит отклонённого листинга. Здесь — только запись, шаги вперёд.
- Побочно: §05 политики перечисляет Google как «phone-number sign-in, push
  notifications and crash diagnostics» — профильное имя там **не названо**, хотя
  живёт именно у него. Одиннадцатым расхождением это не считаю: формулировка
  неполна, а не ложна. Владельцу при правке политики стоит знать.

## Что осталось верным в `007` без изменений

Оба пункта, которые `slave-0` принял к себе: §08 обещает удаление аккаунта,
которого нет (блокер листинга Play, `TECH-DEBT #24`), и §05 описывает
один-к-одному с выбранным советником там, где продукт рисует персону над общим
столом. Плюс отсутствие MX при двух опубликованных адресах.
